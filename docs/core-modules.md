# Core Modules

A high-level map of what each area of the codebase is for. This document describes stable seams — composition roots, domain owner modules, and public contracts. Implementation files evolve inside each area without requiring doc updates.

Coral's product identity is a coding-assistant plugin for Claude Code, Codex, and GitHub Copilot CLI. Its internal architecture is a local coding-agent coordination layer: the coordinator owns live decisions and recovery, domains own truth vocabulary, transport carries requests, and the CLI is the local operator surface.

## CLI and Client

The CLI parses commands, follows detached launches via the `jobs.wait` IPC subscription, and formats output for humans and machines. The client layer owns backend startup, IPC dispatch/subscriptions, direct `read-model/CoralStore` read helpers for no-coordinator paths, and the HTTP gateway/admin helpers exposed through the public barrel. `backend provider-host list|inspect` are served operator reads requiring `system:debug`; `backend provider-host evict` is a mutation requiring `system:shutdown`. Inspect and evict accept either one opaque exact host reference or a `--work-dir` resolver, never both. `cli/handoff-notice.ts` owns the one-time stderr notice printed after a CLI invocation is delegated to a newer build; `cli/format/handoff-publication.ts` owns the human diagnostic and cause-specific successor formatting shared by the notice and routing-resolution surfaces. Publication incidents carry the exact invocation ID, and terminal incidents carry the attempted terminal disposition so formatting distinguishes failed work from finished work without treating the recording phase as an execution result. The notice writes directly to `process.stderr` rather than through `emit.ts` so it never corrupts a machine-readable result on stdout. Coordinator startup logs the publication incident as structured domain data and does not import CLI formatting.

## Backend

The coordinator is a composition root, not a domain. The root is split into a coordinator layer and a transport layer: the coordinator owns lifecycle, startup recovery, projection freshness, corpus notify publication, job-backed KB source import/reindex, and cross-domain assembly; transport owns IPC plus HTTP/SSE parsing, validation, and wire formatting. New domain logic does not land in either layer; it stays in its owning domain and is reached through explicit owner modules/contracts.

## Runtime

The backend uses a **single Runtime world** pattern: one interface with a fixed set of I/O subports (time, storage, paths, process, ids, env), swapped once at composition. Every I/O-touching module routes through it. The real runtime is used in production; a deterministic counterpart powers the simulation lane.

## Journal

The Journal is the event-sourced truth spine for all domain state. It provides append, rebuild, strict envelope decoding, domain append-validator, and projection-reducer dispatch primitives backed by SQLite in WAL mode. `store/` exports the SQL/Journal substrate; product read APIs live in `read-model/CoralStore` and domain-owned read query modules. Projected jobs deliberately retain two coordinates: `projection_jobs.project_root` is project identity, while nullable `projection_jobs.work_dir` is the canonical execution directory (`NULL` only for KB jobs). Ambient job selectors and unfiltered event streams match `work_dir` exactly; explicit wait, abort, and detail allow one-directional containment from the caller directory to the job directory. Both relations govern non-KB jobs only — a KB job matches from every caller directory. `coral-cli jobs` bypasses the ambient filter and retains project-root grouping. There are no body versions, upcasters, or old-format readers: the application-wide store format covers every persisted codec and executable DDL fragment. Startup automatically resets older or corrupt/unsupported state; a newer store still produces the typed operator-recovery refusal. Before that classification, `store/active-store-selection.ts` and `store/active-store-selection-coordination.ts` own the active-store selection/transition coordination records and the recovery protocol that reconciles them against the current build, and `store/startup-store-routing.ts` (`routeOrOpenBackendStoreAtStartup`, wired into `coordinator/lifecycle.ts`) is the startup call site that turns that protocol into an opened store or a validated handoff to a newer local build.

## Causality

Cross-stream event references live below the domains in `causality/`. `CauseRef` is vocabulary, not storage: domains can point at originating Journal events without importing `store/`, database handles, or each other's shells.

## Recovery Containment

`recovery/` owns the single recovery-enumeration boundary, opaque source handles, source registry, and quarantine persistence; raw source modules and settlement policy remain domain-owned and carry no registry/pool knowledge into the boundary. `RecoveryContainment.each(source, policy)` is the only enumeration surface and runs the scan → hydrate → settle phases. Quarantine or durable-continuation dispositions converge in `recovery_quarantine`, while successful exact retries remove their retained row. Static architecture invariants reject direct scan access, forged handles/receipts, eager pre-enumeration, and unmanifested startup walks. Because `recovery_quarantine` is executable store DDL, adding it moved the application-wide store-format fingerprint for this release.

## Domains

Each domain is self-contained: its own contract (events, projection, read-models), its own functional core (pure state transitions), its own imperative shell (persistence, loop control, external effects), and explicit coordinator-facing owner modules for commands, queries, recovery, and ports. Domains do not import each other; cross-domain composition happens at the backend layer only. Ownership surfaces are real contracts/modules, not `api.ts` barrels or compatibility shims.

## Provider Adapters

Provider adapters translate between the domain contract and external CLIs. Codex uses the Codex app-server surface; Claude uses a broker helper around Claude CLI, defaulting to `claude -p` stream-json and retaining an opt-in PTY TUI transport. Adapter-level changes must preserve wire-compatibility with the adapted provider. Adapters normalize provider usage at this boundary to the canonical additive `UsageSummary` (`inputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `outputTokens`, optional `costUsd`) before it reaches jobs. Provider-owned profile, binding, and continuity parsers contribute their exact persisted contracts to the application-wide store format. `ProviderRegistry.register` rejects a managed provider unless it declares `provider-artifact-discard.v1` with both `discardArtifacts` and `reconcileDiscard`; reconciliation is closed over `applied | not-applied | definitive-failure | unknown`.

Provider-host state has three separate vocabularies: process `open | closed`, derived serviceability `serviceable | unserviceable | unknown`, and fresh-placement admission `candidate | blocked`. These are not carrier states: a carrier verdict asks whether work exists, while provider-host serviceability asks whether a present process has answered a typed prerequisite successfully. `providers/app-server-transport.ts` records one diagnostic fact only after a provider response completes and retains its sequenced host-log span; it makes no serviceability decision. Provider-owned pure classifiers interpret those facts, and `providers/host-admission.ts` joins each finding to the exact owner-local slot, host reference, and transport generation. A mute request produces no fact, so no timeout, clock, or failure counter can move the host out of `unknown`. A negative finding blocks only the fresh-placement wrapper; exact session attachment remains available for interrupt and probe.

The shared admission collection carries no close authority. Coordinator-local placement is owned by `DefaultProviderHostManager`; routed placement is owned by the provider proxy's narrower host pool. Each owner retains a naturally retired blocked host as a bounded-diagnostics tombstone and performs its own exact eviction. Only the coordinator administration service may aggregate those owners for an operator: it captures the owner set, requires every inventory to validate, resolves exactly one row, and routes inspect or eviction back to that row's owner. Derived serviceability never invokes eviction.

Coordinator-local app-servers are admitted only on a platform with signalable POSIX process groups. They are spawned detached, and their process incarnation plus `kill(-pid, 0)` group proof are recorded on the host entry before admission; teardown reaps that identity through the shared recorded-containment primitive. Proxy-owned app-servers are not detached again because the guardian has already established their containing group; per-host close is child-only, so leaked descendants can remain until proxy-set teardown. The same host entry carries a token map of acquisition or attached-session pin origins. Idempotent release closures remove exact tokens, and the map size is the retirement authority: Codex uses `'unleased'`, Claude uses `'unleased-and-host-idle'` because its internally multiplexing broker must also emit an idle `host/stats`, and `'never'` disables idle retirement. External Codex does not emit Coral's `host/stats`. The no-live-Codex-job diagnostic reports outstanding pin origins but never closes on that evidence, because an attached-session pin may have no job id.

## Expansion

Expansion is the installable runtime contract that lets optional backends bind to a domain's `RuntimeBinding<Backed<T>>` cells without the domain knowing whether the binding is held. An `Expansion = (host) => void | Promise<void>` is a single-function contract; bundled and installed expansions receive the same host contract. The KB daemon owns and composes `ExpansionLifecycleService`. Its manifest catalog merges the static `BUNDLED_ENGINES` entries with validated installed-tier rows from `expansion_manifest_catalog`. At boot, the daemon invokes bundled loaders from its static fallback registry; an explicit equip dynamically imports an installed entry, invokes it under a fresh disposable scope, and persists `{id, version, installed_at}` in `expansion_state`. Unequip disposes that scope and deletes the row.

KbRuntime registers built-in capability descriptors and empty `RuntimeBinding<Backed<T>>` cells; engines fill those cells through the same binding contract whether they are bundled or installed. Bundled Orama binds `kb.fts` during expansion lifecycle startup. `kb.embedding` carries no constructor-time default — embedders are peer engines (`gemini`, `onnx`) — and no current first-party engine binds `kb.vector`; external engines may fill it through the provider-neutral contract. Single-occupancy is enforced inside `RuntimeBinding.bind` itself (throws `binding-occupied` if held), not by lifecycle bookkeeping. Retrieval-consumer freshness is observed through `ConsumerDriver.waitFreshUntil('corpus', snapshot, consumerId)` after the Corpus commit; readiness is a comparison (`backed.consumer.cursor ≥ corpus version`), not a method on the `Backed<T>` contract. Every Corpus consumer registration must provide `readAuthoritativeFreshness(target)` returning `current | stale | unavailable`; `ConsumerDriver.register` throws when it is absent.

## Knowledge Base

The KB domain owns the Corpus markdown authority over notes, sources, principles, communities, and wiki entries; text and vector search contracts; note and wiki mutation; source persistence; background curation (content-fingerprint-driven note/source classification, community detection, entity consolidation, wiki touch-journal drain that bubbles touched Knowledge links one position toward the front per touch event — transposition heuristic; semantic wiki mutations are user/LLM workflow only); conflict-free multi-machine git sync for derived KB metadata; and the project-scoped memo scratch lifecycle. Source import conversion is coordinator-owned because it can be long-running and is represented as an internal `kb.source_import` job with explicit readiness (`commit`, `base-search`, `active-vector`, `all-equipped`). Explicit reindex is also coordinator-owned as an internal `kb.reindex` job: the KB op rebuilds text artifacts, and the coordinator service waits for base-search freshness. These jobs are Journal-observable process attempts, not provider/session jobs.

Classification pending state is content-driven: the index stores `bodyHash` plus note/source `inputFingerprint`, and curation claims only entries where `inputFingerprint` is absent or differs from the `bodyHash` already stored in the same index entry (no live re-hash at claim time). A synced peer can therefore reuse already-curated frontmatter without re-running the LLM. The curation cursor is `(timestamp, kind, slug)` (`createdAt` for notes, `importedAt` for sources); the per-machine `contentSeq` and `metadataSeq` counters (and the `currentEntrySeq()` derived from them) remain freshness metadata, not the cross-machine ordering key.

Curate/git-sync implementation lives in the KB domain: `kb/curate/entity-graph-merge-driver.ts` merges `.entity-graph.json` by feeding a union of ours and theirs into `consolidateEntityGraph` from an empty base (the git merge base is ignored — it carries no deletion semantics here); `kb/curate/frontmatter-merge-driver.ts` unions frontmatter set fields (`tags`, `principles`, `related`) and resolves scalar fields via body-match/lexicographic tiebreaks, delegating body prose to `git merge-file`; `kb/curate/conflict-quarantine.ts` records entries skipped after unrecoverable body-prose conflicts. `ensureKbMergeDrivers()` in `kb/curate/git-sync.ts` appends the managed `.gitattributes` entries, registers the merge drivers, and pins `rebase.backend=merge`; derivatives and frontmatter resolve without the LLM, while irreducible body-prose conflicts fall back to the LLM resolver as a last resort before git sync aborts the rebase, preserves local commits under `refs/coral-recovery/<branch>/...`, resets to `origin/<branch>`, and quarantines the affected entries. The AC7 rollout migration in `kb/migrations/index.ts` is TEMPORARY (REMOVE AFTER ~2026-07); it backfills missing `inputFingerprint`; errors are caught and logged inside `runPendingKbMigrations`, so a migration failure never blocks scheduler startup.

The KB mutation lock commits Corpus state and text artifacts only. It does not install retrieval projections. Orama is the base CorpusConsumer; optional installed retrieval engines register their own CorpusConsumers and rebuild derived state from the Corpus snapshot they apply.

Orama has a deliberate read/write split. `OramaSearchPort` is a pure consumer of `OramaSnapshotStore`: `ensureLoaded`, `search`, `tokenize`, and `tokenizeBatch` never synchronously rebuild, persist, or call `forceCorpusApply`. They classify cached or persisted artifact metadata with `classifyProjectionMismatch`, activate a served-index record, and query with the tokenizer that matches the served artifact. Intl-tier artifacts are always served through the Intl tokenizer. Kiwi-tier artifacts are served only while a live Kiwi analyzer lease can bind the tokenizer; if the lease is unavailable, the read path returns the degraded/uninitialized FTS path and asks for reconcile instead of querying a Kiwi index through Intl. During an Intl→Kiwi upgrade, a valid Intl artifact is served immediately under the Intl tokenizer, `fts_index_stale_tier` is surfaced, and `requestProjectionReconcile('stale-tier')` is fired without awaiting it.

Orama reconcile ownership lives in the KB daemon's expansion lifecycle, using the shared `projection-consumers/` driver. `createOramaProjectionReconcileRequester` is wired into one `OramaBaseProjection`; that projection's single read port is exposed as both the registered CorpusConsumer and the bound FTS capability. The requester single-flights reconcile requests and delegates writes to `ConsumerDriver.forceCorpusApply(currentSnapshot, { reason: 'projection-artifact-lag', consumers: [ORAMA_BASE_CONSUMER_ID] })`. The read model only requests reconcile. The write path remains the CorpusConsumer apply path, which persists Orama artifacts, stores the returned metadata in the cache, and uses a freshness-safe identity-aware lost-update guard: strictly fresher persisted artifacts win, but equal-snapshot identity-changing tier reconciles are allowed to converge.

Kiwi degradation also reconciles through the KB daemon's expansion lifecycle. The bundled Orama loader registers a mandatory `KiwiAnalyzerManager.observeDegraded` observer scoped to the expansion `host.scope`; scope disposal removes it from the process-singleton manager. `markDegraded` records degraded state and schedules the observer as a fire-and-forget microtask, then throws the terminal Kiwi load error; the observer runs asynchronously after the throw propagates, and observer failures are caught so the terminal-error path remains intact. The observer calls the same `createOramaProjectionReconcileRequester` requester with the `kiwi-degraded` path, which invalidates the text snapshot with `kiwi-degraded` and force-applies the Orama consumer, allowing a terminally degraded Kiwi index to converge back to the Intl tier without a corpus edit or restart. `onApplyFailure` is supplemental coverage, not the primary degradation signal.

Orama projection sidecars carry identity metadata in addition to snapshot metadata: `identitySchemaVersion`, schema version/digest, Node/ICU versions, tokenizer identity, and declared analyzers. Retired sidecars without those fields still parse, but classify as incompatible and are not serve-stale eligible. `identitySchemaVersion` participates in `ORAMA_PROJECTION_IDENTITY_HASH`, so old sidecars are detected as projection-artifact lag on boot; an Orama-only boot repair that times out with `FreshnessTimeout` is non-fatal to KB readiness and leaves FTS stale or uninitialized while the background reconcile continues.

## Work Classes

Jobs are not an async wrapper for every command. They are durable work ledgers for long-running, observable, or recovery-relevant attempts.

| Class                    | Examples                                | Owner                                                       |
| ------------------------ | --------------------------------------- | ----------------------------------------------------------- |
| Direct read              | KB read/list, `jobs`, discuss watch     | Read model or KB query helpers; no durable artifact rebuild |
| Served read              | KB search                               | KB daemon search runtime; no durable job ledger             |
| Direct mutation          | KB note write/delete; memo write/delete | Corpus lock for KB notes; project data dir for memos        |
| Provider/session job     | Codex/Claude launches, workflow atoms   | Jobs + sessions + provider adapters                         |
| Internal coordinator job | KB source import, KB reindex            | Coordinator service over jobs + KB                          |
| Projection freshness     | Active retrieval-consumer catch-up      | ConsumerDriver cursor wait                                  |

Direct KB reads are coordinator-free, not context-free. CLI/bootstrap adapters resolve plugin root, build flavor, project root, Corpus root, and KB runtime root before invoking KB query helpers or `read-model/CoralStore`; lower KB path helpers do not choose `cwd`, `HOME`, or `CORAL_KB_PATH` on their own. KB search is a served read: it uses the KB daemon's search runtime instead of the direct read model.

Projection freshness is not authority. A Corpus commit remains durable even if a retrieval consumer fails to catch up; callers that requested readiness observe that failure through the hosting command or job.

## Coordinator

The routing-status store owns the SQL renderer and the canonical fingerprint and generation derivations. The
coordinator supplies `handoffRoutingStatusStoreSchema()` with the durable SQL bounds, record contracts, and
completed-pair stability contract. `handoffRoutingStatusFingerprint(schema)` hashes that canonical input into the
full 32-byte identity, which the metadata row persists beside the ten-digit generation projection produced by
`handoffRoutingStatusGeneration(schema)`. The projection supplies SQLite `user_version`, event envelopes, and the
`handoff-routing.<generation>.db` address; it is not a substitute for comparing the persisted fingerprint.
Operational capacity remains outside the durable identity because it changes allocation rather than decodability.
Publication compares generation, the complete non-internal schema, and the full fingerprint before initialization
or mutation and repeats admission under `BEGIN IMMEDIATE`.

Record contracts are extracted from the hand-written Zod schemas by `zodPersistedContract`
(`src/infra/persisted-contract.ts`). The descriptor-first alternative is unnecessary: extraction from Zod preserves
the schemas as the readable owner while making their complete persisted grammar an identity input. The claim that
complete identity must cost hand-written Zod readability is therefore false; the same production direction is
used by `src/store/current-format.ts` and `src/providers/registry.ts`.

`HandoffRoutingStoreClassification` and `readHandoffRoutingStoreSnapshotWithObservation`
(`src/store/handoff-routing-status-store.ts`) define the closed eleven-arm observation shared by reads and
publication policy: `absent`, `vacant`, `uninitialized`, `detached-wal`, `generation-missing`,
`foreign-generation`, `format-mismatch`, `schema-divergent`, `current`, `unreadable`, and `undeterminable`.
`readHandoffRoutingStatus` (`src/coordinator/handoff-routing/status.ts`) may project that observation, but read
authority grants neither initialization nor mutation authority. The separate total publication policy admits
mutation only through `publishGenerationCoordinatedHandoffRoutingTransitions`
(`src/coordinator/handoff-routing/status.ts`) after generation-writer admission. Artifact refusals retain their
classification; `unreadable` and `foreign-generation` are not publication-failure causes. Files at superseded
addresses remain isolated and outside the current address's quarantine listing.

The coordinator layer owns process lifecycle, the three-era boot sequence (Kernel → Recovery → Runtime Health Components), projection-consumer wiring, provider-host coordination, job-backed KB source import/reindex proxying, and the corpus notify seam. Its provider-host administration service is an aggregator and router, not the sole host authority: the coordinator-local manager and every live provider proxy report their own live/tombstoned inventory and execute their own admission and eviction. Federation is all-or-error, and exact owner revalidation prevents a selection race from retargeting a destructive operation. It also owns the evidence-gathering half of carrier observation that the classifier deliberately does not: `composition/carrier-observation.ts` gathers local evidence (admission state, the OS process table, and the durable-CLI identity row), classifies health and idle synchronously from that evidence, and builds wait's asynchronous observation port. For inherited wait-time operations only, `live/carrier-observer.ts` adds a bounded `operation.status.v1` pass. That method is a nonce- and proxy/build-bound, read-only ledger-liveness handshake; `operation.inspect.v1` remains the richer durable-saga ambiguity surface used by reconciliation. An unanswered status question is `unknown`, not absence, and every consumer treats it as conservatively active. Only a positive `absent` may render a wait interruption, and even that derived finding authorizes no recovery, cleanup, reconciliation, terminal materialization, or other mutation. `tests/invariants/no-carrier-observation-in-action-paths.test.ts` enforces that boundary at every import depth. Liveness itself is three-valued and says so in its type: `infra/node-process.ts`'s `observeProcessLiveness` answers `alive | absent | unknown`, where `EPERM` is alive, only `ESRCH` is absent, and any other probe failure is a question that could not be asked. The type makes the compiler enumerate every caller, and only `absent` may finalize anything. The same module composes that probe into the question a durable record asks: `createRecordedProcessObserver` (`infra/node-process.ts`) binds an injected incarnation reader and an injected liveness reader into one `RecordedProcessObserver` over a recorded `{ pid, incarnation }`, consulting identity before liveness and falling through to liveness where the record carries no token or none could be read. Its answer is the same three-valued `ProcessLiveness`, so an `absent` reached by either route is what may finalize and `unknown` still never is. Because the readers are injected rather than reached for, the observer can be handed to code entitled only to conclude: provider-proxy set lifecycle receives one beside the discovered capsule list (`coordinator/composition/execution-services.ts`) and decides handoff-capsule retirement from it while its own deps carry no capability to spawn, kill, or signal. The store-aware containment absence proof lives in `coordinator/services/provider-proxy-set/containment-proof.ts`: it composes the recorded enforcer observer, attributes unreadable provider-operation rows, collects every recorded provider root for the exact set into an opaque identity-bound proof, and leaves recorded containment to the lifecycle and inheritance owners after both enforcers are absent. `provider-proxy/containment-proof-contract.ts` is the separate wire vocabulary; `provider-proxy-set/inheritance.ts` remains capsule inheritance policy. Recorded process containment is narrower and independent: `infra/process-containment.ts` revalidates the recorded group leader and its process incarnation before signalling, then requires stable absence before reporting success — on darwin that revalidation is not yet authoritative, which [`docs/todo/darwin-signal-authority.md`](./todo/darwin-signal-authority.md) records. Its success means no verified recorded target remains; it cannot prove original group members disappeared after leader-PID reuse. Proxy callers can include recorded provider roots; coordinator-local host teardown supplies an empty root set and reaps only its recorded group. The coordinator layer is the only place allowed to compose multiple parent-daemon domains together and the only place that speaks to both transport and domain owner modules/contracts at once. `coordinator/handoff-routing/policy.ts` owns the closed `continue-current | handoff` vocabulary, required basis obligations, and pure live-incumbent policy; `coordinator/handoff-routing/runner.ts` owns observation and execution shared by CLI pre-flight delegation, `wait jobs` cursor resume, and backend cold-start handoff (`src/coordinator/bootstrap.ts` calls it when startup finds a newer active-store selection). Its `consumeHandoffRunResult` boundary requires recording incidents to be handled before observed work can be obtained. `coordinator/handoff-routing/status.ts` owns the bounded event and tombstone vocabulary, admission and retention rules, total persisted policy, transactional publisher, acknowledgement mutation, and read projection. `coordinator/handoff-routing/repair-operation.ts` owns the routing-status repair grammar and exhaustive command classification shared by the runner and CLI. Exact capacity evictions stay warning/75 until the registered resolve command folds them into aggregate history; exact operator-resolution tombstones are terminal information and contribute 0. `store/handoff-routing-status-store.ts` owns the SQLite schema, transaction boundary, append/query operations, and raw snapshot; completed-pair stability is derived from the authoritative journal JSON during the bounded retention scan rather than stored as another column. Both real and simulation runtimes supply the database engine through `StoragePort`. Production publication crosses generation admission before SQLite, retrying both forms of contention against one monotonic deadline and returning `generation-maintenance` if maintenance wins admission. Writer leases store pid plus incarnation in their contents; an unknown process observation never authorizes removal and instead reaches the independently heartbeating lease's ten-minute stale successor. Publication is a SQLite transaction at `handoff-routing.<generation>.db` rather than an advisory lock over JSON, and the reason is that publication and exclusion are then the same act — an advisory fence is not consulted by `rename(2)`, so a writer that lost one still publishes, while nothing becomes visible except through a `COMMIT` that cannot succeed without the lock it verifies. Two settings carry that: `busy_timeout=0` keeps the wait in JS rather than in C where it would block the event loop, and `BEGIN IMMEDIATE` takes the write lock before the read-validate prefix a deferred transaction would leave unprotected. A failure before the `COMMIT` attempt is decisively `not-published`; a failure after that attempt starts is `commit-outcome-unknown`, regardless of its SQLite cause. Admission reserves a maximum legal closing record for every unresolved opening, because reserving space and admitting a record are different things and a terminal that cannot be admitted is an obligation that can never close. The reader answers `absent | vacant | uninitialized | detached-wal | generation-missing | foreign-generation | format-mismatch | schema-divergent | current | unreadable | undeterminable`; expected discard guard failures are result variants rather than throws, and the read projection validates the reserve invariant so it cannot certify an obligation whose exit could not commit.

The daemon bind handoff also stays inside that Runtime world: both its identity anchor and later target observations use `ProcessPort.readProcessIncarnation`, identity agreement is followed by a distinct `ProcessPort.observeLiveness` verdict, and the boolean returned by `ProcessPort.kill` means kernel acceptance or rejection of the request, not that the target received or acted on it. Only an accepted request starts a pending settlement and attempts ledger publication. The writer must first publish a V1-shaped shadow with `accepted: true`; only that success permits the matching V2 detail write. The reader retains every matching record with address provenance. A shared publication id correlates only this build's detail and paired shadow; independent records fall back to recency, a tie keeps the conservative record, and every active independent candidate contributes to the cooldown disposition. The marked shadow is accepted evidence and an unmarked genuine shipped V1 is an indeterminate foreign attempt. A rejected request branches immediately into target-gone, observed-live, and unverified dispositions; the latter two refuse with the external owner action or fresh observation that ends the hold. A bound socket completes only after the accepted signal's anchored target is observed absent. One boundary surrounds all pending-signal handling, so an unchosen bind, poll, grace-transition, or post-grace discovery exception re-observes the target and either propagates after absence or becomes a refusal retaining that exception as its cause. An abort logs the accepted signal, target pid, and observed status, then propagates unchanged. What makes that safe is not a record: the path returns no coordinator and claims no incumbent outcome, and the next startup re-derives everything about the target from its own discovery and observation. Ledger persistence remains best-effort, so total write failure may leave no cooldown entry and a later contender re-observes from scratch; it cannot publish V2 without first publishing its shipped shadow. `settleBoundSocketAgainstPendingSignal` owns the bind event and `advanceExpiredPendingSignal` owns grace expiry, keeping those state-machine decisions separate. The wall-clock timing of the handoff deadline and graces is unchanged and tracked in [`handoff-wall-clock-graces.md`](./todo/handoff-wall-clock-graces.md).

`runtime/errors.ts` is the canonical documented setup-error registry for authored public text, retryability, and CLI exit. The generation-mutation store owner classifies a live writer as `legacy_source_not_quiescent` and an unobservable writer as `legacy_source_writer_observation_unknown`; direct, IPC, HTTP, and CLI boundaries carry that code unchanged. Bootstrap diagnostics derive `retryable` from the registry; backend status accepts both booleans and carries them in `recent_failure` while continuing to exclude structured context from public rendering. `cli/errors.ts` consults the registry for documented codes, and expansion retains only its non-error exit-0 deviation before delegating errors to the same mapper.

An ordinary routing writer probes the maintenance lease through heartbeat-aware lock acquisition while holding
generation admission. A live holder remains `generation-maintenance`; an abandoned holder becomes reclaimable
after the ten-minute heartbeat stale bound, and the CLI names that retry path instead of promising an active
maintenance operation will finish.

The persisted routing classification has one rule: a disposition is a hold only when a Coral operation can change its record; every other disposition is retained and rendered history with exit contribution 0. A `Record` keyed by every persisted disposition kind makes that decision mandatory for new kinds. Exact capacity evictions remain holds until resolve folds them into aggregate history; every committed terminal, including a terminal recorded without a selection, is history. `coordinator/handoff-routing/status-operator.ts` owns offline discard and quarantine-clear authorization and orchestration, while `store/handoff-routing-status-store.ts` retains raw filesystem mutation and the CLI only supplies the socket guard. Expected pre-effect storage failures, including root creation, return typed outcomes; post-effect failures distinguish directory-barriered effects from namespace changes that were only observed before a failed barrier.

The main `handoff-routing.<generation>.db` file is hard-capped at 1 MiB by `max_page_count`. `journal_size_limit=1_048_576` returns its WAL to at most 1 MiB when a checkpoint can reset it, and `wal_autocheckpoint` is `floor(1_048_576 / page_size)` pages (256 at a 4-KiB page size) so checkpoint attempts follow the same budget. SQLite cannot hard-cap the WAL while an open reader prevents reset: it may exceed 1 MiB by the writes accumulated during that reader's lifetime and returns to the configured limit only when a checkpoint can reset it. The `-shm` file is a SQLite-managed sidecar, not part of the main-file hard cap.

§7's subdivision trigger is satisfied by the five-file `coordinator/handoff-routing/` component: `policy.ts` owns the closed routing decision and obligations, `runner.ts` owns observation and execution, `status.ts` owns the durable routing-status vocabulary and projection, `status-operator.ts` owns offline maintenance authorization and orchestration, and `repair-operation.ts` owns routing-status repair grammar and command classification. `coordinator/handoff.ts` remains outside because it is the daemon-side bind/escalation state machine, a different meaning of handoff.

Authorization of the explicit provider-proxy containment path is coordinator-service policy. `provider-proxy/set-lifecycle-state-vocabulary.ts` is the canonical provider-proxy contract leaf for lifecycle-state vocabulary; the live state machine remains in `coordinator/services/provider-proxy-set/index.ts`. `coordinator/services/recovery/unreadable-provider-operation-discard.ts` is the transactional destructive owner for unreadable raw provider-operation rows: it requires the exact unowned persisted quarantine subject before the store removes the raw row, its due pointers, and quarantine evidence together. `coordinator/services/provider-proxy-authority-fault.ts` owns the control-call policy types plus the separate non-consuming observation and terminal-fault channels; `provider-proxy-operation-activation.ts` requires every mutation to declare `indeterminate: 'retry-safe' | 'requires-containment'` and classifies each failed control call. `provider-proxy/heartbeat-observation.ts` owns the strict heartbeat result/refusal decoder, the branded `HeartbeatObservation`, and the pure evidence-window reducer. The coordinator receives the observation intact beside role, method, and scheduler lateness, so it never reconstructs peer evidence from an error origin or reason string. Each set, role, and method has one exclusive `clear | silence | answered-unusable` window. No-response advances silence; an unusable reply replaces silence with a fresh answered-unusable window; accepted and challenge-mismatch replies clear either state. Locally unsent and channel-fault observations cannot produce window state. Once a continuous answer-free, set-derived adoption-window span elapses without material scheduler lateness, `heartbeat_hold_exhausted` authorizes the coordinator's bounded `stop-and-reap` containment path. Exhausting answered-unusable evidence stops heartbeating, closes control, and waits for independent containment absence; a recognised `method_not_found` clears the window and takes that same independent-absence path immediately. It sends no destructive control RPC, but after both enforcers are proven absent the read-only containment prover supplies the exact targets and the lifecycle reaps the orphaned proxy group through the sanctioned helper. Attempts are rendered evidence, never an exit predicate. The bound is carried by each established set as timing — resolved configuration for fresh acquisition and the capsule timeout for redemption — rather than as proof that another role accepted ownership. The endpoint's complete `teardown-latched` refusal shape is the only heartbeat terminal fault the endpoint itself can name; a locally unsent request remains a decisive `local-failure` terminal reason about this process, not evidence about the peer. `provider-proxy-set/decisions.ts` owns the preserve/drain/containment/stop-and-reap vocabulary and pure log rendering, while `provider-proxy-set/index.ts` records each decision before action and carries it through the live transition state machine. That lifecycle also owns the opaque process-absence and durable-claim-discharge values; its slot-removal sink accepts only their combined discharge, so a label or zero count cannot authorize removal. A no-live-claims constructor rechecks the mirror at discharge, while claim-bearing sets discharge only after every disappearance consumer acceptance. `coordinator/live/provider-proxy/set-authority.ts` separately owns recovery-credential installation as `idle | installing | installed`: concurrent callers share only the current attempt, only an installed receipt is retained, and retryable/refused/cancelled outcomes return to idle. A v1 ACK proves storage of that grant and no ownership transfer. `coordinator/live/provider-proxy/control-redemption.ts` owns one guardian→reaper→proxy attempt under a shared absolute deadline and publishes its replacement clients, heartbeats, identities, faults, and operation membership only as one privately branded bundle. `coordinator/services/provider-proxy-recovery-policy.ts` enumerates the recovery producers and consumer seams those channels serve and classifies every producer outcome before it reaches a sink. One seam is a deliberate exception: on `foreign-capsule-retirement` every way the `capsule-retirement` producer can disappoint reaches the owner-local incident channel and none reaches the global fatal sink, because that owner holds a capsule path and nothing else. `provider-proxy-set/index.ts` owns the hold that follows — a bounded local retry to `FOREIGN_CAPSULE_RETIREMENT_ATTEMPT_LIMIT` attempts whose exhaustion drops the owner, leaves the capsule's conservative representation standing for the rest of the boot, and hands the path back to a later boot's discovery. A claim-bearing reap requires a containment-qualified terminal fault, while faultless retirement can reap only with literal `liveClaims: 0`. The provider-proxy domain owns enforcement and reap mechanics for that authorized decision; the separate deadline machines in guardian and reaper retain autonomous enforcement at their adoption deadlines.

Channel loss is now structurally excluded from the terminal-fault union. Close and
`invalid-unattributable-frame` facts enter the incident channel and move the established slot to a distinct
`reattaching` state. Its route is removed while claims stay attached; authenticated three-role redemption and
independent absence run concurrently under one absolute monotonic adoption-window deadline. A branded success
rebuilds and promotes the complete operation authority before establishment notification, while refusal or
expiry enters the awaiting-absence path without sending `stopAndReap`; once both enforcers are proven absent, the read-only prover supplies the exact targets and the lifecycle reaps the orphaned proxy group. Ordinary `backend shutdown` is handoff, not a forced exit. The explicit exit is
`coral-cli backend provider-proxy-set contain <pps1-token>`.

## Runtime Components

`coordinator/runtime-components/` is a small registry layer for daemon-visible health/lifecycle components that must not extend the kernel path. It does not host the KB runtime; the parent registers the mandatory recovery component and a best-effort KB daemon health mirror:

- `contract.ts` — `RuntimeComponent` (init / dispose / status), `RuntimeComponentStatus` (4 serving phases: `initializing → online | degraded | offline`), `DegradedReason` (`{ kind: 'curate-publish'; consecutiveFailures; lastError } | { kind: 'recovery-quarantine'; count; lastError }`), and branded `RuntimeComponentId`.
- `registry.ts` — `createRuntimeComponentRegistry()` exposing `register / initAll / disposeAll / list / status`. It is a status/lifecycle projection only; KB requests go through the KB daemon supervisor, not through this registry.
- `recovery-component.ts` — projects `recovery_quarantine` count and latest error into daemon health. Its registration is mandatory and aborts startup on failure; unlike KB registration, it is not wrapped as best effort.
- `runtime-components/kb-health-component.ts` — `createKbDaemonHealthComponent(kbDaemonSupervisor)` mirrors daemon health into `/health.components[]`; the KB daemon process owns the boot pipeline (Corpus replay + CorpusConsumer registration + Orama freshness wait), runtime construction, curate work, and expansion lifecycle. When `CORAL_KB_ENABLE=0`, the parent wires a disabled daemon supervisor, so the health component reports terminal `offline` with `KB_DISABLED_REASON` and does not spawn the KB daemon. The CLI matches that reason on `/health` to decide whether to restart the daemon and re-enable KB.

KB request failures (`kb_initializing`, `kb_offline`, `kb_disabled`) come from the KB daemon request/supervisor path and lift to HTTP 503 through the standard error envelope with the `remediation` field.

Five invariants enforce the contract: `runtime-component-contract-singleton`, `kb-daemon-error-codes`, `lifecycle-phase-monotonic`, `abort-signal-threading`, `no-kb-status-accessors`.

Workflow plans persist only semantic slots: slot id, dependencies, provider, instruction, and optional agent. Step indexes, display labels, and atom keys are derived from that semantic plan. Child job ids are separate runtime identities: initial execution mints them through the runtime `ids` port. Recovery reconstructs the current mapping by reusing the durable `job_id` for a `workflowSlotId` with a current child row, mints an id for a slot without a row, and mints a new id for the next replacement generation when a pending continuation lease requires one.

## Infrastructure

Infrastructure helpers sit below every domain: schemas, small utilities, SSE parsing, cross-process locking, file tailing, and child-env construction. Infrastructure resolves canonical paths, build flavor, backend connection info, and expansion paths without becoming a generic domain dumping ground. A relocated Unix-socket namespace for current builds is derived from the Coral state root, so caller uid and `TMPDIR` cannot split one installation into multiple current-build locks; the bind boundary separately verifies that the calling uid can hold the resulting directory. `infra/handoff-target.ts` owns the sealed `ValidatedHandoffTarget` capability and the foreign-target validator that hashes and re-verifies a candidate build before it is trusted; `infra/monotonic-clock.ts` owns branded, non-serializable elapsed-time arithmetic; `infra/process-containment.ts` owns the owner-neutral SIGTERM→SIGKILL reap of a recorded process/group identity verified by pid plus process incarnation, shared by coordinator-local host and provider-proxy containment owners.

## Stable Seams

These are the load-bearing boundaries that must not leak:

- The Runtime interface is the only channel for I/O inside the backend.
- The boot eras are ordered — Era I blocks until kernel-ready, Era II blocks until running, Era III runs fire-and-forget. Existing-incumbent and existing-starting probes remain fail-fast under `KERNEL_BIND_DEADLINE_MS = 5s` and `KERNEL_READY_DEADLINE_MS = 15s`. A newly spawned current attempt instead remains owned by its initiating reader until authenticated readiness or that exact child becomes terminal; terminality triggers one final readiness probe and one final exact-attempt sentinel read. Backend-startup delegation keeps the original child responsible until the selected backend is authentically ready or terminal, transitively through further delegation. The 100 ms interval is only the delegated-readiness poll cadence, never evidence of readiness.
- `AbortSignal` is the cancellation primitive throughout startup. Aborting the startup signal with no string reason preserves the `AbortError` discriminator; calling `abort('shutdown')` strips that discriminator and breaks downstream `name === 'AbortError'` checks. Enforced by the `abort-signal-threading` invariant.
- Each domain owner module/contract set is the coordinator-facing surface for its domain; deleted `api.ts` barrels and compatibility shims are not recreated for convenience.
- `store/` is the SQL/Journal substrate; `read-model/CoralStore` composes product reads over domain-owned query modules.
- Routing-status quarantine is bounded store evidence: sidecars move before the main database, an incomplete UUID-addressed set refuses a new discard until the operator clears its exact ID, and the seventeenth complete or incomplete set is refused until an operator lists and clears an exact ID.
- Domain registries own event schemas, append validators, and reducers; `store/` only runs the composed validators transactionally.
- Expansion lifecycle is KB-daemon-owned: transport reaches it through the parent `KbDaemonSupervisor.expansionRpc` proxy, and the KB daemon resolves active backends through `kbRuntime.<name>.read()` on each `RuntimeBinding<Backed<T>>` cell.
- KB retrieval projections are rebuildable consumers of the Corpus authority; source import and explicit reindex readiness wait on `ConsumerDriver.waitFreshUntil('corpus', ...)`.
- KB source import/reindex failure facts are recorded by coordinator-owned KB job recording glue as job progress cause events; the KB domain remains Corpus authority only.
- Compatibility shims are not stable seams on the rewrite branch; retired owner paths stay deleted once responsibility moves.
- Hooks never import from `src/`; shared hook logic lives alongside the hooks themselves.
- Runtime ingestion emits canonical domain events; incompatible historical bodies are rejected and the store-format reset boundary handles adoption.
