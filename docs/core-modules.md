# Core Modules

A high-level map of what each area of the codebase is for. This document describes stable seams — composition roots, domain owner modules, and public contracts. Implementation files evolve inside each area without requiring doc updates.

Coral's product identity is a coding-assistant plugin for Claude Code, Codex, and GitHub Copilot CLI. Its internal architecture is a local coding-agent coordination layer: the coordinator owns live decisions and recovery, domains own truth vocabulary, transport carries requests, and the CLI is the local operator surface.

## Composition Roots

| ------------------------ | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| CLI entrypoint           | `clients/bridge/coral-cli`                  | Commander-based CLI client that uses IPC for mutating/live work, reads `read-model/CoralStore` directly for no-coordinator paths, and retains HTTP for the remote gateway plus operational carveouts. |
| Claude broker helper     | `clients/bridge/coral-claude-appserver.cjs` | Provider helper that accepts broker RPC and runs Claude through the default `claude -p` stream-json transport or the opt-in PTY TUI transport.                                                        |

## CLI and Client

The CLI parses commands, follows detached launches via the `jobs.wait` IPC subscription, and formats output for humans and machines. The client layer owns backend startup, IPC dispatch/subscriptions, direct `read-model/CoralStore` read helpers for no-coordinator paths, and the HTTP gateway/admin helpers exposed through the public barrel. Startup glue is method-aware rather than policy-carrying: `transport/ipc/ensure.ts` takes the invocation's method and derives from `ipcRouteLifecycleAdmission` (`transport/rpc/operational-catalog.ts`) whether a draining incumbent may serve that route, so one catalog answers for both client and server. `transport/lifecycle-refusal.ts` is the single home of the success-shaped `backend_shutting_down` refusal body and of the `code`-only predicate that recognizes it, including from a newer server that adds fields; the unary `requestIpcMethod` (`transport/ipc/client.ts`) rejects with `IpcLifecycleRefusal`, which carries the method, the socket path, and an address disposition of `unobserved` or `held-past-release-budget`, while the subscribe path keeps its transient-503 mapping. A request the drain bound itself cut short is neither of those: `IpcDrainRequestUnanswered` carries code `coordinator_drain_unanswered` to exit `75` and says whether the method ran is unknown, so no successor is obtained and nothing is re-issued. Each catalog route also declares `onRefusal`, and `issueWithSuccessorAfterLifecycleRefusal` reads it before asking for a successor at all: `spawn-successor` obtains a successor and re-issues the request once, `report-refusal` raises the refusal immediately, and an incumbent that never releases the address restates that same refusal as held past the release budget rather than trading it for `backend_unreachable`. `backend provider-host list|inspect` are served operator reads requiring `system:debug`; `backend provider-host evict` is a mutation requiring `system:shutdown`. Inspect accepts either one opaque exact host reference or a `--work-dir` resolver, never both. Eviction requires the exact reference and refuses a work-directory selector before inventory or mutation because a work directory cannot identify one retry subject. `backend recovery-quarantine discard-provider-operation` rejects tagged provider-operation keys at CLI ingress and emits readable-deletion consent only from `--allow-readable`. `cli/format/backend.ts` renders its typed result, including the safe `recovery-in-progress`/`backend_recovering` launch-fence refusal and every `adoption-refused` record. The former reports that no raw row was inspected and no state changed, then tells the operator to wait for startup recovery and run the command again; the latter reports that reconciliation and settlement were not observed. Command registration maps both outcomes to exit `75`. `cli/handoff-notice.ts` owns the one-time stderr notice printed after a CLI invocation is delegated to a newer build; `cli/format/handoff-publication.ts` owns the human diagnostic and cause-specific successor formatting shared by the notice and routing-resolution surfaces. Publication incidents carry the exact invocation ID, and terminal incidents carry the attempted terminal disposition so formatting distinguishes failed work from finished work without treating the recording phase as an execution result. The notice writes directly to `process.stderr` rather than through `emit.ts` so it never corrupts a machine-readable result on stdout. Coordinator startup logs the publication incident as structured domain data and does not import CLI formatting.

## Backend

The coordinator is a composition root, not a domain. The root is split into a coordinator layer and a transport layer: the coordinator owns lifecycle, startup recovery, projection freshness, corpus notify publication, job-backed KB source import/reindex, and cross-domain assembly; transport owns IPC plus HTTP/SSE parsing, validation, and wire formatting. `coordinator/live/admission.ts` owns exact `LaunchPermit` acquisition, holder transfer, release, and evidence-gated reclamation. For provider-operation discard, `coordinator/composition/index.ts` checks the launch fence before constructing the discard service or reading the recovery database; an active fence returns `recovery-in-progress` without row inspection, a quarantine claim, mutation, or permit release. After an admitted discard, composition releases startup ownership, attempts adoption of a sole surviving readable record, and projects bounded permit, release, reclamation, and adoption-refusal diagnostics into backend health. New domain logic does not land in either layer; it stays in its owning domain and is reached through explicit owner modules/contracts.

## Runtime

The backend uses a **single Runtime world** pattern: one interface with a fixed set of I/O subports (time, storage, paths, process, ids, env), swapped once at composition. Every I/O-touching module routes through it. The real runtime is used in production; a deterministic counterpart powers the simulation lane.

## Journal

The Journal is the event-sourced truth spine for all domain state. It provides append, rebuild, strict envelope decoding, domain append-validator, and projection-reducer dispatch primitives backed by SQLite in WAL mode. `store/` exports the SQL/Journal substrate; product read APIs live in `read-model/CoralStore` and domain-owned read query modules. Projected jobs deliberately retain two coordinates: `projection_jobs.project_root` is project identity, while nullable `projection_jobs.work_dir` is the canonical execution directory (`NULL` only for KB jobs). Ambient job selectors and unfiltered event streams match `work_dir` exactly; explicit wait, abort, and detail allow one-directional containment from the caller directory to the job directory. Both relations govern non-KB jobs only — a KB job matches from every caller directory. `coral-cli jobs` bypasses the ambient filter and retains project-root grouping. The application-wide store format covers persisted codecs and executable DDL; historical formats are read through retained roots and frozen readers, without migration into the active database. `coordinateActiveStoreSelection` in `src/store/active-store-selection-coordination.ts` publishes selection only after a committed open. `settleStoreEpoch` in `src/store/epoch/index.ts` requires a coordinator retirement disposition for a production mint; an unreadable predecessor alone does not grant one.

## Store Epochs

`store/epoch/` owns the generated-store layout and settlement loop. Generated stores start at `store/epoch-<N>/store.db` for positive `N`, with WAL, SHM, format sidecar, and an additive `epoch.json` published with the directory. The flat `store/store.db` belongs to the previous generation; job lookups observe only existence. The flat store and its sidecars remain as one-time residue because pre-epoch writers cannot be excluded. A publisher builds under a private `.mint-<uuid>` name. Before publishing a successor, it moves earlier epochs with proven contained directories and locks under `.coral-protected-store-epochs.v1`, outside the shipped sweep's search space. Protection first waits up to `SUPERSEDED_OPENER_DRAIN_MS` (2 seconds) for a live opener to release the epoch being moved; one still held past that wait — or the current writer generation's own open epoch — stays at its canonical address instead of blocking the mint, recorded in `store-epoch-protection-pending.v1` with audit event `store_epoch_protection_deferred` (`store_epoch_protection_unrecorded` if even that record could not be written durably). The lineage marker and protected address map distinguish epochs that share `N`; exact opens and historical readers resolve the mapped address. `settleSupersededEpochClosures` in `src/coordinator/services/recovery/epoch-closure.ts` retries owner-certified custody closure while serving; `recordEpochClosure` in `src/store/epoch/closure.ts` persists execution discharge outside the epoch. `JobLocationIndex` in `src/jobs/location-index.ts` stores locations, terminal details, result paths, and a revision-checked completeness certificate outside the active store. The post-ready sweep deletes an epoch only with its exact-key closure and `JobLocationIndex.resultsReleased` proof, subject to retention; each pass first retries every recorded pending protection whose epoch is now superseded (`retryPendingProtections`), clearing the record once the epoch is gone or protection succeeds, and `listStoreEpochs` shows a still-pending reason as `protectionPending` on that epoch's list entry. Undecidable custody remains visible as `unrecoverable-retained` and stays on disk. Abandoned mint residue still requires absence proof; unattributed `.reaping-` residue is retained. Protected deletion-residue discovery checks the protected root, lineage, address directory, and tombstone with no-follow directory observations before admitting removal. A symlink or unreadable ancestor is reported as `unobservable-metadata`; ordinary interrupted residue remains reclaimable.

New stores and new epochs enable `auto_vacuum=INCREMENTAL` before schema creation. Existing NONE-mode stores remain in NONE mode: deleted rows create free pages that subsequent writes reuse, bounding growth without returning those pages to the filesystem. They shrink at the next epoch mint or store reset. No runtime full VACUUM, conversion helper or startup conversion runs. Additive maintenance indexes are installed independently during writable store opening; neither indexes nor persisted cursor keys change the store-format fingerprint. `store/retention-vacuum.ts` yields between 32-page incremental chunks on incremental stores.

Storage retention rechecks `causeRef` and `causation_seq` inside each progress deletion transaction. Its additive indexes cover shipped direct, reason and terminal cause paths; unknown causal shapes conservatively hold progress. A progress sweep captures a terminal-sequence ceiling and scans only `afterSeq < seq <= ceiling`, at most 1,000 terminals per run. The persisted ceiling and the position within a job resume after shutdown, park or crash; progress checkpoints commit with deletion. Finishing the captured range resets the cursor even while newer terminals arrive, so expired prefixes get another turn. Older cursor meta without a ceiling is accepted and starts a fresh capture; unknown additive keys are retained. Each batch deletes at most 64 rows, caps SQLite lock waits at 25 ms; the connection timeout is restored before yielding. Normal SQLite automatic checkpoints remain enabled to prevent retention from accumulating a large WAL. Retention does not run an unbounded passive checkpoint. Native commits and filesystem I/O remain synchronous and cannot be interrupted by a timer. Export and holder directory continuations are additive keys in `meta`. Export traversal sorts names and resumes strictly after the last processed name without charging the retained prefix against the operation budget. Scratch scanning and settlement check the budget and yield between subjects; their meta cursor preserves progress. Active hydration quarantines report pending holds on every cycle until cleared. Scratch and export deletion failures each persist in a pending set of at most 100 subjects in meta. A persisted rotation index gives each member a turn across cycles. Retries receive at most half of the owner's cooperative time and operation allowance; the main scan receives the remainder and skips pending members. Individual synchronous operations can overrun that allowance. Outstanding subjects report `partial` with `scratch-cleanup-pending` or `export-cleanup-pending`; overflow reports `scratch-pending-overflow` or `export-pending-overflow` and stops cursor advancement at the failed subject until capacity is available. Pending reasons remain visible even when failure details fill the bounded status list. Actual scratch removals publish counted deleted outcomes; already-absent artifacts publish nonpending kept outcomes. Unfinished scans report `partial` and `scan-pending`, and each owner receives an independent budget on startup and daily retry.

Retention compares wall-clock change with monotonic elapsed time between runs. Samples older than one minute are discarded; they cannot distinguish accumulated drift from a single step. A forward discrepancy above one minute in a recent sample opens a one-second untrusted window. The cutoff includes a one-minute safety margin, so second-scale wall-clock steps do not decide day-granular expiry. A terminal timestamp earlier than any preceding timestamp in the same job is kept as `terminal-clock-regression`. The cutoff uses wall time without a per-boot age anchor, so idle restarts do not reset expiration. An unwitnessed clock error larger than the retention period can still expire results early; this residual loss of results is accepted. Gradual drift below the detector tolerance is also not distinguished from elapsed age. Age, regression and residue holds are visible kept outcomes and make the run `partial` while work remains.

`jobs/export-retention.ts` owns whole terminal exports and provider artifacts. Exports without location records have no epoch closure hold. Residue eligibility checks the export directory and top-level entry mtimes, including directories, without walking descendants. Deletion admission persists in meta across partial cleanup; top-level content newer than the admitted cutoff keeps the residue. Unknown protected epochs retain their exports. `jobs/progress-retention.ts` owns journal progress pruning. `coordinator/composition/storage-retention-scheduler.ts` schedules these owners after serving and every 24 hours using `CORAL_JOBS_RETENTION_DAYS`; each owner has its own 5-second cooperative budget and stops on shutdown or writer park.

## Causality

Cross-stream event references live below the domains in `causality/`. `CauseRef` is vocabulary, not storage: domains can point at originating Journal events without importing `store/`, database handles, or each other's shells.

## Recovery Containment

`recovery/` owns the single recovery-enumeration boundary, opaque source handles, source registry, and quarantine persistence; raw source modules and settlement policy remain domain-owned and carry no registry/pool knowledge into the boundary. `RecoveryContainment.each(source, policy)` is the only enumeration surface and runs the scan → hydrate → settle phases. Quarantine or durable-continuation dispositions converge in `recovery_quarantine`, while successful exact retries remove their retained row. `recovery/unreadable-provider-operation.ts` owns the strict discard request/result vocabulary, including readable-deletion consent, the `recovery-in-progress` arm with `backend_recovering`, and `adoption-refused` with its row disposition, released-permit count, and complete refused-record identity. The launch-fence arm is a pre-inspection refusal: the raw row, due pointers, quarantine evidence, startup permit, and launch capacity remain unchanged, and its remediation is to wait for startup recovery to finish before running the command again. Static architecture invariants reject direct scan access, forged handles/receipts, eager pre-enumeration, and unmanifested startup walks. Because `recovery_quarantine` is executable store DDL, adding it moved the application-wide store-format fingerprint for this release.

### Jobs wait and terminal owners

`jobs/wait/session.ts:WaitSession` owns the shared streaming/snapshot session contract: admission, progress frontiers/line offsets, terminal acknowledgement, artifact settlement, carrier coverage and exit precedence. `jobs/wait/reader.ts` reads streams; `jobs/wait/snapshot.ts` selects bounded unary snapshots for `wait jobs --now`. Snapshot continuations retain `--now`; dropping it opens a blocking wait. `jobs/wait/cursor.ts` owns the single per-job cursor shape and its compact encoding; a cursor in any other shape is refused softly and the CLI restarts fresh with the replay notice.

`jobs/location-index.ts:JobLocationView` supplies read-only locations to `JobAddressing`. Historical source reads use no-repair shared guards and read-only SQLite opens; SQLite reader sidecars are allowed, while Coral-record writes and fsync/fdatasync are forbidden. Startup and epoch maintenance own hydration. Validated retained terminals survive source retirement; failed reads without usable retained outcomes stay unresolved.

`jobs/terminal/recording.ts:appendJobTerminalRecorded` owns raw terminal recording. Coordinator materializers and existing event builders call it. Active wait continuity comes from the current provider session through `jobs/shell/wait.ts:readQueryContinuity`; historical wait continuity is null. No immutable terminal-continuity snapshot is recorded.

`jobs/terminal/export.ts:TerminalResultExportOwner` alone publishes result.md from accepted journal facts. Workflow composition injects its source fact reader and pure step renderer through a report port. Read-only availability has four states: `available`, `retained-away`, `repair-pending`, `failed`. Only available files get `Result path:`; older path claims get `Unverified result path:`. Write-owned post-commit/startup/historical/maintenance paths repair eligible missing files, preserving available files. Publication uses unique atomic stages, no shared export lock and no sibling-stage sweep, with authorization rechecked immediately before rename.

`jobs/export-retention.ts:terminalEligibility` is the common epoch-aware age authority for retention, availability, repair and retirement. A trusted cutoff expires only `terminalAt < cutoff`. `JobLocationIndex.resultDurable` first requires semantically validated retained terminal detail, then accepts a regular nonempty durable file or known past-window age. Unknown/regressed age never discharges by age. Source-backed regression can authorize canonical publication and file-based proof; retained-only regression cannot. Compaction preserves the additive terminalAge evidence through source retirement and restart.

## Provider Adapters

Provider adapters translate between the domain contract and external CLIs. Codex uses the Codex app-server surface; Claude uses a broker helper around Claude CLI, defaulting to `claude -p` stream-json and retaining an opt-in PTY TUI transport. Adapter-level changes must preserve wire-compatibility with the adapted provider. Adapters normalize provider usage at this boundary to the canonical additive `UsageSummary` (`inputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `outputTokens`, optional `costUsd`) before it reaches jobs. Provider-owned profile, binding, and continuity parsers contribute their exact persisted contracts to the application-wide store format. `ProviderRegistry.register` rejects a managed provider unless it declares `provider-artifact-discard.v1` with both `discardArtifacts` and `reconcileDiscard`; reconciliation is closed over `applied | not-applied | definitive-failure | unknown`.

Codex request mapping keeps Coral's tier-to-size policy while reading the app-server model catalog once per kernel invocation, after effective transport verification and without a Coral-side cache. It selects the highest numeric version per size among non-hidden models without an upgrade flag and shares one resolved model and effort across thread creation/resume and turn start. Defaults and pin semantics are defined in [configuration](./configuration.md#codex-model-selection). An unavailable catalog, a missing size, or skipped malformed entries produce a single progress notice naming each finding and the model used. Catalog-supported effort levels determine the ceiling while Coral retains its Terra/Luna reasoning floor.

Provider preflight has three answers in `ProviderPreflightOutcome`: `satisfied`, `refused`, and `undetermined`. This ownership boundary is mandatory: a provider classifies only what it observed, and the coordinator's `PreflightDecision` policy alone owns the `provider | deadline` causes, including the deadline no provider can observe. Returning no valid answer is not another undetermined cause but the internal fault `provider_preflight_faulted`: a throw, a rejection, a fulfilled value outside the union, and a recognised `refused` or `undetermined` whose required message is missing or blank all reach it, because a discriminator without the message a caller reads is not an answer either. An adapter therefore never names a cause, and never assigns a status — `docs/architecture.md` carries what the wire does with each answer and fault.

Provider-host state has three separate vocabularies: process `open | closed`, derived serviceability `serviceable | unserviceable | unknown`, and fresh-placement admission `candidate | blocked`. These are not carrier states: a carrier verdict asks whether work exists, while provider-host serviceability asks whether a present process has answered a typed prerequisite successfully. `providers/app-server-transport.ts` records one diagnostic fact only after a provider response completes and retains its sequenced host-log span; it makes no serviceability decision. Provider-owned pure classifiers interpret those facts, and `providers/host-admission.ts` joins each finding to the exact owner-local slot, host reference, and transport generation. A mute request produces no fact, so no timeout, clock, or failure counter can move the host out of `unknown`. A negative finding blocks only the fresh-placement wrapper; exact session attachment remains available for interrupt and probe.

The shared admission collection carries no close authority. Coordinator-local placement is owned by `DefaultProviderHostManager`; routed placement is owned by the provider proxy's narrower host pool. Each owner retains a naturally retired blocked host as a bounded-diagnostics tombstone and performs its own exact eviction. Only the coordinator administration service may aggregate those owners for an operator: it captures the owner set, requires every inventory to validate, resolves exactly one row, and routes inspect or eviction back to that row's owner. Derived serviceability never invokes eviction.

Coordinator-local app-servers are admitted only on a platform with signalable POSIX process groups. They are spawned detached, and their process incarnation plus `kill(-pid, 0)` group proof are recorded on the host entry before admission; teardown reaps that identity through the shared recorded-containment primitive. Proxy-owned app-servers are not detached again because the guardian has already established their containing group; per-host close is child-only, so leaked descendants can remain until proxy-set teardown. The same host entry carries a token map of acquisition or attached-session pin origins. Idempotent release closures remove exact tokens, and the map size is the retirement authority: Codex uses `'unleased'`, Claude uses `'unleased-and-host-idle'` because its internally multiplexing broker must also emit an idle `host/stats`, and `'never'` disables idle retirement. External Codex does not emit Coral's `host/stats`. The no-live-Codex-job diagnostic reports outstanding pin origins but never closes on that evidence, because an attached-session pin may have no job id.

## Expansion

Expansion is the installable runtime contract that lets optional backends bind to a domain's `RuntimeBinding<Backed<T>>` cells without the domain knowing whether the binding is held. An `Expansion = (host) => void | Promise<void>` is a single-function contract; bundled and installed expansions receive the same host contract. The KB daemon owns and composes `ExpansionLifecycleService`. Its manifest catalog merges the static `BUNDLED_ENGINES` entries with validated installed-tier rows from `expansion_manifest_catalog`. At boot, the daemon invokes bundled loaders from its static fallback registry; an explicit equip dynamically imports an installed entry, invokes it under a fresh disposable scope, and persists `{id, version, installed_at}` in `expansion_state`. Unequip disposes that scope and deletes the row.

KbRuntime registers built-in capability descriptors and empty `RuntimeBinding<Backed<T>>` cells; engines fill those cells through the same binding contract whether they are bundled or installed. Bundled Orama binds `kb.fts` during expansion lifecycle startup. `kb.embedding` carries no constructor-time default — embedders are peer engines (`gemini`, `onnx`) — and no current first-party engine binds `kb.vector`; external engines may fill it through the provider-neutral contract. Single-occupancy is enforced inside `RuntimeBinding.bind` itself (throws `binding-occupied` if held), not by lifecycle bookkeeping. Retrieval-consumer freshness is observed through `ConsumerDriver.waitFreshUntil('corpus', snapshot, consumerId)` after the Corpus commit; readiness is a comparison (`backed.consumer.cursor ≥ corpus version`), not a method on the `Backed<T>` contract. Every Corpus consumer registration must provide `readAuthoritativeFreshness(target)` returning `current | stale | unavailable`; `ConsumerDriver.register` throws when it is absent.

## Knowledge Base

The KB domain owns the Corpus markdown authority over notes, sources, principles, communities, and wiki entries; text and vector search contracts; note and wiki mutation; source persistence; background curation (content-fingerprint-driven note/source classification, community detection, entity consolidation, wiki touch-journal drain that bubbles touched Knowledge links one position toward the front per touch event — transposition heuristic; semantic wiki mutations are user/LLM workflow only); conflict-free multi-machine git sync for derived KB metadata; and the project-scoped memo scratch lifecycle. Source import conversion is coordinator-owned because it can be long-running and is represented as an internal `kb.source_import` job with explicit readiness (`commit`, `base-search`, `active-vector`, `all-equipped`). Explicit reindex is also coordinator-owned as an internal `kb.reindex` job: the KB op rebuilds text artifacts, and the coordinator service waits for base-search freshness. These jobs are Journal-observable process attempts, not provider/session jobs.

Classification pending state is content-driven: the index stores `bodyHash` plus note/source `inputFingerprint`, and curation claims only entries where `inputFingerprint` is absent or differs from the `bodyHash` already stored in the same index entry (no live re-hash at claim time). A synced peer can therefore reuse already-curated frontmatter without re-running the LLM. The curation cursor is `(timestamp, kind, slug)` (`createdAt` for notes, `importedAt` for sources); the per-machine `contentSeq` and `metadataSeq` counters (and the `currentEntrySeq()` derived from them) remain freshness metadata, not the cross-machine ordering key.

Curate/git-sync implementation lives in the KB domain: `kb/curate/entity-graph-merge-driver.ts` merges `.entity-graph.json` by feeding a union of ours and theirs into `consolidateEntityGraph` from an empty base (the git merge base is ignored — it carries no deletion semantics here); `kb/curate/frontmatter-merge-driver.ts` unions frontmatter set fields (`tags`, `principles`, `related`) and resolves scalar fields via body-match/lexicographic tiebreaks, delegating body prose to `git merge-file`; `kb/curate/conflict-quarantine.ts` records entries skipped after unrecoverable body-prose conflicts. `ensureKbMergeDrivers()` in `kb/curate/git-sync.ts` appends the managed `.gitattributes` entries, registers the merge drivers, and pins `rebase.backend=merge`; derivatives and frontmatter resolve without the LLM, while irreducible body-prose conflicts fall back to the LLM resolver as a last resort before git sync aborts the rebase, preserves local commits under `refs/coral-recovery/<branch>/...`, resets to `origin/<branch>`, and quarantines the affected entries. The AC7 rollout migration in `kb/migrations/index.ts` is TEMPORARY (REMOVE AFTER ~2026-07); it backfills missing `inputFingerprint`; errors are caught and logged inside `runPendingKbMigrations`, so a migration failure never blocks scheduler startup.

The KB mutation lock commits Corpus state and text artifacts only. It does not install retrieval projections. Orama is the base CorpusConsumer; optional installed retrieval engines register their own CorpusConsumers and rebuild derived state from the Corpus snapshot they apply.

Orama has a deliberate read/write split. `OramaSearchPort` is a pure consumer of `OramaSnapshotStore`: `ensureLoaded`, `search`, `tokenize`, and `tokenizeBatch` never synchronously rebuild, persist, or call `forceCorpusApply`. They classify cached or persisted artifact metadata with `classifyProjectionMismatch`, activate a served-index record, and query with the tokenizer that matches the served artifact. Intl-tier artifacts are always served through the Intl tokenizer. Kiwi-tier artifacts are served only while a live Kiwi analyzer lease can bind the tokenizer; if the lease is unavailable, the read path returns the degraded/uninitialized FTS path and asks for reconcile instead of querying a Kiwi index through Intl. During an Intl→Kiwi upgrade, a valid Intl artifact is served immediately under the Intl tokenizer, `fts_index_stale_tier` is surfaced, and `requestProjectionReconcile('stale-tier')` is fired without awaiting it.

Orama reconcile ownership lives in the KB daemon's expansion lifecycle, using the shared `projection-consumers/` driver. `createOramaProjectionReconcileRequester` is wired into one `OramaBaseProjection`; that projection's single read port is exposed as both the registered CorpusConsumer and the bound FTS capability. The requester single-flights reconcile requests and delegates writes to `ConsumerDriver.forceCorpusApply(currentSnapshot, { reason: 'projection-artifact-lag', consumers: [ORAMA_BASE_CONSUMER_ID] })`. The read model only requests reconcile. The write path remains the CorpusConsumer apply path, which persists Orama artifacts, stores the returned metadata in the cache, and uses a freshness-safe identity-aware lost-update guard: strictly fresher persisted artifacts win, but equal-snapshot identity-changing tier reconciles are allowed to converge.

Kiwi degradation also reconciles through the KB daemon's expansion lifecycle. The bundled Orama loader registers a mandatory `KiwiAnalyzerManager.observeDegraded` observer scoped to the expansion `host.scope`; scope disposal removes it from the process-singleton manager. `markDegraded` records degraded state and schedules the observer as a fire-and-forget microtask, then throws the terminal Kiwi load error; the observer runs asynchronously after the throw propagates, and observer failures are caught so the terminal-error path remains intact. The observer calls the same `createOramaProjectionReconcileRequester` requester with the `kiwi-degraded` path, which invalidates the text snapshot with `kiwi-degraded` and force-applies the Orama consumer, allowing a terminally degraded Kiwi index to converge back to the Intl tier without a corpus edit or restart. `onApplyFailure` is supplemental coverage, not the primary degradation signal.

Orama projection sidecars carry identity metadata in addition to snapshot metadata: `identitySchemaVersion`, schema version/digest, Node/ICU versions, tokenizer identity, and declared analyzers. Retired sidecars without those fields still parse, but classify as incompatible and are not serve-stale eligible. `identitySchemaVersion` participates in `ORAMA_PROJECTION_IDENTITY_HASH`, so old sidecars are detected as projection-artifact lag on boot; an Orama-only boot repair that times out with `FreshnessTimeout` is non-fatal to KB readiness and leaves FTS stale or uninitialized while the background reconcile continues.

## Work Classes

Jobs are not an async wrapper for every command. They are durable work ledgers for long-running, observable, or recovery-relevant attempts.

| Class                    | Examples                                | Owner                                                       |
| ------------------------ | --------------------------------------- | ----------------------------------------------------------- |
| Direct read              | KB read/list, `jobs`, discuss watch     | Read model or KB query helpers; no durable artifact rebuild |
| Served read              | KB search                               | KB daemon search runtime; no durable job ledger             |
| Direct mutation          | KB note write/delete; memo write/delete | Corpus lock for KB notes; project data dir for memos        |
| Provider/session job     | Codex/Claude launches, workflow atoms   | Jobs + sessions + provider adapters                         |
| Internal coordinator job | KB source import, KB reindex            | Coordinator service over jobs + KB                          |
| Projection freshness     | Active retrieval-consumer catch-up      | ConsumerDriver cursor wait                                  |

Direct KB reads are coordinator-free, not context-free. CLI/bootstrap adapters resolve plugin root, build flavor, project root, Corpus root, and KB runtime root before invoking KB query helpers or `read-model/CoralStore`; lower KB path helpers do not choose `cwd`, `HOME`, or `CORAL_KB_PATH` on their own. KB search is a served read: it uses the KB daemon's search runtime instead of the direct read model.

Projection freshness is not authority. A Corpus commit remains durable even if a retrieval consumer fails to catch up; callers that requested readiness observe that failure through the hosting command or job.

The coordinator layer owns process lifecycle, the three-era boot sequence (Kernel → Recovery → Runtime Health Components), projection-consumer wiring, provider-host coordination, job-backed KB source import/reindex proxying, and the corpus notify seam. Its provider-host administration service is an aggregator and router, not the sole host authority: the coordinator-local manager and every live provider proxy report their own live/tombstoned inventory and execute their own admission and eviction. Federation is all-or-error, and exact owner revalidation prevents a selection race from retargeting a destructive operation. It also owns the evidence-gathering half of carrier observation that the classifier deliberately does not: `composition/carrier-observation.ts` gathers local evidence (admission state, the OS process table, and the durable-CLI identity row), classifies health and idle synchronously from that evidence, and builds wait's asynchronous observation port. That method is a nonce- and proxy/build-bound, read-only ledger-liveness handshake; `operation.inspect.v1` remains the richer durable-saga ambiguity surface used by reconciliation. An unanswered status question is `unknown`, not absence, and every consumer treats it as conservatively active. Only a positive `absent` may render a wait interruption, and even that derived finding authorizes no recovery, cleanup, reconciliation, terminal materialization, or other mutation. `tests/invariants/no-carrier-observation-in-action-paths.test.ts` enforces that boundary at every import depth. Liveness itself is three-valued and says so in its type: `infra/node-process.ts`'s `observeProcessLiveness` answers `alive | absent | unknown`, where `EPERM` is alive, only `ESRCH` is absent, and any other probe failure is a question that could not be asked. The type makes the compiler enumerate every caller, and only `absent` may finalize anything. The same module composes that probe into the question a durable record asks: `createRecordedProcessObserver` (`infra/node-process.ts`) binds an injected incarnation reader and an injected liveness reader into one `RecordedProcessObserver` over a recorded `{ pid, incarnation }`, consulting identity before liveness and falling through to liveness where the record carries no token or none could be read. Its answer is the same three-valued `ProcessLiveness`, so an `absent` reached by either route is what may finalize and `unknown` still never is. Because the readers are injected rather than reached for, the observer can be handed to code entitled only to conclude: provider-proxy set lifecycle receives one beside the discovered capsule list (`coordinator/composition/execution-services.ts`) and decides handoff-capsule retirement from it while its own deps carry no capability to spawn, kill, or signal. Both real and simulation runtimes supply the database engine through `StoragePort`. Production publication crosses generation admission before SQLite, retrying both forms of contention against one monotonic deadline and returning `generation-maintenance` if maintenance wins admission. Writer leases store pid plus incarnation in their contents; an unknown process observation never authorizes removal and instead reaches the independently heartbeating lease's ten-minute stale successor. Publication is a SQLite transaction at `handoff-routing.<generation>.db` rather than an advisory lock over JSON, and the reason is that publication and exclusion are then the same act — an advisory fence is not consulted by `rename(2)`, so a writer that lost one still publishes, while nothing becomes visible except through a `COMMIT` that cannot succeed without the lock it verifies. Two settings carry that: `busy_timeout=0` keeps the wait in JS rather than in C where it would block the event loop, and `BEGIN IMMEDIATE` takes the write lock before the read-validate prefix a deferred transaction would leave unprotected. A failure before the `COMMIT` attempt is decisively `not-published`; a failure after that attempt starts is `commit-outcome-unknown`, regardless of its SQLite cause. Admission reserves a maximum legal closing record for every unresolved opening, because reserving space and admitting a record are different things and a terminal that cannot be admitted is an obligation that can never close. The reader answers `absent | vacant | uninitialized | detached-wal | generation-missing | foreign-generation | format-mismatch | schema-divergent | current | unreadable | undeterminable`; expected discard guard failures are result variants rather than throws, and the read projection validates the reserve invariant so it cannot certify an obligation whose exit could not commit.

The daemon bind handoff also stays inside that Runtime world, and it never signals a live incumbent. `bindWithHandoff` in `src/coordinator/handoff.ts` retries the bind on the Runtime time port until its budget expires. An answering incumbent that is not draining is reused: the contender passes it to `requestUpgradeFromContender`, which registers an upgrade only for a strictly newer same-flavor target, and a failed negotiation grants no replacement authority. A draining incumbent releases the socket through its own shutdown sequence, so the contender keeps polling for the bind. An unanswered probe is not a refusal: the contender keeps probing until its budget expires, and an address still bound at the deadline refuses with `handoff_socket_holder_unverified`; startup reports that hold and infers no consent from a version comparison, a timeout, or an earlier contender's signal.

`runtime/errors.ts` is the canonical documented setup-error registry for authored public text, retryability, and CLI exit. The generation-mutation store owner classifies a live writer as `legacy_source_not_quiescent` and an unobservable writer as `legacy_source_writer_observation_unknown`; direct, IPC, HTTP, and CLI boundaries carry that code unchanged. Bootstrap diagnostics derive `retryable` from the registry; backend status accepts both booleans and carries them in `recent_failure` while continuing to exclude structured context from public rendering. `cli/errors.ts` consults the registry for documented codes, and expansion retains only its non-error exit-0 deviation before delegating errors to the same mapper.

An ordinary routing writer probes the maintenance lease through heartbeat-aware lock acquisition while holding
generation admission. A live holder remains `generation-maintenance`; an abandoned holder becomes reclaimable
after the ten-minute heartbeat stale bound, and the CLI names that retry path instead of promising an active
maintenance operation will finish.

The persisted routing classification has one rule: a disposition is a hold only when a Coral operation can change its record; every other disposition is retained and rendered history with exit contribution 0. A `Record` keyed by every persisted disposition kind makes that decision mandatory for new kinds. Exact capacity evictions remain holds until resolve folds them into aggregate history; every committed terminal, including a terminal recorded without a selection, is history. `coordinator/handoff-routing/status-operator.ts` owns offline discard and quarantine-clear authorization and orchestration, while `store/handoff-routing-status-store.ts` retains raw filesystem mutation and the CLI only supplies the socket guard. Expected pre-effect storage failures, including root creation, return typed outcomes; post-effect failures distinguish directory-barriered effects from namespace changes that were only observed before a failed barrier.

The main `handoff-routing.<generation>.db` file is hard-capped at 1 MiB by `max_page_count`. `journal_size_limit=1_048_576` returns its WAL to at most 1 MiB when a checkpoint can reset it, and `wal_autocheckpoint` is `floor(1_048_576 / page_size)` pages (256 at a 4-KiB page size) so checkpoint attempts follow the same budget. SQLite cannot hard-cap the WAL while an open reader prevents reset: it may exceed 1 MiB by the writes accumulated during that reader's lifetime and returns to the configured limit only when a checkpoint can reset it. The `-shm` file is a SQLite-managed sidecar, not part of the main-file hard cap.

The coordinator receives the observation intact beside role, method, and scheduler lateness, so it never reconstructs peer evidence from an error origin or reason string. Each set, role, and method has one exclusive `clear | silence | answered-unusable` window. No-response advances silence; an unusable reply replaces silence with a fresh answered-unusable window; accepted and challenge-mismatch replies clear either state. Locally unsent and channel-fault observations cannot produce window state. Once a continuous answer-free, set-derived adoption-window span elapses without material scheduler lateness, `heartbeat_hold_exhausted` joins its two siblings — a recognised `method_not_found` and an exhausted answered-unusable window — on the coordinator's non-destructive `await-containment-absence` action rather than `stop-and-reap`. With live claims present none of the three may authorize destruction on their own: the coordinator instead records a held, non-authorizing disposition and keeps the route and heartbeat loop running, so a later accepted answer or the set draining to zero claims can still clear it without ever sending the destructive control RPC. Attempts are rendered evidence, never an exit predicate. The bound is carried by each established set as timing — resolved configuration for fresh acquisition and the capsule timeout for redemption — rather than as proof that another role accepted ownership. One seam is a deliberate exception: on `foreign-capsule-retirement` every way the `capsule-retirement` producer can disappoint reaches the owner-local incident channel and none reaches the global fatal sink, because that owner holds a capsule path and nothing else. `provider-proxy-set/index.ts` owns the hold that follows — a bounded local retry to `FOREIGN_CAPSULE_RETIREMENT_ATTEMPT_LIMIT` attempts whose exhaustion drops the owner, leaves the capsule's conservative representation standing for the rest of the boot, and hands the path back to a later boot's discovery. A claim-bearing reap requires a containment-qualified terminal fault, while faultless retirement can reap only with literal `liveClaims: 0`. The provider-proxy domain owns enforcement and reap mechanics for that authorized decision; the separate deadline machines in guardian and reaper no longer enforce autonomously at their adoption deadlines once a holder is published — each tick instead classifies the admitted control holder `alive | absent | unobservable` from a recorded-process observation and mints a demolition capability only on proven `absent`, holding on `unobservable` and renewing the check on `alive`. Before publication, no operation authority has been returned and no claim can exist, so the tick lets the pure clock bound decide even when an installed provisional holder is unobservable — the one place elapsed time alone still authorizes teardown, and nothing is at risk when it does.

## Runtime Components

`coordinator/runtime-components/` is a small registry layer for daemon-visible health/lifecycle components that must not extend the kernel path. It does not host the KB runtime; the parent registers the mandatory recovery component and a best-effort KB daemon health mirror:

- `contract.ts` — `RuntimeComponent` (init / dispose / status), `RuntimeComponentStatus` (4 serving phases: `initializing → online | degraded | offline`), `DegradedReason` (`{ kind: 'curate-publish'; consecutiveFailures; lastError } | { kind: 'recovery-quarantine'; count; lastError }`), and branded `RuntimeComponentId`.
- `registry.ts` — `createRuntimeComponentRegistry()` exposing `register / initAll / disposeAll / list / status`. It is a status/lifecycle projection only; KB requests go through the KB daemon supervisor, not through this registry.
- `recovery-component.ts` — projects `recovery_quarantine` count and latest error into daemon health. Its registration is mandatory and aborts startup on failure; unlike KB registration, it is not wrapped as best effort.
- `runtime-components/kb-health-component.ts` — `createKbDaemonHealthComponent(kbDaemonSupervisor)` mirrors daemon health into `/health.components[]`; the KB daemon process owns the boot pipeline (Corpus replay + CorpusConsumer registration + Orama freshness wait), runtime construction, curate work, and expansion lifecycle. When `CORAL_KB_ENABLE=0`, the parent wires a disabled daemon supervisor, so the health component reports terminal `offline` with `KB_DISABLED_REASON` and does not spawn the KB daemon. The CLI matches that reason on `/health` to decide whether to restart the daemon and re-enable KB.

KB request failures (`kb_initializing`, `kb_offline`, `kb_disabled`) come from the KB daemon request/supervisor path and lift to HTTP 503 through the standard error envelope with the `remediation` field.

`createKbDaemonSupervisor` in `src/coordinator/live/kb-daemon-supervisor/index.ts` assembles its process and request ports around `KbDaemonSupervisorState` in `kb-daemon-supervisor/state.ts`. The adjacent `kb-daemon-supervisor/` modules own health and exit observation, parent requests, probes, RPC decoding and recovery, process start and stop, stdout dispatch, and the public supervisor ports.

Five invariants enforce the contract: `runtime-component-contract-singleton`, `kb-daemon-error-codes`, `lifecycle-phase-monotonic`, `abort-signal-threading`, `no-kb-status-accessors`.

Workflow plans persist only semantic slots: slot id, dependencies, provider, instruction, and optional agent. Step indexes, display labels, and atom keys are derived from that semantic plan. Child job ids are separate runtime identities: initial execution mints them through the runtime `ids` port. Recovery reconstructs the current mapping by reusing the durable `job_id` for a `workflowSlotId` with a current child row, mints an id for a slot without a row, and mints a new id for the next replacement generation when a pending continuation lease requires one.

## Stable Seams

These are the load-bearing boundaries that must not leak:

- The Runtime interface is the only channel for I/O inside the backend.
- The boot eras are ordered — Era I blocks until kernel-ready, Era II blocks until running, Era III runs fire-and-forget. Existing-incumbent and existing-starting probes remain fail-fast under `KERNEL_READY_DEADLINE_MS = 15s`. A newly spawned current attempt remains under supervisor ownership while its initiating reader observes the 660-second recovery budget until authenticated readiness or that exact child becomes terminal; terminality triggers one final readiness probe and one final exact-attempt startup diagnostic read, and a coordinator that still answers the address without naming its own shutdown converts the wait into the bounded existing-starting wait rather than finalizing a failed startup. Backend-startup delegation keeps the original child responsible until the selected backend is authentically ready or terminal, transitively through further delegation. The 100 ms interval is only the delegated-readiness poll cadence, never evidence of readiness.
- `AbortSignal` is the cancellation primitive throughout startup. Aborting the startup signal with no string reason preserves the `AbortError` discriminator; calling `abort('shutdown')` strips that discriminator and breaks downstream `name === 'AbortError'` checks. Enforced by the `abort-signal-threading` invariant.
- Each domain owner module/contract set is the coordinator-facing surface for its domain; deleted `api.ts` barrels and compatibility shims are not recreated for convenience.
- `store/` is the SQL/Journal substrate; `read-model/CoralStore` composes product reads over domain-owned query modules.
- Routing-status quarantine is bounded store evidence: sidecars move before the main database, an incomplete UUID-addressed set refuses a new discard until the operator clears its exact ID, and the seventeenth complete or incomplete set is refused until an operator lists and clears an exact ID.
- Domain registries own event schemas, append validators, and reducers; `store/` only runs the composed validators transactionally.
- Expansion lifecycle is KB-daemon-owned: transport reaches it through the parent `KbDaemonSupervisor.expansionRpc` proxy, and the KB daemon resolves active backends through `kbRuntime.<name>.read()` on each `RuntimeBinding<Backed<T>>` cell.
- KB retrieval projections are rebuildable consumers of the Corpus authority; source import and explicit reindex readiness wait on `ConsumerDriver.waitFreshUntil('corpus', ...)`.
- KB source import/reindex failure facts are recorded by coordinator-owned KB job recording glue as job progress cause events; the KB domain remains Corpus authority only.
- Compatibility shims are not stable seams on the rewrite branch; retired owner paths stay deleted once responsibility moves.
- Hooks never import from `src/`; shared hook logic lives alongside the hooks themselves.
- Runtime ingestion emits canonical domain events; incompatible historical bodies are rejected and the store-format reset boundary handles adoption.

`jobs/location-index.ts:JobLocationIndex.compactTerminalRecords` owns automatic bounded compaction of terminal details, preserving the matching terminal event and additive status/exit fields. `jobs/location-recovery.ts:recoverJobLocations` requests terminal-only journal events and avoids unchanged durable writes. The storage scheduler checkpoints compaction independently of boot.

`coordinator/services/recovery/custody-reconciliation.ts:reconcileFinishedCustody` owns exact bound-entry discharge: applicable retained terminal/results and matching transfers, plus recorded incarnation and containment absence confirmed through `reapRecordedContainment`. `store/custody-ledger.ts:pruneCustodyLedger` owns whole-entry retention after reconciliation, under entry locks and writer fencing. The single `CORAL_JOBS_RETENTION_DAYS` knob gates deletion from absence proof time. Atomic rename into `.stage.retention.*`, directory fsync and a durable receipt bound to root/entry identity allow bounded crash cleanup without partially visible entries. The ledger root and coverage metadata remain. `coordinator/composition/storage-retention-scheduler.ts` retries budget-limited `scan-pending` backlogs after five minutes and otherwise remains daily; backend status adds `deletedByOwner` counts for exports, progress rows, holder markers, scratch, custody and reclaimed vacuum pages. Export admission, rename and evidence share one fenced transaction. Small trees preserve the first-leaf yield, then retire their remaining entries in one transaction (at most eight entries); larger trees batch at most eight leaves. Transactions end before async discovery yields.

Compaction persists identity-keyed refusals under `job-locations.v1/compaction-refusals.v1`, advances past damaged records, and retries them daily; readable evidence clears the refusal. Custody discharge uses `JobLocationIndex.resultDurable` independently for each job: validated retained terminal detail precedes either a regular nonempty durable file, known expired-age discharge, or validated unknown-age legacy terminal with an absent export directory and includes both the initial identity-bound child root and all transferred roots. Missing or unobservable evidence holds custody until daily reconciliation can prove those obligations. Recovered export retirements commit validated admission and initial evidence before their first deletion batch. Repair failures and pending repair use the five-minute retry cadence. A run that cannot execute an owner preserves its due slot and schedules another attempt after one second. Other failed owners retain their daily cadence.
