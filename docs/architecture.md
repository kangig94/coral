# Architecture

Coral is a coding-assistant plugin for Claude Code, Codex, and GitHub Copilot CLI. Its purpose is to help LLM agents do software work better: plan/review workflows, side-effect and bug discovery, multi-perspective discussion, durable job observation, session continuity, and long-term project memory through KB.

Internally, Coral is a local coding-agent coordination layer. Claude Code reaches Coral through hooks, slash-command skills, and Bash calls to `coral-cli`. For local mutating and live-follow commands, `coral-cli` ensures the backend daemon is running and talks over the authenticated IPC socket. Read-only no-coordinator paths use the `read-model/CoralStore` facade directly. HTTP remains available as the remote gateway plus the operational carveouts (`/health`, `/admin/shutdown`, `/events/stream`). No bridge or stdio proxy remains in the runtime path.

Coral also has a build flavor axis. `prod` is the marketplace-installed runtime and `dev` is a local build meant to coexist with it on the same machine. Each bundle embeds `version`, `buildSetId`, `flavor`, and `storeFormatFingerprint`; the adjacent manifest in the active artifact directory repeats those fields and binds the backend, CLI, and Claude helper by content hash. Ordinary and dev builds use `clients/build/manifest.json`; published release bundles use `clients/bridge/manifest.json`. The embedded identity and adjacent manifest form one matched attestation set. `CORAL_FLAVOR` is only a session-level hook selector that decides which hook set should execute.

A build that cannot present that attestation set does not borrow an identity. `resolveStrictBundleIdentity` (`infra/bundle-manifest.ts`) answers `embedded_identity_unavailable` both when the four injected constants are absent — a source checkout, where nothing replaced them — and when they are present but hold values its schema refuses, so this is a bundled build's failure mode too and not a source-mode-only path. On that one reason startup continues (`coordinator/composition/world.ts`) and mints a fresh `buildSetId` for the boot, so no two boots ever claim the same build; every other reason concerns the adjacent manifest — missing, invalid, or disagreeing — and still aborts. Such a boot does not inherit an earlier run's proxy set: redemption compares the durable record's `buildSetId` against its own, answers not-bequeathed before reading a capsule, and leaves the abandoned set to its own orphan deadline. Store selection recovery has no staged-reset resume or parked-active-evidence protocol: it durably republishes the retained transition and selection, then settles the selected store epoch through the ordinary startup routing path.

## Design Frame

The product frame is coding assistance. The architecture frame is local coordination. "Control plane" in this document is internal vocabulary: the coordinator owns local decisions, live state, recovery sequencing, and capability activation so Claude/Codex do not have to manage those concerns inside prompts or shell glue.

| Product capability                  | Internal owner                              |
| ----------------------------------- | ------------------------------------------- |
| Plan/review workflow                | Workflow plan + jobs execution              |
| Side-effect and bug discovery       | Workflow slots, provider jobs, wait/follow  |
| Idea digging and multi-agent review | Discuss domain and shell                    |
| Long-term coding memory             | KB Corpus authority + retrieval projections |
| Provider conversation continuity    | `ProviderSession` aggregate                 |
| Executable work ownership           | `ExecutionOwner` on every job               |
| Long-running observable work        | Jobs authority                              |
| Optional sharper retrieval          | KB daemon expansion lifecycle               |

This frame constrains new code: first name the truth owner, then decide whether the work is direct, durable, or projection freshness, then compose cross-domain behavior only in the coordinator or CLI.

## Supported Platforms

Coral supports **Linux and macOS**. Windows is not supported: `socketPathForRunDir` (`infra/path/coordinator.ts`) has no named-pipe branch, and CI runs Linux only. A feature may not narrow that set to one platform — where a platform lacks a capability, the narrowing belongs at the operation that needs it, not at admission. macOS is the case that keeps this honest: a Darwin process incarnation cannot authorize a signal (`incarnationMayAuthorizeSignal`, `infra/node-process.ts`), so the signal boundary refuses and the resulting containment stays visible as a cleanup hold, while launches are still admitted. 0.10.10 shipped the opposite arrangement and refused every macOS provider host; [`darwin-signal-authority.md`](./todo/darwin-signal-authority.md) carries what is still owed there.

## Provider Usage Reporting

Usage is captured at each provider boundary before provider-specific stream shapes enter the jobs domain. Providers normalize their raw counters to the canonical additive `UsageSummary`: `{ inputTokens, cacheReadTokens, cacheWriteTokens, outputTokens, costUsd }`. Token totals are derived by renderers from the four token buckets and are never stored as `totalTokens`.

The canonical storage home is the job terminal record's `diagnostics.usage` field. In the read model, that lives in `projection_jobs.diagnostics`; live wait, replay wait, SSE reconnect, and job detail all read usage from the same terminal diagnostics instead of recomputing it from provider artifacts.

Provider transports are intentionally asymmetric because Coral records only what the provider reports:

- Claude print (`claude -p` stream-json) reports token usage and `total_cost_usd`, so Coral can render both tokens and `costUsd`.
- Claude TUI reports token usage from the transcript but no cost, so Coral renders tokens only.
- Codex reports tokens only, captured from the native `thread/tokenUsage/updated` notification (`tokenUsage.total`, a cumulative `TokenUsageBreakdown`). Its `cachedInputTokens` are a subset of `inputTokens`, so Coral subtracts cached input before storing fresh `inputTokens` and records cached input as `cacheReadTokens`; Codex has no `costUsd`.

Workflow usage is not written onto `workflow.completed`. It is aggregated at read time by summing child job `diagnostics.usage` rows where `projection_jobs.parent_workflow_job_id` is the workflow job id. Token fields are summed across children, including children that failed after spending tokens. Cost is summed only where present; mixed-provider workflows render partial cost as `$X+` with `(+N jobs without cost data)`.

User-facing usage surfaces are deliberately narrow. `coral-cli wait` appends usage only to terminal completion lines, with `--verbose` expanding the four token buckets. `coral-cli jobs detail <jobId>` renders the terminal diagnostics usage, and workflow detail uses the same read-time aggregate as wait. When cache-read tokens dominate the total, renderers add the honesty annotation `(NN% cached)`; detail uses the fuller cache-read annotation with `billed ~0.1×`.

`GET /jobs` accepts optional `projectRoot`, `phase`, `provider`, and `all=1` query filters. Without `all=1`, the list stays live-only (`queued`, `launching`, `running`) and remains sorted by `updatedAt` descending.

Error responses use real HTTP status codes: 400 (validation), 403 (scope mismatch), 404 (not found), 409 (conflict / non-resumable or provider-mismatched session), 503 (recovering / busy).

Accepted launches use explicit, discriminated identifiers. Provider launches return `{ kind: 'provider-session', jobId, sessionId, launchState }`; workflow launches return `{ kind: 'workflow', jobId, workflowId, launchState }`. Owner, binding, and workflow-lifecycle conflicts are typed 409 responses rather than opaque internal errors.

The provider-session branch of `LaunchDecision` has three answers: accepted (`running` or `queued`), `refused`, and `undetermined`; its workflow branch has no `undetermined` answer because workflow submission performs no provider preflight. The launch wire seam is the only place a status is assigned, and for provider preflight that status preserves the answer boundary: 503 means the answer was not established and the request may be repeated; 400 means it was refused. A preflight that returns no valid answer at all escapes instead as the internal fault `provider_preflight_faulted`, with HTTP 500 and CLI exit 70 — it is not a third undetermined cause. Who classifies what, and what counts as no valid answer, is in `docs/core-modules.md`; the operator-facing mappings are in `docs/cli-errors.md`.

`POST /kb/sources` accepts `{ filePath, slug?, readiness?, async? }`. It does not accept pre-staged markdown paths from clients. Source conversion, staging, persistence, progress, terminal outcome, and failure causes are coordinator-owned as an internal `kb.source_import` job. `readiness` defaults to `base-search` and may be `commit`, `base-search`, `active-vector`, or `all-equipped`; `async: true` returns 202 with the job id immediately, while the default waits for the requested readiness and returns 201 after the completed import.

`POST /kb/index` rebuilds KB text artifacts through an internal coordinator-owned `kb.reindex` job and waits for base-search readiness before returning. The job is recorded for recovery and observability, but it is not a provider/session job.

Raw work-directory spellings stop at transport ingress. Capability authorization happens before filesystem access; then Coral resolves the directory with `realpath`, rejects missing or non-directory targets explicitly, and authorizes resource binding against the canonical project root. Internal launch, workflow, recovery, provider-host identity, and displayed cwd values carry that same canonical value. A symlink and its target therefore identify one provider-server specification rather than silently creating separate hosts.

Reads of the shared KB Corpus (search, diagnose, note, source, wiki, community, and principle reads) name no project, because no project owns the Corpus: they are authorized by the `kb:read` capability alone, so a project-bound job child can search the KB it is granted without naming a root. The KB daemon canonicalizes a project root such a read carries but does not hand it to the handler. Memo and wake-up reads stay project-bound.

## Work Classification

Not every command becomes a job. Jobs are for work that is long-running, observable, resumable, or recovery-relevant. Immediate reads and small mutations remain direct commands.

| Class                     | Examples                                                               | Surface                                                             | Rule                                                                                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Direct read               | `kb read`, `kb principles`, KB metadata lists, `jobs`, `discuss watch` | Return result immediately                                           | No job id; uses `read-model/CoralStore` direct library reads. KB list/read paths do not persist derived rebuild artifacts.                                                             |
| Served read               | `kb search`                                                            | Return result immediately                                           | No job id; routes through IPC to the KB daemon's hot search runtime and never builds a library-direct lexical index.                                                                   |
| Direct mutation           | KB note write/delete; memo write/delete                                | Return result after the small write                                 | Corpus writes use the KB mutation lock. Memos are project-scoped scratch artifacts (under `runtime.paths.projectData(projectRoot)` — see design-rationale §5.3), not Corpus authority. |
| Provider job              | `codex`, `claude`, workflow/discussion children                        | Return job and provider-session ids; `wait` observes terminal state | User-facing provider work is Journal-observable and recoverable.                                                                                                                       |
| Internal coordinator job  | `kb source import`, `kb reindex`                                       | Default may wait; `async` returns job id                            | Used when source conversion, indexing, or readiness can take time.                                                                                                                     |
| Projection freshness wait | Active retrieval-consumer catch-up after Corpus commit                 | `ConsumerDriver.waitFreshUntil(...)`                                | Freshness wait is not itself truth; failure reports against the hosting command/job.                                                                                                   |

Every job has an `ExecutionOwner` independent of provider continuity. A direct provider job is owned by its `ProviderSession`; a workflow root owns itself; workflow children are owned by the workflow; discussion children are owned by the discussion; KB work is owned by a system task. Only provider jobs have a non-null provider-session id. Workflow queued wait events carry `workflowId`, and KB queued events carry `systemTaskId`, instead of fabricating `sessionId: ''`.

`kb source import` is job-backed because it can spend time reading and converting large documents before committing Corpus markdown. With retrieval readiness, it also waits for the applicable active retrieval consumers. By contrast, KB read/list commands, note write, memo operations, and principle reads are direct unless a future implementation gives them durable work to recover. `kb search` is a served read owned by the KB daemon, but it is still not a job. Direct list/read commands may build transient in-memory views, but explicit `kb reindex` owns durable text-artifact repair.

Direct does not mean ambient. CLI/bootstrap adapters choose the active plugin root, build flavor, project root, Corpus markdown root, and KB runtime root before calling KB/read-model code. KB path helpers and `read-model/CoralStore` do not silently fall back to the current working directory or the user's home KB.

## Primary Execution Flows

### Session lifecycle

1. `coral-cli codex -i ...` or `coral-cli codex <agent> -i ...`
2. The CLI client calls `POST /sessions`
3. The transport layer validates the direct body, builds `CallerContext`, and forwards a domain-shaped request into the coordinator
4. The coordinator API resolves agent intent, persists session continuity, and launches or resumes work through jobs-owned launch/admission contracts plus sessions-owned continuity storage
5. Provider adapters spawn the real CLI/runtime and emit progress
6. Journal appends publish projection freshness through the live `ConsumerDriver`; session continuity remains authoritative in the sessions shell

### Proxied provider execution

An app-server operation does not have to run inside the coordinator. When a live guardian/reaper/proxy set exists for the job's executable identity, the coordinator sends a strictly-validated, data-only prepared envelope and the **proxy runs the kernel in its own process** — which is the point: the carrier outlives a coordinator restart.

Publication is a durable saga rather than a returned transport result. Before each prepare send, the coordinator commits a `prepare-pending` record containing the exact attempt fingerprint. Proxy preparation and guardian authorization advance that record through explicit phases; only `operation.activate.v1` can start the kernel. A complete activation ACK then commits the `executing` phase and `job.runtime.started` in one SQLite transaction. Lost replies leave a named phase for `inspect.v2` and the reconciler to resolve, while `cancel.v2` can prove an attempt never started without reconstructing a reservation. **No operation is reported executing without both a real activation ACK and committed saga evidence.**

Events may be buffered after the kernel starts, but they cannot leave the proxy until the coordinator commits `executing + job.runtime.started` and attaches the operation to the current control epoch with `operation.attach.v1`. They then travel back over that connection as `provider.event.v1` — the one method in the protocol that runs proxy-to-coordinator. Each is applied durably by `applyProviderEventAtSeq` and acknowledged only after its transaction commits.

That makes durable-effect authority exclusive, and the two paths are kept apart structurally rather than by discipline: a proxied job returns from `executeJob` before the local consume/finalize path is ever entered, so the applier is the only writer. Running both would record every terminal twice.

The coordinator still owns what it is responsible for. `LocalOperationRegistry` holds each executing saga record, its stop capability, and exact proxy-binding cleanup identity. Admission itself issues one generation-bound `LaunchPermit` carrying reservation, job, pool, provider, holder, and acquisition time. Release accepts that permit rather than reconstructing authority from job and pool: a stale reservation reports `already-released`, a holder change reports `transferred`, and only the matching current permit returns capacity and admits the next queued launch. When a terminal or suspension commits, the registry routes binding settlement and process-local cleanup; the binding owner releases the exact permit. Without that path the durable state would be correct while finished work continued to hold launch capacity.

With no live set, the route returns explicit local authorization. Acquisition is deliberately fire-and-forget, so a cold start never waits on a proxy handshake.

### Provider-host serviceability and recovery

A provider host has three independent states. They answer different questions and must not be collapsed:

| State          | Vocabulary                                | Question answered                                      |
| -------------- | ----------------------------------------- | ------------------------------------------------------ |
| Process        | `open \| closed`                          | Is this concrete provider process present?             |
| Serviceability | `unknown \| serviceable \| unserviceable` | Has it produced typed evidence that it can serve work? |
| Admission      | `candidate \| blocked`                    | May fresh work be placed on this host slot?            |

This is intentionally not carrier-liveness vocabulary. Carrier observation asks whether work is still there; the incidents handled here involve a provider process that is present but cannot serve. Each new host instance starts at `unknown`, and `unserviceable` is terminal for that instance. Serviceability is derived only from a completed provider response. For Codex, a successful required `config/read` prerequisite is `serviceable` and its typed failure is `unserviceable`; unrelated responses remain `unknown`. A silent request and a host/process fault publish no response fact at all. There is no clock, elapsed-time comparison, retry count, or transport timeout that turns silence into a finding, so a mute host may remain `unknown` indefinitely.

A negative finding changes fresh-placement admission only. It does not close the process and does not gate exact attachment, because an already-running job still needs that attachment for provider interrupt and probe. If a blocked process exits naturally, its owner retains a `retired-blocked` tombstone with canonical non-secret metadata and bounded diagnostic evidence; the slot remains blocked. The only path that clears either blocked form is an operator eviction of the exact `HostRef`, after the owning process has closed that live host or confirmed the retained tombstone's process is absent.

Host ownership is process-local in two places. `DefaultProviderHostManager` owns coordinator-local hosts, while each provider-proxy process owns the hosts used by operations routed through that proxy. Both run the same admission model, but each performs its own placement and physical eviction. The RPC boundary performs capability and resource authorization before calling `ProviderHostAdministrationService`; the service itself receives no principal. It captures the current owner set and, for exact-reference eviction, first asks every owner whether it retains a terminal disposition for that reference. One match reconstructs the route and replays the eviction through that owner; no match falls through to complete-inventory selection; multiple matches are identity corruption. An unavailable owner fails the whole request, so neither discovery nor inventory selection can silently omit part of the federation. `--work-dir` is only a convenience resolver over complete inventory: it is canonicalized relative to the CLI invocation root and refuses zero or multiple matches rather than guessing. See [Configuration](./configuration.md#provider-host-recovery) for the operator commands.

Host compilation receives its placement's bundle directory explicitly. Proxy placement captures the
coordinator's running bundle directory and keeps its running entrypoint, including `clients/build` in
development builds. The coordinator and proxy compile Claude's broker path from that same root. A refused
proxy placement recompiles for local execution. Codex's external executable has no bundle-relative spec
path. The custody wrapper is selected at physical spawn and is outside the host fingerprint. See
[Provider proxy operations](./provider-proxy.md) for the activation identity checks and upgrade cleanup.

Containment follows those two ownership boundaries but shares one low-level primitive. It exists because a provider can leak its own children: a codex app-server spawns MCP servers per thread and does not reap them when those threads end ([openai/codex#30408](https://github.com/openai/codex/issues/30408), open). Coral cannot repair lifecycle ownership inside codex, and it never attributes a descendant to a session — codex itself does not track which MCP belongs to which thread, so any such attribution would be resemblance rather than identity. Containment instead reclaims by group at host teardown, which needs no descendant enumeration. Provider-host admission requires both a supported POSIX process group and a process-incarnation probe, including on Darwin and Linux. The provider server is spawned `detached`; before the entry becomes live, the coordinator reads the child's process incarnation, proves `kill(-pid, 0)` can address the new group, and records `{ pid, incarnation, processGroupId: pid }` on the entry. Either identity check failing kills the child and refuses admission. Teardown uses `reapRecordedContainment`, which revalidates identity before SIGTERM→SIGKILL escalation and stable absence observation. A signal requires either retained live-child authority or an authoritative platform identity match; Darwin record-only teardown therefore refuses to signal and retains a visible cleanup hold. That check is fail-closed rather than exhaustive: if the leader PID has been recycled, Coral still probes the numeric group to distinguish absence from a surviving or unobservable group, but it never signals that group because ownership can no longer be proven. Surviving members of the original group may therefore remain. The guarantee is never to signal the wrong group, not always to reap ours. The provider proxy uses the same primitive at proxy-set teardown. Its app-server is deliberately not detached again; per-host close signals only that child, so leaked descendants can remain inside the guardian-established set until set teardown. A custody wrapper owns SIGTERM→SIGKILL escalation for its actual app-server through `gracefulKill`; its parent never hard-kills the wrapper during that escalation. Private IPC carries the actual-child identity and cessation receipt. Wrapper disappearance alone cannot discharge host retirement; if the wrapper exits first, automatic cleanup retries observe and reclaim only the recorded provider incarnation. Sibling hosts share the proxy group and are never per-host signal targets.

Pins, not job counts, authorize idle retirement. Each `ProviderHostEntry` keeps a `Map<PinToken, ProviderHostPin>` whose acquisition and attached-session pins carry origin metadata and are released by idempotent closures; `activePinCount` is the map size. For shared hosts, `idleRetirement` names the condition: `'unleased'` permits retirement after the last pin releases, `'unleased-and-host-idle'` additionally requires an idle `host/stats` report, and `'never'` retains the host until explicit shutdown. Codex uses `'unleased'` because Coral's pin ledger sees its work. Claude uses `'unleased-and-host-idle'` because its broker multiplexes sessions that the pin ledger cannot see; `host/stats` is emitted by that Coral-owned broker, not by the external codex app-server. A diagnostic names every outstanding pin when no live Codex job owns the host, but never closes on that observation: an attached-session pin has no job id, so zero jobs does not prove zero attachments.

Completed-response diagnostics retain the typed RPC result and the sequenced host-log interval occupied by that request, with explicit truncation markers. This separates a call's cause from accumulated process stderr and keeps the same evidence available after a blocked host retires. It does not repair either upstream root cause: provider-side resource exhaustion can still make a host mute, and provider per-cwd state can still reject `config/read`. Coral now makes both incidents scoped, diagnosable, and recoverable without restarting the daemon or disturbing unrelated hosts.

Codex job outcome and provider cessation are separate observations. A final answer uses the passive 250 ms completion inference, with errors vetoing inference and pending collaborations or subagent turns suppressing it. Inferred output records the same successful answer as explicit completion. For proxy-owned inferred turns, a provider settlement capability retains the notification subscription and managed host lease after the output stream ends. Release accepts a late exact `turn/completed` or a validated terminal status for the exact thread and turn from `thread/read` with `includeTurns: true`. Re-observation uses one two-second elapsed timer across reads and paced 250 ms waits; wall-clock corrections cannot extend it. Only a turn still reported `inProgress` after that bound receives an exact cleanup interrupt, followed by a bounded terminal-confirmation wait; cleanup cannot replace the recorded job outcome. Unknown state authorizes no interrupt or release receipt. The supervisor's existing one-second release retries repeat observation; three unconfirmed attempts enter the existing containment successor, which retains live siblings and relinquishes only after their settlement or cancellation. Both the execution and staging cleanup promises remain joined throughout.

### What a coordinator restart does to a running job

This is the question proxied execution exists to answer. Clean shutdown only relinquishes control sooner; it does not create recoverability.

A fresh set receives one exact-set recovery credential before it becomes visible to routing. Guardian, reaper, and proxy retain the credential digest; the protected mode-0600 capsule retains its secret. Every operation is registered into the set's succession membership before prepare, so the durable journal always names work a successor can recover.

After either graceful control release or an abrupt transport loss, the successor computes the capsule address from the operation identity and set locator in the saga journal, redeems the set in guardian → reaper → proxy order, and registers the recovered set before resolving any individual operation. Each `executing` row is independently attached at its durable watermark; the other phases resume their phase-specific reconciler work. An indeterminate `operation.attach.v1` outcome is retry-safe and cannot authorize set reaping; `control_client_closed` and malformed unattributable frames are narrower channel incidents and cannot enter the terminal-fault union. Heartbeats use the transport's closed `ControlExchange` directly. `provider-proxy/heartbeat-observation.ts` alone decodes that exchange into a branded reply, no-response, locally-unsent, delivery-unconfirmed, or channel-fault observation. A timeout or close after write is retryable no-response evidence; a socket error after write is delivery-unconfirmed, a local-failure outcome that cannot advance a peer-silence window. Request encoding and synchronous write failures are locally unsent and likewise cannot enter that window. A well-formed but unusable reply remains answered evidence and can only reach the coordinator's separately bounded independent-absence containment wait. That wait does not send the destructive control RPC; once both enforcers are proven absent, the read-only containment prover returns the recorded targets and the provider-proxy-set lifecycle reaps the orphaned proxy group through `reapRecordedContainment`. Only the endpoint's complete JSON-RPC `invalid_request` refusal shape can name `teardown-latched` as terminal. If an accepted echo's response was lost, the endpoint returns `heartbeatRefusal: challenge-mismatch` plus a fresh `nextHeartbeatChallenge` on the tenancy's own socket, allowing the establish retry or next periodic tick to resynchronize without treating the mismatch as displacement.

An unconfirmed operation cancellation closes admission for its entire proxy set and retains the unresolved operation. Already-running siblings drain through supervisor release after coordinator settlement before the proxy relinquishes control and exits; another unconfirmed sibling cancellation removes that sibling from the drain obligation. The enforcers then own set retirement. No new operation can reuse the unsafe host while siblings finish.

Ambiguous redemption failures and retry-safe attachment failures remain retryable; a transport error is never translated into operation absence. A typed teardown-latched inheritance refusal enters exact containment observation and recorded reaping. Inconclusive observation, declined reap authorization, and publication that was not attempted retain durable retry ownership instead of stopping the coordinator. Identity or operation-membership disagreement remains fatal. Only a typed `operation-absent` proof resolves that exact `executing` row as provider-lost. If exact containment disappearance is proven instead, each saga phase follows its own durable outcome: prestart phases complete local placement or their terminal directive, ambiguous activation terminalizes without fallback, executing terminalizes without re-execution, and settlement deletes its already-terminal tombstone.

Every mutation control policy declares how an indeterminate outcome affects supervision. `operation.attach.v1`, `operation.settle.v1`, and `operation.stop.v1` are retry-safe and stay on the non-consuming incident channel. `operation.prepare.v1`, `guardian.operation-activate.v1`, `operation.activate.v1`, and `operation.cancel.v1` require containment and may consume the terminal authority-fault latch. Heartbeat silence stays on that same incident channel; an accepted echo revives the lease even after its clock window. The enforcer's own tick classifies the admitted control holder `alive | absent | unobservable` from a recorded-process observation and mints a demolition capability only on proven `absent`, never from elapsed time alone; the coordinator's bounded silence hold joins its two siblings on the non-destructive `await-containment-absence` action instead of starting a destructive attempt by itself. Control-channel close and invalid-unattributable-frame observations stay on the incident channel regardless of the interrupted method.

A channel incident moves the established slot to `reattaching`, removes its route immediately, stops the displaced generation's heartbeats, and leaves durable claims attached. This is not heartbeat silence: it has its own first monotonic observation and one absolute adoption-window deadline. Each attempt runs authenticated three-role redemption beside independent containment proof. A branded success rebuilds the complete operation authority before it is promoted, restores the prior `available` or `draining` state, restores routing only for `available`, invalidates old callbacks by attempt token, and notifies establishment so live operations reattach to newly built controls. Refusal stops redemption immediately; unavailability may retry only inside the original bound. Refusal and expiry both enter `await-containment-absence` without calling `stopAndReap`; after guardian and reaper are both proven absent, the read-only prover supplies the exact recorded targets and the lifecycle reaps the orphaned proxy group before entering the existing disappearance-delivery path.

After the recorded monotonic adoption-window deadline, the channel hold continues as an automatic durable retry.
Control reattachment and independent containment observation remain the only exits; confirmed absence enters the
ordinary disappearance path, while observed-live and unobservable enforcers keep the representation held. The
retry cadence is at most 60 seconds, and `backend status` reports the current bound, retry disposition, and exit
without offering containment or abandonment as a reader decision. When an automatic disposition cannot proceed,
status names the missing evidence and stops there. A local unreadable-row fence cannot be overridden. Ordinary
shutdown remains handoff and reports every decoded set token plus whether its best-effort inventory was complete.
A fault-driven `containing` or `containment-wait` hold uses a fixed 30-second containment-attempt observation gate
instead of the configured adoption window. The forced route signals the
recorded proxy process group and every recorded provider root for the set that is observed present through
`reapRecordedContainment`. Guardian and reaper are never signalled; successful containment requires both to
have been observed absent, while explicit abandonment may leave either live because it sends no signal.

Each role and method has one exclusive heartbeat evidence window: `clear | silence | answered-unusable`. An unusable answer replaces silence with a fresh answered-unusable window; a later no-response replaces answered-unusable with a fresh silence window. Accepted echoes and current-tenancy resynchronization clear either prior state. The shape therefore cannot retain a stale silence timestamp beside answered evidence. The guardian and reaper each hold an armed enforcer. Before publication, no operation authority has been returned and no claim can exist, so the tick lets the pure clock bound decide even when an installed provisional holder is unobservable — the one place elapsed time alone still authorizes teardown, and nothing is at risk when it does. Once a holder is published, that adoption deadline no longer latches teardown on elapsed time: `createArmedEnforcer`'s tick (`src/provider-proxy/enforcement.ts`) instead classifies the admitted control holder `alive | absent | unobservable` from a recorded-process observation, renews the check on `alive`, holds on `unobservable`, and mints a demolition capability only on proven `absent` — `buildDeadlines` (`src/provider-proxy/role-main.ts`) is constructed only inside `startProviderGuardianRole` and `startProviderReaperRole`, never `startProviderProxyRole`, so no enforcer exists to observe holder absence for the proxy's own `control.heartbeat.v1` hold at all. Where an enforcer does exist, it is anchored on its own role's round-trip evidence: the guardian's `adoptionDeadline()` advances on the coordinator's heartbeat _to the guardian_, a channel independent of the coordinator's heartbeat _to the proxy_, so a coordinator starved specifically toward the proxy — while the guardian and reaper keep answering normally — never reaches that deadline either. A containment-required control call against the wedged role reaches `faultAuthority` through `routeControlCallFailure`'s `requires-containment` policy independently of any of the above, but only if some operation attempts one; a job already `executing` and merely waiting attempts none. `containment-proof` is not itself a trigger: it is the absence half of a containment attempt already started. Silence containment runs it beside `role-control`'s `stop-and-reap`; answered-unusable exhaustion and `method_not_found` run the independent proof without treating the answering roles as custody of the set. `coral-cli backend shutdown` reaps a live set only in `shutdownModeFromReason`'s hard mode, and this command never reaches it: both its IPC dispatch (`transport/ipc/server.ts`) and its HTTP handler (`transport/http/handler.ts`'s `/admin/shutdown`) hard-code `reason = 'replaced'`, which maps to handoff. Handoff calls `releaseHandoffAuthority` instead, preserving the set for a successor to redeem rather than ending the hold — so running this command against a live, wedged set hands the same wedge to the next coordinator rather than closing it. Ending one exact held set is `coral-cli backend provider-proxy-set contain <pps1-token>`, which is deliberately a separate operation: a routine restart must not reap live provider work. Hard mode is real and does reap every live set, and in production exactly two reasons reach it: `sigint`, from `createCoordinatorShutdownSignalHandler` (`src/coordinator/bootstrap.ts`), and `idle`, from `IdleTimer` (`src/coordinator/live/idle.ts`); the union's only other hard member, `test-teardown`, has no production producer. An internal provider-proxy lifecycle fatal takes handoff, preserving live sets for successor recovery rather than destroying them on the failing coordinator's judgement — see [Shutdown settlement and what the process leaves](#shutdown-settlement-and-what-the-process-leaves).

The provider-proxy reducer separates silence from an answer this build cannot use before coordinator policy sees either. After `heartbeatHoldBound.spanMs` of continuous silence without material scheduler starvation, `heartbeat_hold_exhausted` joins its two siblings on the non-destructive `await-containment-absence` action rather than `stop-and-reap`: with zero live claims the coordinator stops heartbeating, closes control, and waits for independent containment absence, exactly as `heartbeat_answer_unusable_hold_exhausted` already does. With live claims present none of the three heartbeat sources may authorize destruction on their own; the coordinator instead records a held, non-authorizing disposition and keeps the route and heartbeat loop running. After both enforcers are proven absent, the read-only prover supplies the exact targets and the lifecycle reaps the orphaned proxy group. A decoded `method_not_found` clears the prior window, skips timing, and takes the same `heartbeat_protocol_incompatible` containment path. Neither path treats a role ACK or owner label as discharge. The heartbeat loop records `observedWake − requestedWake` on the monotonic clock and carries that delay beside the branded observation for its exact role and method. The observation that opens a window contributes no accumulated lateness because the window begins at that observation; only later observations add `schedulerLatenessAfterFirstObservationMs`. `providerProxyHeartbeatHoldBound` derives the span and material-lateness threshold from per-set timing — resolved configuration for fresh acquisition or the redeemed capsule for an inherited set. The threshold is one quarter of the span, requiring at least three quarters of a candidate window to remain attributable to heartbeat work. Reaching it resets that evidence window. At the default timeout the span is 23 seconds and material lateness is 5.75 seconds. The enforcer and coordinator window share a formula and monotonic instrument, but not an anchor or an ordering; an endpoint may accept an echo whose reply the coordinator never receives. Human-readable `unanswered`, `unclassified`, and `method-not-found` labels are derived only after the reducer transition and never feed policy.

**Across builds.** A host's build is immutable provenance; its processes keep running the plugin root they were spawned from, because `coordinator/live/provider-hosts/host-root.ts` captures the coordinator's own running bundle and entrypoint at world assembly. Transfer requires that build's installed root to remain available and manifest-valid. Which build controls the set is a separate fact each role records per admitted holder (`createControllerBuildLedger` in `src/provider-proxy/controller-succession.ts`), and a recovery grant names the controller build that may redeem it. A successor of another build redeems only after the incumbent authorized it: during prepare, the `provider-proxy-sets` and `provider-operations` succession owners ask each serving host, through `guardian.controller-transfer.v1` and `controller-transfer.v1`, to accept that one successor build for this attempt, and the receipt names every transferred set, job, and recovery grant. The incumbent drops control only at commit, after its writer is parked, and reclaims it through its own grant if the commit fails. The successor redeems at startup, attaches each transferred job at its watermark instead of finalizing it as interrupted, and installs its own grant only after it serves (`createProviderHostTransfer` in `src/coordinator/succession/provider-host-transfer.ts`). A host that answers `method_not_found` predates controller succession; it, a successor whose capability file lacks the host control generation, a store-format change, and any job without a durable saga record answer `blocking` and follow the deferred path. Because a launch waits for a proxy set to be acquired before it falls back to a coordinator-local host (`awaitAppServerOperationRoute` on `DefaultProviderHostManager`), coordinator-local provider work is the exception rather than the first job's default.

One recovery consumer seam is a deliberate exception to that separation. Capsule discovery at boot can meet a handoff capsule this build may not dial — an earlier bundled build's, left by a rollback, an upgrade, or a reinstall — and retiring one is a boot's housekeeping rather than a claim on any authority, so on the `foreign-capsule-retirement` seam every producer disappointment reaches the incident channel and none reaches the global fatal sink. Three things can end an attempt short of retirement: the producer reporting the capsule directory not durable, a rejection carrying a filesystem error code, and a fulfillment the producer's own outcome schema refuses. All three are owner-local and retryable, the reported incident kind distinguishes them, and it carries an operating-system code wherever one could be read. The retry is bounded at five attempts and the last failure reaches a named terminal rather than another wait: the retirement owner is dropped, the capsule keeps the conservative representation installed for it for the rest of the boot, and a later boot retries it from discovery while it stays readable. Abandoning that hold on a count is only sound because the owner holds a path and nothing else — no acquisition capacity, no claim, and no absence slot — so dropping it strands nothing.

Representation release — the delivery of a disappearance or abandonment notice to the provider-operation consumer — is retried at a fixed one-second cadence under a 60-second settlement bound while its representation slot exists. The bound belongs to the slot rather than any delivery and is armed once when release begins, so a delivery that never settles expires it just as a delivery that keeps failing does. Expiry releases the slot: capacity, the mutation fence, the route, and the in-memory operator dispositions all go, and the hold settles as `released-undischarged` rather than as a success. Nothing durable is written by delivery. The settlement derives its one witness from what remains: an operation still pending at the bound stays on its provider-operation record, and an empty operation set means only the handoff capsule remains to be retired. `ProviderOperationReconciler.reconcile` parks a latched `ready` notice after the slot is gone; it does not start a live re-attempt.

A failed release delivery does not mutate the provider-operation record. The delivery disposition is already decided before any such bookkeeping could run, and a store lock that caused terminalization to return retry-safe can also refuse an accounting write; letting that second refusal escape would upgrade the decided retry into a fatal. Avoiding the write also leaves a `provider_host_unserviceable` record describing the host refusal its terminal still consumes instead of incrementing a retry count beside stale evidence. The release failure is reported once when the slot's initial disposition enters `operational-retry-owned`; expiry later reports the distinct `released-undischarged` transition. For disappearance, terminalization settles the binding and releases startup ownership before the dispatcher turn, so the parked record keeps neither serializer `inFlight` nor recovery ownership. With no other active work the idle timer retires the coordinator, the next mutating command starts a successor, and startup re-derives absence through `reconcileAtStartup` → `recoverSetAtStartup` → set inheritance → `containment-disappeared` → `containmentAbsent` → the disappearance consumer. Abandonment is different: it is a decision represented only by the in-memory latch and is not re-derived at startup. Its durable `controlIntent` form is deferred in [`representation-release-notice-as-a-durable-phase`](./todo/representation-release-notice-as-a-durable-phase.md).

The lifecycle emits one pinned log record before route removal, heartbeat shutdown, containment, or reaping. Its base message body and field order are exactly `Provider proxy set action=<action> reason=<reason> fault=<kind|none> subject=<role|method|retirement> liveClaims=<n> set=<key> error=<formatted|none>`. After the evidence-window transition, heartbeat records derive `incidentReason=<unanswered|unclassified|method-not-found>` for preserved or protocol-incompatible decisions, `terminalReason=<teardown-latched|local-failure>` for the endpoint's own decisive refusal or this process's locally unsent call, or window evidence as `attempts=<n> elapsedMs=<n> schedulerLatenessMs=<n> lastIncidentReason=<x>`. A channel-reattachment record instead appends its exact `cause=<closed|invalid-unattributable-frame>` and `attempts=<n> elapsedMs=<n> boundMs=<n>`. Coalesced preservation records may then append ` summary=<kind> suppressed=<n>` after that base. `/health` and `backend status` use the existing per-set disposition for active heartbeat holds, channel-reattachment holds, and containment waits. While reattaching, that disposition carries the exact set, triggering role and cause, attempts, elapsed time, absolute-window bound, and live claim count; refusal or expiry replaces it with an awaiting-absence disposition naming which outcome ended reattachment. The entry is removed when the slot is discharged, so completed sets do not accumulate in coordinator-lifetime history. The logging intent is INFO for expected preservation and retirement decisions and WARN for authority loss, hold exhaustion, and protocol-incompatible containment; an authority-loss message's own `set=` reference is shared with the corresponding job terminal message for correlation. Slot removal accepts only the lifecycle's opaque combined discharge: branded process-containment absence plus branded durable-claim discharge. A zero-claim set mints the claim half only after rechecking the claim mirror, and a claim-bearing set mints it only after every disappearance delivery is accepted. A claim-bearing retirement records `drain` first and, only after the claim count reaches zero, records a distinct zero-claim `stop-and-reap` transition.

Every saga row, including `executing`, is excluded from generic carrier recovery. Startup and control-established workers select the reconciler phases, active proxy deadlines drive remote release, and exact disappearance provides the phase-specific final exit.

### Upgrade succession and administrative shutdown

#### Request and deferral

A newer same-flavor build records an upgrade request only when it strictly outranks the serving build. The incumbent keeps serving while any owner cannot complete or transfer its obligations. The request remains visible with its blocker and the event that prompts another attempt. A shipped incumbent may first retire through its normal idle exit; a newer contender does not stop it. A corrupt request record is quarantined durably after any active attempt exits, and the next recorded request can proceed.

#### Supervisor recovery

One namespace supervisor holds the data-free `namespace-supervisor.v1.lock`, owns coordinator launches, and keeps reservations, heartbeats and termination commitments in memory. Each child acquires its independent data-free lifetime lock at `launch-lifetimes.v1/` before publishing `launch-admissions.v2/<id>.json` or entering startup effects. The lifetime address preserves the authenticated child and parent identities, build, purpose and original admission time. Its boot-clock admission reading preserves elapsed startup budgets through takeover and wall-clock adjustments; successful TERM delivery starts a monotonic KILL grace. Discovery projects that same time and adds `supervision`; it does not remove the admission. The child removes its JSON on normal exit and retains its lifetime descriptor until process exit. After independently proven abrupt exit, the namespace lock holder cleans leftover JSON and lifetime evidence against the same subject and device/inode, including corrupt JSON, and retries failed cleanup. An unreadable admission remains a visible hold while its addressed lifetime lock is held or unobservable; the namespace owner cleans it when the same lock inode is provably released, or its lifetime hierarchy is absent. Conflicting envelopes and incomplete first-acquisition evidence remain guarded. Unknown occupancy prevents new launches, while retirement of a fully identified expired child depends only on that child's evidence and current namespace authority. Branch-only pre-lifetime `launch-admissions.v1/` records are ignored and left untouched.

A lifetime pathname can appear before its first shared acquisition completes. Exclusive acquisition on that inode alone cannot prove a completed lifetime ended: a positively live child remains occupied, and unknown identity keeps a visible acquisition-window hold. The probe is released promptly so the child can acquire. Settlement requires authenticated completion evidence followed by decisive lifetime release, or independent exact-child absence. A replacement reconstructs admissions, lifetime subjects, discovery and `upgrade.v1.json` without renewing startup or attempt deadlines. Remaining live inherited or unknown subjects prevent ordinary reservation. Actual memory changes from `recovering` to `supervised` when custody-preserving serving restores parenthood for every remaining child, or when all subjects are decisively settled and no live or unknown occupancy remains; empty recovery normalizes before reservation. Intent-only incumbents without authenticated admission provenance stay passive: neither termination commitments nor signals are permitted. If the sole observer of a shipped incumbent dies, the next CLI or hook `ensure` resumes its recorded upgrade; no guard process is added, and the incumbent retires naturally.

A parentless coordinator nominates a replacement and keeps serving. On Linux, parent silence beyond the heartbeat lapse permits guarded TERM then KILL after grace: before each signal, `process.ppid` and a fresh incarnation probe must still match the authenticated admission parent tuple. Unknown identity refuses visibly and retries against that retained tuple. On macOS, permanent parent silence is an accepted availability limit: a visible `parent-silent` hold, continued coordinator service, and upgrades waiting for the parent to exit. A wedged inherited macOS child likewise remains held. An accepted replacement is monitored through fresh sequenced private control responses independently of bridge readiness until actual normalization. On Linux, sustained control silence permits guarded retirement of that exact direct child, followed by retry only after proven exit and actual namespace-lock release. Responsive accepted owners waiting for child health remain protected; surviving admissions stay occupied.

`launch-status.v1.json` is diagnostic and never authorizes boot, reservation or signals. The retained `launch-status.v1.lock` directory and owner/claim markers serialize only publication. Unreadable access, malformed marker populations, contention or timeout retain current holds and a visible publication-failure disposition in memory, exposed through serving status. Paced automatic retries durably republish the holds when access recovers without stalling requests or adding a durable fallback. A possibly owned serialization directory is never quarantined to force publication.

`coordinator-launch/controller-build.ts:controllerBuild` compares v2 proxy start times in the shipped capsule's seconds encoding: a mismatch excludes the recorded proxy, without signalling the reused PID. Unreadable capsule or custody artifacts and unobservable proxy identity cannot choose a build. `candidate-selection.ts:selectNextCandidate` allows a two-second monotonic grace for refusal-only uncertainty, then selects from the readable evidence alone. After that grace expires, a readable capsule or completed serving receipt still requires its build, including when that build is unavailable; the original candidate launches only when no readable requirement remains. Outside that expiry path, a completed receipt adds a candidate without constraining selection; readable live capsules still require their controller build. Conflicting readable requirements and indeterminate live served-transfer evidence retain the existing hold and do not start that grace. Every return retains collected capsule and custody refusals. Refused artifacts remain untouched and visible by path in `controllerEvidenceRefusals`, with one event per observation change. Readable live capsules retain controller-build selection authority. Startup capsule discovery refuses each unreadable candidate independently; affected work still passes through the existing recovery ownership and settlement gates, so a refused capsule never proves process absence.

Controller evidence refusals carry an additive `observedAt` timestamp. Health preserves this timestamp, and `backend status` renders retained refusals as dated history whose current readability may have changed; older records without a timestamp render as history with an unknown observation time. Retaining a refusal does not assert that the path is still unreadable. The additive `evidenceGraceMs` diagnostic describes selection after the refusal grace; readers continue to accept older `boundedExit` observations.

`backend status` preserves the observed service state and exit code when it adds historical upgrade refusals. Launch observations read from disk retain persisted provenance; they establish no retry owner and do not suppress startup guidance. Automatic retry claims require an authenticated current owner's launch report.


The launch lock carries no data. A malformed lock address — bytes SQLite cannot lock, a directory, a symlink, or a second hard link — is moved aside to `namespace-supervisor.v1.lock.malformed-<ts>-<uuid>` only after `repairMalformedFileLockSync` (`src/infra/fs-lock.ts`) proves no process can hold it, and the path is then recreated. A live holder is left in place, because a lock binds its inode and moving a held inode would create a second lock at one address. A socket bound before any discovery record names nobody, so the supervisor writes no upgrade request for it; it keeps that observation in memory and records the request with the real incumbent identity once `coordinator.json` publishes one.

#### Commit window

The incumbent prepares every owner before pausing new top-level launches. Each commit pause lasts at most five seconds, with at most fifteen seconds of pause in a rolling minute. Accepted work, reads, waits, and cancellation continue. Immediately before a commit, owners that cannot transfer are checked again. A failed attempt cannot take the writer generation or publish serving after the incumbent reclaims it.

#### Handover

The incumbent forwards new and existing connections while the successor accepts the complete address claim set, so no released bind gap invites another coordinator. The successor proves its exact store epoch, writer generation, custody receipt, and serving state before the incumbent releases accepted carriers. Compatible provider hosts transfer control without restarting their processes. Administrative shutdown remains a separate authenticated HTTP operation; IPC replacement shutdown is refused.

#### Failure disposition

A failed attempt is reaped or proven absent before another launch can use its slot. Startup resolves a recorded incomplete attempt before ordinary build selection; bounded startup patience eventually abandons an undecidable attempt and returns to service with the upgrade deferred. A live attempt remains held until its exit is known. Superseded epochs and historical results remain addressable until their independent closure and retention requirements permit reclamation. The source owners for these protocols are listed in [Core modules](./core-modules.md).

### Shutdown settlement and what the process leaves

A shutdown releases what this coordinator holds and exits; it never destroys on its own judgement, never waits for what it cannot end, and everything it leaves is either owned by a durable successor or named as lost — in the type, in the exit code, and in one record. No operator is watching ([`design-philosophy`](../.claude/rules/design-philosophy.md) §12), so every hold below names the event that ends it, and that event is produced by this process.

**Reason → mode.** `ShutdownReason` is a closed union owned with `shutdownModeFromReason` by `src/infra/shutdown-contract.ts`: `replaced`, `sigterm`, and `provider-proxy-lifecycle-fatal` take handoff; `sigint`, `idle`, and the test-only `test-teardown` take hard. The mode is not why the process exits but whether it may execute destruction on its own judgement. Hard mode reaps live sets, terminates children, and marks crashed jobs; handoff releases authority and leaves every set for a successor or its enforcers. A fatal is the state in which this coordinator's judgement is void, so it takes handoff. The lifecycle single-flight state owns the active reason and pending incidents as well as the promise: a fatal outranks any in-flight or retained-retry reason, aborts an in-flight hard consequence, is entered into the same ledger, and switches all remaining mode-specific work to handoff. Lower-precedence requests do not relabel the active drain.

The handoff drain budget is `HANDOFF_DRAIN_TIMEOUT_MS` in `src/infra/shutdown-contract.ts`, shared by coordinator shutdown and IPC transport.

**The ledger.** `SettlementLedger` (`src/obligation/settlement.ts`) runs each `SettlementObligation` exactly once; a declined obligation is never re-executed. The authority-release boundary, `buildAuthorityReleaseBoundary` (`src/coordinator/shutdown.ts`), is the only producer of a hold: its prepare/commit transfer is attempted through `attemptBoundaryTransfer` at most `BOUNDARY_TRANSFER_ATTEMPT_LIMIT` times, and the third declined transfer becomes a named `process-exit` loss and a terminal rather than another hold. `gate` is the sole disposition constructor and the only return of the shutdown sequence, so a hold can never flow out through a success-shaped value.

**Two remainder owners, no third.** Every obligation declares in its type who owns whatever it leaves (`UndischargedRemainder` and `SuccessorRecoveryEvidence`, `src/infra/shutdown-contract.ts`), read at the moment the obligation settles. `process-exit` means this process names the loss: completion was not proved, process death is the mechanism that releases what was held, and the record is visibility, not a claim that exit performs the unfinished cleanup. `successor-recovery` carries typed evidence naming the mechanism that will pick the work up — `startup-adoption` with the retained child list (job id, `DurableCliRuntimeRecord` pid, leader incarnation per child), `startup-store-recovery`, or `startup-liveness-recovery` — never a free-form string, and never `none`. Child termination is two ordered obligations along the seam inside `LaunchCoordinator` (`src/coordinator/live/admission.ts`): `settlePendingLaunches` first, whose still-pending launches (no wrapper identity yet) are `process-exit` losses, then `terminateRegisteredChildren`, whose remainder is derived from the disposition its task observed under the every-child rule — `successor-recovery` only when every retained child is `durably-published`, the state `publishWrapperSpawned` (`src/coordinator/live/durable-transport.ts`) latches after the runtime record commits; any unpublished or unobserved child makes the whole obligation `process-exit`, with each child's publication state named in the settlement detail. The wrapper finalizer is the child's enforcer, just as proxy sets under handoff are owned by their enforcers in prose; custody is evidence for the durable successor path, not a third ownership axis. An under-claiming aggregate is the §11-safe one.

**Who owns each obligation's remainder.** Each row is what the obligation's own `remainder` thunk in `src/coordinator/shutdown.ts` answers, read at settlement. `process-exit` is the conservative answer and is chosen wherever completion has no successor-readable receipt; `successor-recovery` is claimed only where the successor re-derives the work from durable truth without consulting anything this process leaves behind.

**The terminal and the exit code.** `LifecycleShutdownTerminalDisposition` (`src/coordinator/lifecycle.ts`) is `finalized` or `finalized-with-losses`, and `isLifecycleShutdownTerminal` is the single predicate that separates those two from the sole live `held` arm of `LifecycleShutdownDisposition`; a terminal with losses stops retries, runs cleanup, and offers no abandonment. At the ledger boundary, a prepare or commit refusal produces `GateResolution.held`; final exhaustion or a successful commit produces `GateResolution.terminal`, and remainder acceptance is attempted only for that terminal outcome. The exit code is `0` iff nothing was left, otherwise `1`, contributed through `recordExitCode` (`src/coordinator/bootstrap.ts`), which keeps the maximum of every contributor so an earlier repeated signal is never lowered by a later clean ledger. The bootstrap probe exit gate, `createBootstrapProbeExitGate`, bounds its probe cleanup by `SIGTERM_GRACE_MS` and exits after that grace whether the cleanup held or rejected: the probe is observation-only, so it holds nothing exit would betray.

**The remainder record.** `recordShutdownRemainder` (`src/coordinator/shutdown-remainder.ts`) writes on every shutdown, including a clean one whose entry list is empty, to one address (mode `0o600`) in the run directory: `SHUTDOWN_REMAINDER_RECORD_NAME` (`src/infra/shutdown-remainder-record.ts`), derived from `SHUTDOWN_REMAINDER_RECORD_VERSION` so the generation has a single owner. The record carries its own `instanceId`, so the address does not need to; a later coordinator's losses replace an earlier coordinator's, and the reader scopes by the `instanceId` and `recordedAt` inside the record rather than by a filename. Before the final rename it uses a writer-owned stage whose name extends the record path with the coordinator pid and a digest of the boot-memoized process incarnation. If no probe succeeded during the process lifetime, the stage name carries `unobserved`; the record is still written because losing the obligations is worse than leaving a stage nothing reads. It creates the run directory itself, because the non-durable `writeAtomicSync` it uses intentionally does not (`docs/design-rationale.md` §12.5), and it removes both of its stage forms if a handled write or rename failure occurs — that cleanup swallows its own errors so the originating failure is what the caller receives. It writes before `removeBackendInfoIfOwner` (`src/infra/backend-discovery.ts`) withdraws the discovery address others use to find this coordinator, so a reader can always learn what was left before the address that named this instance disappears; a refused withdrawal folds itself back in as one more named loss and forces exactly one more write to the same file, and exit is requested regardless. A refused _write_ is only logged — it changes neither the exit code nor the disposition, so losing the record itself never blocks exit. Each entry is keyed by the ledger's own obligation `label` (`docs/design-rationale.md` §12.4) and carries a `remainder` and a `settlement`; `shutdownRemainderEntrySchema` and its settlement vocabulary (`src/infra/shutdown-contract.ts`) define the exact values either may hold, while `src/infra/shutdown-remainder-record.ts` adapts that contract to the durable envelope and file classification.

**Reading the record.** `classifyShutdownRemainderFile` (`src/infra/shutdown-remainder-record.ts`) opens that one address and answers with exactly one of five classifications: `vanished` (nothing is there), `corrupt` (bytes were read but are not JSON, so every build would reject them), `unsupported` (JSON was read but this build's schema rejects it), `unreadable` (no byte reached this build), and `readable`. A target-following `ENOENT` alone does not prove absence — a dangling symlink answers that way — so `vanished` additionally requires the lexical directory entry to be absent; an `ENOENT` read behind an entry that is still there, or one whose own `lstat` could not answer, is `unreadable`. Nothing enumerates the run directory and nothing deletes: a writer-owned stage is at an address no reader derives, so a stage a writer crashed before renaming is never read as a record. Nothing reclaims that stage either — `ProcessIncarnation` distinguishes pid reuse, so the pid-and-incarnation pair in its name essentially never recurs — and it is inert, because the only reader opens one exact path. The window it can be left in is a crash between the stage write and the rename. There is no retention cap, no ranking, and no periodic pruner — the count that a cap would have bounded is one.

**What `backend status` may report.** A distinction earns a rendered line only when it changes what the reader does and has an owner. `readRecentShutdownRemainder` (`src/cli/backend-status.ts`) renders a readable record's header and entries through their closed vocabularies. A record this build could not use is not silence: it reports `shutdown_remainder_unreadable` carrying the classification that was actually observed — `unreadable`, `corrupt`, or `unsupported` — plus the record path. The reader of that line is the LLM driving the session (`design-philosophy` §12), and the three causes call for different next moves, so collapsing them into one word would be a line it cannot act on; the path is what makes any of those moves possible, which a digest of a compile-time constant was not. `unreadable` alone is the same collapse one level down — `EACCES`, `EISDIR` and `EIO` are three different next moves — so that member alone also carries the refused read's `errno`, rendered as `errno=EACCES` beside the cause and as `errno=unavailable` when the thrown value named no system code. It is the _read's_ code even when the lexical probe behind it refused differently, because the read is the refusal the reader acts on. The field belongs to that member and not to the report, because a parse refusal has no system error code to be missing, and one value meaning both "no code applies" and "a code applies but was unobservable" is the overload `design-philosophy` §11 forbids. Carrying it opens no new boundary: system error codes are a closed set from the operating system, `operatorFacingErrorCode` already admits `isSystemErrorCode`, and the projection type asserts that `path` remains the only broad string on the line. That member is also the one the coordinator scope cannot reach: there is no decoded record, so there is no recorded writer to match against, and the rendered line says so rather than letting the evidence read as the running instance's. Filename labels, raw record subjects, error messages, stacks, free-text details, forecasts, and unowned entries do not cross the status or coordinator-log boundary. A bound owned and reported by its ledger is not a forecast: `formatProviderProxySetAutonomousDisposition` (`src/cli/format/backend.ts`) already renders the provider-proxy disposition's `boundMs`, and the live drain follows that precedent. The classification is never filtered by age, because none of the three proves anything about when the record was written. Recency instead decides whether a _readable_ record is current: `backend status` compares its `recordedAt` (never file metadata) against `RECENT_COORDINATOR_RECORD_MS`, reporting `recent_shutdown_remainder`, `stale_shutdown_remainder` for an older one, or `shutdown_remainder_clock_skew` for one dated after the observation. A coordinator-scoped read additionally requires the record's `instanceId` to match and its timestamp to be no earlier than the coordinator's own start; a record failing that scope is not this coordinator's evidence and is reported as no evidence at all.

**Where remainder evidence attaches.** `statusWithRecentCoordinatorEvidence` (`src/cli/backend-status.ts`) is the enrichment point for no-address observations and every addressed ambiguity. It reads a startup diagnostic first; whenever one exists, it attaches remainder evidence to that diagnostic's `recent_failure`, regardless of which fallback reached it. Otherwise `no_record_no_socket`, `no_record_socket_present`, `recorded_process_absent`, `unauthorized`, and every `unreachable` cause (`responded`, `refused`, `no_response`, and `foreign_peer`) may carry the correctly scoped remainder report. An answered detailed health result also receives an unscoped remainder lookup so a predecessor's record remains visible. Only a decoded health body whose namespace and flavor match the discovery record may establish `ok`, `starting`, or `draining`; a bodyless 502, 503, or 504 remains an unreachable response and contributes a non-zero exit.

**Status transport selection.** `src/cli/backend-status.ts` owns the HTTP probes and the decision to fall back to retained IPC. `readIdentityCheckedAuthenticatedHealth` (`src/transport/ipc/health.ts`) is the authenticated IPC seam: it uses the discovery boot token and accepts a health result only after the expected socket and coordinator identity match before and after the call. Status uses that answer only for `draining`; an IPC `ok` or `starting` answer cannot conceal a failed HTTP listener. The lifecycle-owned live drain projection comes from `observeShutdown` (`src/coordinator/lifecycle.ts`), crosses either carriage as the optional `shutdown` field on `HealthSnapshot` (`src/transport/server-ports.ts`), and is decoded by `parseBackendHealth` (`src/transport/http/backend/health.ts`). The rendered drain carries a deliberate output contract, because its reader is an LLM that runs what it is printed (`design-philosophy` §12): the `Shutdown drain:` section is evidence only — reason, mode, elapsed and bound, the attempt, what it waits for, the undischarged obligations and the authority still held — and `formatLiveShutdownSection` (`src/cli/format/backend.ts`) emits no runnable command inside it. The one next step a drain may offer is a status re-check, supplied separately by `formatDrainNextStep`, and a drain whose automatic retry has failed offers none at all, because nothing the reader could run would advance it. Every other executable line a running report would have emitted is withheld while draining rather than printed and filtered, since a draining coordinator refuses the commands those lines name.

### Wait / follow

Detached provider launches print `Provider job <jobId> <launchState> (provider session <sessionId>)`; detached workflows print their `workflowId` and `jobId`.

`coral-cli wait jobs <ids...> [--embed]` is a bounded read that returns at the first newly collected terminal or with a continuation at its deadline. `jobs/wait/session.ts:WaitSession` owns admission dispositions, per-job progress frontiers and line offsets, per-job terminal acknowledgement and artifact-pending flags, carrier coverage, the remaining collection set and exit precedence. Active and historical streaming reads (`jobs/wait/reader.ts:readWaitSession`) and unary snapshots (`jobs/wait/snapshot.ts:selectWaitSnapshot`) share that contract. A sibling in the continuation is a result still to collect; remaining work can also be unread progress, discovery or artifact settlement. It does not establish that a carrier is live.

`coral-cli wait jobs <ids...> --now [--lines <N>]` reads an immediate snapshot without a subscription. Without a cursor, it selects the most recent N progress lines per job (default 20, range 1..500); `--lines` cannot be combined with `--cursor`. Both modes share a 500-line/64 KiB progress budget. Each poll also reads at most 500 raw progress rows, lookahead and fault rows included, shared by positioning and selection across every job; a stream whose poll ran out continues after a macrotask, while a snapshot is one poll and reports the rest through its continuation. Snapshot terminal previews are labeled and bounded, and the complete encoded unary response is at most 2 MiB. When fitting that size omits the selected progress, each affected job keeps its unread progress and its cursor entry and stays in the printed continuation; a fault-only page may advance or exhaust a job only behind lines actually delivered, while terminal acknowledgement does not depend on progress. `coral-cli jobs detail <jobId> --full` retrieves full retained terminal content and diagnostics, including when the artifact is unavailable. Only complete delivery advances the saved cursor. A snapshot continuation keeps `--now`; dropping it opens a blocking wait.

The first delivered failed terminal in request order keeps its mapped exit code, including after acknowledgement. An undelivered sibling failure contributes only when that outcome is collected. Otherwise permanent refusals exit 1, remaining collection work exits 75, and an exhausted successful set exits 0. Follow the single printed cursor-aware continuation. `Carrier unconfirmed for: <ids>` preserves unknown coverage; it never authorizes finalization.

`cli/wait-invocation.ts:WaitInvocation` takes a monotonic deadline before handoff preflight in `cli/program.ts:parseProgramWithHandoff`. Its in-process watchdog bounds routing, reconciliation, ensure, opening, consumption and cleanup to 590 s plus a 10 s hard-exit margin (30 s plus 1 s for `--now`). Delegation carries the remaining duration where supported. A synchronous event-loop stall beyond the flush margin can delay the backstop; the caller's 600 s ceiling ends the process, and rerunning the wait replays journal facts. Before admission, timeout or SIGINT prints the original command; afterwards it uses the last delivered cursor. Ctrl+C ends monitoring with exit 75 and never aborts jobs. Launch-and-follow retains its until-terminal policy and double-Ctrl+C abort; when it delegates to a newer build, the child runs the hidden `wait jobs <id> --follow` with that same draining, reconnecting policy, ignores Ctrl+C, and is ended by the parent when the parent stops. The child has no budget of its own, so it is spawned with an IPC channel and exits 75 when that channel closes, which happens however the parent ends, SIGKILL included.

`jobs/wait/cursor.ts` owns the single wait cursor: one entry `{hash, epoch, seq, lineOffset, flags}` per job, encoded as a job count, an epoch count, each opaque 16-byte epoch token once, then 22 bytes per job, with no version tag, prefix or absolute path. Each job owns its entry: consuming a line changes only that job, and positioning changes only an unpositioned job, once, on its first readable visit. A tail scan the row allowance cuts short keeps its job unpositioned, with its lowest scanned seq and the lines found above it recorded in the entry, so the next poll or request resumes the scan instead of positioning on a partial tail. A newly resolved or newly added member receives its own tail while existing members keep their exact frontier; reordering or subsetting membership preserves frontiers. Every stream begins with a non-final `cursor` frame carrying the complete frontier after reconciliation and positioning, and repeats it whenever an entry advances without a delivered line; progress events carry only their own entry, and only the final event carries the complete cursor and the exit code. The CLI folds by replacing its base with each frame and upserting later entries. A cursor in any other shape, including an older build's token, is refused as `wait_cursor_malformed`; the CLI prints `saved cursor not accepted by this coordinator; the current progress tail and retained results are collected again, so earlier results may repeat` and starts a fresh read.

Wait carries no capability negotiation. A request formed by another Coral build — a released CLI reaching this coordinator, this CLI reaching an older one, or a wait the handoff would delegate to a selected CLI without the wait invocation contract — is refused as `wait_build_mismatch` with the guidance to restart the session so the current Coral plugin loads, since the coordinator follows the installed build. Succession notices reach every current client. `Unverified result path: <path>` names a file Coral could not certify as this outcome's result. IPC and HTTP carry the same jobs-owned contracts; HTTP backpressure waits for drain within 1,000 ms or the remaining budget.

`jobs/location-index.ts:JobLocationView` is the read-only location view used by `JobAddressing`. Wait, scope checks, detail and snapshots never register locations, hydrate history, ensure exports, mutate Coral records or perform fsync/fdatasync. Write-owned startup and epoch maintenance hydrate locations. Historical journals open read-only under `infra/fs-lock.ts:acquireSharedFileLockNoRepairSync`; SQLite's own reader sidecars are allowed. A validated retained terminal remains deliverable after source retirement. Otherwise decided closure followed by a successful journal read finding no terminal establishes outcome-unrecoverable; unreadable evidence stays unresolved.

Terminal output reports artifact availability separately from outcome. `Result path:` is emitted only for an available artifact; `--embed` adds a preview when size permits; every embedded content line is prefixed with `> `, while status and continuation lines remain unprefixed. Usage appears on terminal headers, for example `Job <id> completed · $4.18 · 18.6M tokens (90% cached)`; `--verbose` expands the token buckets.

Each projected job retains project identity and canonical work directory. Ambient selectors require exact work-directory equality; explicit wait, abort and detail requests require the caller's cwd to contain the job's work directory. KB jobs match every caller directory. On scope mismatch, change cwd to the job's work directory or a containing directory and rerun; `coral-cli jobs --all` includes terminal jobs and shows their work directories.

### Result exports

`jobs/terminal/export.ts:TerminalResultExportOwner` is the single result.md writer. Callers pass a job id; the owner renders accepted terminal facts from that job's source epoch. Workflow composition injects `workflow/result-report.ts:renderWorkflowReport` with the pure `workflow/result-rendering.ts:serializeWorkflowResult` step renderer. Without `workflow.completed`, an accepted workflow terminal renders a nonempty outcome explanation. Present completion facts must validate before their step output can be rendered. Availability observation validates those facts once per stored terminal and source identity and never serializes the report; only publication and repair render it. Empty terminals render nonempty outcome explanations. Repair preserves available files.

| Availability | Read output and collection effect |
| --- | --- |
| `available` | `Result path: <path>`; an artifact follow-up says `result file now available` without replaying the outcome. |
| `retained-away` | `no longer kept: past the N-day retention window`; no read recreates it. |
| `repair-pending` | `Result file pending; Coral will attempt publication on its next maintenance pass.`; retain the artifact follow-up in the continuation. |
| `failed` | Cause in `Result file unavailable: <cause>.` plus `Coral will retry on its next maintenance pass.` or `Coral cannot repair this file automatically.`; collection settles. |

Availability observation is read-only and may post an in-memory repair or hydration hint. Every transient artifact state is repair-pending, preserves the artifact continuation and names a maintenance retry; failed without retry is reserved for permanent loss. Historical discovery retries transient seed failures at most three times; deterministic decode failures do not retry, and exhausted discovery resolves unknown IDs to missing with an unreadable-epoch caveat. Carrier coverage keeps its last settled value until refresh completes or fails. Post-commit, startup/historical hydration and the export repair maintenance owner perform publication. Retention, availability, repair and retirement use `jobs/export-retention.ts:terminalEligibility`, the job's own epoch evidence and a trusted cutoff. Expiry is strictly `terminalAt < cutoff`; equality is inside the window. Unknown age, regression and an untrusted clock cannot authorize age discharge: a terminal timestamped before an earlier row of its own job is only bounded from below by that row, so its export is kept under `terminal-clock-regression` and never deleted by age. Unknown age never authorizes publication or deletion. First publication and repair both require a trusted cutoff, so nothing publishes while the retention clock is untrusted; publication resumes on the maintenance pass after five minutes of stable observation. A validated unknown-age legacy terminal with no export directory supplies retained outcome content for retirement without recreating a file. A source-backed, validated recorded regression may publish canonical content but still requires a durable file for retirement.

`runtime/real.ts:writeAtomicDurableSyncNode` publishes through a unique wx stage, syncs it, renames and syncs the directory, cleaning only its own stage. Publication and retention share no export lock. First publication and repair revalidate authorization immediately before rename. A cutoff race may leave canonical content until the next retention cycle; it never blocks age-based retirement. There is no age-based sweep of sibling stages.

### Carrier observation

Observable liveness is derived; stored lifecycle and mutation authority are not. A read never rewrites stored phase, and **only the journal ends a job**.

The coordinator classifies a job's carrier — the thing actually running the work — from its in-memory admission state, workflow owner's running set, operation registry, the OS process table, and the durable-CLI identity row. The verdict is deliberately tri-state:

| Verdict   | Meaning                                  | Wait effect                            |
| --------- | ---------------------------------------- | -------------------------------------- |
| `live`    | positive evidence the carrier is running | none; the wait continues               |
| `absent`  | positive evidence it is gone             | emits a nonterminal `interrupted` line |
| `unknown` | no evidence either way                   | treated as conservatively active       |

Only `absent` is a positive finding. `unknown` means the question was not answered; it is not a weaker `absent`. A transport error, timeout, unsupported endpoint, malformed or relationally mismatched reply, exhausted observation budget, predecessor build, or unreadable process incarnation remains compatible with the work still running, so every consumer treats `unknown` as active. A transport error never becomes `absent`.

Absence is established, never inferred from a pid. The kernel reuses pids, so a durable CLI is judged on the recorded pid's liveness and on its **process incarnation** matching the token captured at launch. A failing fact does not become `absent`; it becomes `unknown` wherever the failure is itself unobserved. Missing runtime metadata, metadata naming a different pid, and a live pid whose incarnation cannot be read are all `uncaptured` — the last deliberately, because an unreadable identity cannot distinguish a recycled pid from the same process (`composition/carrier-observation.ts`). Only a pid observed dead, or a successfully probed incarnation that differs from the recorded one, can establish `absent`. An acquired local app-server placement is `live` while `jobs/shell/launch.ts:LaunchOrchestrator.holdsLocalAppServerExecution` retains its execution handle, even without a registry entry or durable proxy operation. Composition supplies that placement evidence to wait; reservation membership alone is insufficient. Once the local handle is released, an app-server operation with no live registry entry — not yet attached, inherited from a predecessor, or already settled and evicted — has no decisive local evidence. Health and idle leave it `unknown`; only an open wait subscription may ask the recorded proxy through `operation.status.v1`. The proxy returns ledger liveness only, with the nonce, exact proxy instance, build set, and complete requested operation relation echoed so the coordinator can reject a stale or mispartitioned answer. `held` becomes `live`; `absent` is the only answer that becomes `absent`; every failure to obtain that exact answer remains `unknown`.

The boundary this buys is enforced, not conventional: `tests/invariants/no-carrier-observation-in-action-paths.test.ts` proves no recovery, cleanup, reconciliation, terminal-materialization, or other action path can obtain a carrier verdict **at any import depth**, over runtime edges only. A recovery walk that filtered candidates by observation would skip exactly the stored-nonterminal work it exists to settle; a cleanup pass that deleted on it would delete artifacts belonging to a running job. Derived absence therefore authorizes nothing: wait may render one nonterminal `interrupted` event, but it does not remove the job from the pending set, end the stream, or enter a recovery/action path. `coordinator/composition/` is the only runtime root allowed to import the classifier. It uses synchronous local classification for health and idle and injects the asynchronous external observer only into wait (`composition/execution-services.ts` to `jobs/shell/wait.ts`). Health and idle perform no network probe. The idle-retirement guard fails closed on missing services, read or mapping errors, unexpected stored phases, and either `live` or `unknown`; it does not ask a foreign process whether hard retirement is safe.

Recovery completeness is also a per-job classification, not a single global post-recovery assertion. Each coordinator owns a startup-recovery barrier; until its provider reconciliation and applicable generic recovery walk return, every job's coverage is `in-progress`. After the barrier passes, a job with a durable provider-operation record is `accounted-for`; one without such a record is `unaccounted`, and only that last state can add `local-unknown-after-recovery-decision`. This distinction is necessary because provider reconciliation may return with retries still scheduled while the generic walk deliberately excludes saga-owned jobs: crossing the barrier cannot truthfully say that every job was handled.

The operational health snapshot uses the same conservative but network-free local policy. `activeJobs` is `live + unknown`; `diagnostics.carriers` reports exact fields `{ coverage, liveJobs, unknownJobs, recoveryDefectJobs }`, where normal local classification yields `coverage: 'complete'`. If the store or classification cannot provide a complete mapping, the fallback is `coverage: 'unknown'`, `liveJobs: 0`, `unknownJobs: activeJobs`, and `recoveryDefectJobs: 0`: every job still counted active by the fallback is explicitly counted unknown rather than silently presented as live. Reading `/health` never invokes `operation.status.v1`.

1. `coral-cli jobs [--phase <phase>] [--provider <name>] [--all]` reads `read-model/CoralStore` directly for local no-coordinator paths; the same shape remains available through `GET /jobs` on the HTTP gateway
2. `coral-cli jobs detail <jobId>` reads the detailed job projection and renders terminal diagnostics, including usage when present

### Generation boundary and operator recovery

1. Pre-boundary state remains under `data[-dev]` and `run[-dev]`; generated state lives under `gen2/data[-dev]` and `gen2/run[-dev]`. Current code never mutates or binds the legacy generation during ordinary startup.
2. Before generated initialization, readiness is one of three states: `generated-ready` proceeds; `no-legacy` initializes; `legacy-ignored` leaves legacy bytes uninspected and untouched, reports only that the legacy tree remains, and initializes this generation's own state. A previous generation is never a precondition for startup and is never imported: the boundary exists to end that coupling, so whether this build could read the legacy store makes no difference to whether it boots.
3. Cold start resolves an incomplete succession attempt and its host recovery grants before ordinary selection. It validates the selected build root, prepares an exact-epoch open, and checks custody and historical job locations before any mint. `createStartupMintAuthorizer` in `src/coordinator/services/startup-retirement.ts` constructs the retirement disposition only after those checks. A retained old-format controller with independently verified live custody gets a protected exact-epoch hand-back, once the retained build proves through `controllerRecoveryTarget` in `src/coordinator/services/retained-epoch-executor.ts` that it can open that exact epoch; the same module's `settleWithRetainedExecutor` asks a retained build to seed an old-format epoch's historical jobs. If no root can open the old format, startup retains the old epoch and known job identities as unresolved, then can serve from a new epoch after the bounded evidence check. A compatible epoch opens in place. Job lookups observe only existence of the previous generation's flat `store.db`; the flat store and its sidecars remain as one-time residue because pre-epoch writers cannot be excluded. Unsafe coordination paths still refuse as `active_store_coordination_invalid`, and an unresolvable running bundle refuses as `startup_bundle_unresolvable` before selection.
4. Publication creates `.mint-<uuid>/.lock`, constructs the database, WAL/SHM state, format sidecar, and additive `epoch.json` beneath that mint, then renames the directory to `epoch-<N>`. The same lock inode is carried to `epoch-<N>/.lock`. Before publishing, earlier contained epoch directories with proven locks move under the protected store root outside the shipped sweep's search space; lineage markers and an address map preserve their full epoch keys, including when a shipped build later reuses numeric `N`. Protection waits up to `SUPERSEDED_OPENER_DRAIN_MS` (2 seconds) for a live opener before moving an epoch; one still held past that wait is left at its canonical address rather than blocking the mint, recorded in `store-epoch-protection-pending.v1` with audit event `store_epoch_protection_deferred`, and shown as `protectionPending` on that epoch's store-listing entry until the post-ready sweep's own retry succeeds. `ENOTEMPTY`/`EEXIST` means another publisher won and is adopted on the next loop; `ENOENT` means the mint was swept and is rebuilt. `settleSupersededEpochClosures` in `src/coordinator/services/recovery/epoch-closure.ts` composes custody evidence and owner settlement while service runs. Execution discharge and retained-result release are independent gates. The post-ready sweep removes an older epoch only after both are certified for its full key, subject to retention and locking. An undecidable epoch is `unrecoverable-retained`: it stays on disk, appears in store listing, and does not block the new serving epoch. Proven-absent mint residue and the legacy reset quarantine can still be removed. The flat `store.db` and its sidecars remain on disk. Sweep failures are audited and never block boot. Protected deletion-residue discovery checks the protected root, lineage, address directory, and tombstone with no-follow directory observations before admitting removal. A symlink or unreadable ancestor is reported as `unobservable-metadata`; ordinary interrupted residue remains reclaimable.
5. `JobLocationIndex` in `src/jobs/location-index.ts` binds each known job id to its originating full epoch key before a different-format mint. Terminal records and result artifacts remain readable across an active-epoch switch; a known live job without recoverable control stays addressable as unresolved. Historical readers use validated installed roots for old formats and never import old rows into the new store. Wait cursors name each epoch key and its local journal sequence; a mixed wait carries a map of positions, without a total order across epochs. `backend store-reset list --target <legacy|current>` classifies visible epochs by lineage key, shows closure and result-retention status, and appends bounded legacy quarantine rows while that root exists. `backend store-reset report --target current <epoch>` reports observable filesystem and provenance facts without opening SQLite. `backend store-reset release` retains a present epoch with `release-closure-required`; automatic reclamation owns the exact-key closure and result gates. Release and discard both take the operator socket guard and refuse a live incumbent with `coordinator_socket_in_use`.
6. `backend kb-commit quarantine --flavor <prod|dev> --commit <id>` is the explicit recovery for a `kb_commit_corrupt_or_unsupported` refusal. After `backend shutdown`, it holds the same socket → adoption → maintenance boundary, validates the single-segment commit ID before acquisition, and durably moves only that commit and matching index evidence to retained quarantine.

`backend recovery-quarantine discard-provider-operation` is the coordinator-owned destructive exit for one
exact quarantined provider-operation coordinate. Its strict CLI and RPC ingress reject a key carrying the
retired NUL-delimited subject tag. The CLI adds `allowReadable: true` only for an explicit `--allow-readable`;
without that consent a row this build can decode is refused. With consent, readable deletion still requires
the encoded record to match the requested SHA-256 fingerprint.

Composition checks the coordinator launch fence before constructing the discard service or reading the recovery
database. While startup recovery owns that fence, it returns `recovery-in-progress` with code
`backend_recovering`, message `Provider-operation discard is unavailable while startup recovery owns the launch
fence.`, and a structured discard remedy carrying the exact key, revision, and consent flag. The CLI renders
the complete retry invocation from that structure. Run it as printed once startup recovery finishes. This exit-`75`
refusal inspects and claims no raw row and performs no mutation: the raw row, due pointers, quarantine evidence,
startup permit, and launch capacity remain unchanged. It is therefore distinct from both a completed destructive
result and a no-verdict response that may follow a completed deletion.

Once the launch fence is inactive, the service claims the exact unowned quarantine subject before deletion and
never signals a process or settles the operation.

After the row is removed or observed absent, recovery releases startup permits no remaining record needs and
offers a sole surviving readable record to the reconciler. A refused adoption returns `adoption-refused` with
exit `75`, the row disposition, released-permit count, and each refused record's key, job, operation, proxy,
build set, and reason. Reconciliation and settlement have not been observed for those records; they remain
unowned and their launch capacity remains held. Composition retains the same facts with observation time in a
bounded backend-health diagnostic. Multiple readable records for one job remain an
`undecided-provider-operation` hold: neither recovery nor automatic reclamation can choose an authoritative
record without risking capacity assigned to live work, so that ambiguity requires operator repair.

`src/coordinator/handoff-routing/reconciler.ts:createHandoffRoutingReconciler` owns automatic retirement of unmatched routing selections. `createCoordinatorLifecycleDeps` composes it with lifecycle transitions: kernel readiness starts an immediate sweep and a one-second interval, independently of startup recovery; draining or stopped cancels observation and publication. Sweeps do not overlap. `status.ts:reconcileHandoffRoutingStatus` uses one fresh batch under the existing 500 ms observation budget and retires only absent PIDs or different exact incarnations through the existing generation-writer lease and sequence-checked transaction. Live owners, failed/unavailable/expired observations, terminal races, and uncertain commits retain their observable disposition for later sweeps. No job is settled and no process is signalled. Existing `operator-resolved` tombstones with `owner-absent`, late-terminal handling, record shapes, fingerprint, and generation remain compatible with v0.10.15–v0.10.17 readers. Status prints automatic reconciliation timing, or that reconciliation resumes on startup when no coordinator is available; it never points at the resolution command. An absent-owner selection contributes `75` until retirement commits, so automation retries the pending bookkeeping.

Authenticated inner health `starting` also contributes `75` to `backend status` while preserving outer probe `ok`, including the `kernel-ready` recovery phase. The formatter says to retry in about 1 s before printing the labeled observation retry `command=coral-cli backend status`. Ready health contributes `0`; precedence is `70 > 75 > 0`. Successful `backend start` remains `0`, and health-polling readiness callers do not consume the status command's exit.

Routing history has separate resolution, discard, and retained-quarantine commands. Every registered `backend routing-status` leaf passes through one exhaustive operator classification and is excluded from routing lifecycle recording; unclassified future leaves fail the CLI coverage invariant, while an unrecognized routing-status invocation remains excluded by default. `backend routing-status resolve --invocation <id>` resolves a retained opening or acknowledges a retained capacity eviction. For an opening, a decisively live owner is refused, a decisively absent owner may be resolved, and an unobservable owner requires `--force-unobservable` after external verification. The override is false by default and cannot override `deadline-expired`, because an expired sweep established nothing about the owner. A capacity acknowledgement atomically folds the exact tombstone into aggregate history; exact `operator-resolved` tombstones are already terminal information and require no acknowledgement. The resolve boundary preserves commit truth as distinct success, `artifact-refused`, `not-published`, and `commit-outcome-unknown` result arms, with the requested invocation ID intersected directly into each publication outcome instead of duplicating its discriminator; every non-validation failure contributes exit `75`. Every committed terminal remains rendered history with its policy severity but contributes `0`, while the next live invocation re-derives any recurring routing problem and its actionable exit. The journal body is also the only persisted retention authority: completed-pair stability is derived from its validated JSON during the bounded retention scan, not stored as a parallel bit. Production publication retries generation admission and SQLite contention against one monotonic deadline. It performs filesystem and WAL preflight before opening, classifies after opening but before configuration, and repeats the full classification under `BEGIN IMMEDIATE` before initialization or mutation. Maintenance winning an admission retry is reported distinctly. `backend routing-status discard` is allowed only for `detached-wal`, `generation-missing`, `foreign-generation`, `format-mismatch`, `schema-divergent`, and `unreadable`; under the coordinator-socket and generation-maintenance guards it revalidates ownership after the guarded read and quarantine scan, preserves the WAL before removing the observation-rewritten source SHM, and then preserves the main database when one was observed. A wal-only incomplete UUID-addressed set is a successful discard only when both observations found the main absent; otherwise an incomplete set refuses the next discard with its exact ID until `backend routing-status quarantine clear --id <id>` removes it. A retained WAL cannot establish the identity of a database currently at the source path. Expected pre-effect refusals and post-attempt failures are public result arms rather than throws: coordinate observation, root creation, artifact preservation, directory sync, and ownership loss all exit `75` with the exact quarantine ID and applicable repair/retry command. Moved and removed arrays contain only effects made durable by their directory barriers; successful namespace changes whose barriers fail are reported separately as observed effects. Known-empty retention names storage repair and a discard retry; known retained evidence additionally names quarantine list and exact clear. Unknown retention is a separate result arm that never reports absence and requires `backend routing-status quarantine list` to resolve the hold. Clear likewise returns typed `quarantine-clear-undeterminable` before removal and `quarantine-clear-storage-failed` for any failed removal or sync; both exit `75`, retain the exact ID, and name the exact clear retry, with storage failure also naming quarantine list. `current` and `undeterminable` refuse discard with a nonzero exit; `absent`, `vacant`, and `uninitialized` report that no discard action is needed and exit successfully. Expected socket and generation-maintenance guard failures are typed refusals: a live owner names `backend shutdown`, an unobservable socket remains a distinct no-verdict answer, maintenance contention names a later retry, an unobservable writer identity names process-observation repair or the heartbeat stale bound, and lease loss names repair of the generation coordination root followed by a fresh status read and discard retry. At most 16 complete or incomplete sets are retained; the next discard refuses until `backend routing-status quarantine list` exposes exact evidence and `backend routing-status quarantine clear --id <id>` removes an operator-selected set under the same guards. No evidence is pruned automatically. Journal and Corpus authority are unchanged by these commands.

`vacant`, `uninitialized`, `detached-wal`, `generation-missing`, `foreign-generation`, `format-mismatch`,
`schema-divergent`, `current`, `unreadable`, and `undeterminable`. `readHandoffRoutingStatus`

An ordinary routing writer probes the maintenance lease through heartbeat-aware lock acquisition while it holds
generation admission. A live holder still produces `generation-maintenance`; an abandoned holder becomes

The sixteen-set routing-status quarantine ceiling is a count bound, not a byte bound. A complete set contains the database and an optional WAL; an incomplete set contains a WAL without a database. The main database is hard-capped at 1 MiB; the WAL returns to its 1-MiB `journal_size_limit` when a checkpoint can reset it, but may exceed that limit while an open reader prevents reset, with growth limited by the writes accumulated during that reader's lifetime. Before upgrading a dev or CI checkout that used the pre-two-file implementation, list and clear every routing-status quarantine with the pre-change build. Uncleared three-file database/WAL/SHM residue is unsupported and is not swept during upgrade.

The routing-status store's schema renderer, `handoffRoutingStatusFingerprint(schema)`, and
`handoffRoutingStatusGeneration(schema)` are the canonical identity home. The fingerprint is the full 32-byte
SHA-256 identity of the canonical durable format, rendered SQL, and completed-pair stability contract. The metadata

identity check. Operational capacity remains outside the durable identity because it changes allocation rather
than decodability. Publication compares generation, the complete non-internal schema, and the persisted fingerprint
before initialization or mutation, then repeats admission inside `BEGIN IMMEDIATE`. A mismatched canonical schema
is `schema-divergent`; a matching address and schema with another full identity is `format-mismatch`.

Persisted body grammar participates in that identity by extraction from the hand-written Zod schemas through
`zodPersistedContract` (`src/infra/persisted-contract.ts`). A descriptor-first language is therefore not required,
and the claim that complete identity must cost the readability of hand-written Zod is false. The same extraction
direction already supplies production persisted contracts in `src/store/current-format.ts` and
`src/providers/registry.ts`. Callers derive the generation before passing it to the path authority; the coordinator
does not re-export it. Superseded-address artifacts remain isolated and outside the current address's quarantine

### Workflow

1. `coral-cli workflow ...` posts to `POST /workflow`
2. The workflow domain compiles the DSL into a semantic plan (slot id, dependencies, provider, instruction, optional agent)
3. The executor launches provider or `coral:` atoms through the coordinator API; launch and retry stay intertwined per architecture §10.1a
4. Workflow state is persisted as Journal events with a projection row per workflow. `workflowSlotId` identifies a semantic slot and is carried and surfaced separately from child job identity. Each child receives a separately minted canonical UUID job id from the runtime `ids` port. Recovery reconstructs the current slot-to-job mapping from durable child rows, reuses the durable job id for a slot with a current row, mints an id for a plan slot without a row, and mints a new id for the next replacement generation when a pending continuation lease requires one; job ids are never stored in the semantic plan. `coral-cli wait` reads the same job store
5. Workflow usage is resolved from child job terminal diagnostics at read time, not stored on the workflow terminal event

### Boot Eras

Backend boot is split into three sequential eras so the CLI gets a usable socket as quickly as possible and individual component failures stay isolated.

| Era                             | Owner                                        | What runs                                                                                                            | Lifecycle phase on completion                 |
| ------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| I — Kernel                      | `coordinator/lifecycle.ts`                   | Bind IPC socket, open Journal, install transport listeners                                                           | `kernel-ready`                                |
| II — Recovery                   | jobs / discuss / workflow shells             | One-shot startup reconciliation for in-flight work                                                                   | `running`                                     |
| III — Runtime Health Components | `coordinator/runtime-components/registry.ts` | Fire-and-forget `initAll()`; each `RuntimeComponent` projects daemon-visible health without blocking the kernel path | per-component `online \| degraded \| offline` |

Era II waits for provider-operation startup reconciliation for at most 500 ms, measured by the runtime's monotonic clock. This is a serving responsiveness budget, not an estimate of healthy inheritance latency: crossing it only ends the lifecycle's await. It leaves room in succession's 2.5 s serving window (5 s admission pause minus the 2.5 s writer-reclaim reserve) for component registration and reaching `running`. Expiry never aborts recovery, revokes a fence lease, proves containment absence, or releases startup job ownership.

Claims/lifecycle initialization continues under its original live context after detachment, including durable-disposition re-observation and its existing retry timers. Once initialization finishes, each set recovers independently under its own live context. Each unfinished set remains owned by its startup recovery; retained sockets and callbacks keep accepted mutation admission. The due poll excludes these sets before counting its executable batch, so it neither competes with startup nor lets one set's old due rows starve unrelated sets. Settlement applies the ordinary outcome: success needs no successor, while a failure or retry disposition uses the existing saga retry and due-poll ownership. No abandoned-scope retirement is needed.

A detached wait that never settles is the residual: it holds that set and its startup ownership, remains visible, and no longer holds the coordinator or other initialized sets. Initialization itself remains a visible prerequisite for queued startup sets until it settles; it does not hold component registration or `running`. Saga rows and durable operator dispositions survive coordinator restart; the startup health projection is in memory.

Detailed health and `backend status` add `diagnostics.providerOperationStartupReconciliation`: continuously advancing elapsed time, bound, set keys, queued/recovering/detached state, pending mutation and fence labels, incidents, and the current owner. Unfinished initialization appears even with no operation rows. Older readers may ignore this optional field; an unsupported projection is omitted without rejecting health.

Set-fence closers are not globally serialized: ordinary inheritance can overlap the lifecycle's operator-disposition proof or operator-exit fence. `ProviderOperationMutationAdmission.closeSet` makes a competing admitted chain retry with `ProviderOperationMutationSetClosedError`; recovery dispatch projects that refusal as `mutation-set-fenced`, never a fatal proof failure. The first closer still drains that chain's unfinished writes. Reading a transferred fence's wait from a mutation it must drain receives the same refusal. The exclusion remains the creating admission chain, including its ancestors; sibling chains sharing an ancestor are competitors. External leases remain supported, and whole-admission shutdown drain remains separately bounded by shutdown settlement.

The CLI waits for a usable coordinator (`ok`, `kernel-ready`, or `running`), or the draining incumbent itself, for a route the operational catalog admits while draining; Era III takes whatever time it needs without holding the CLI. Which of those a given invocation accepts is not the caller's choice: `ensure()` takes the invocation's method and derives the answer from `ipcRouteLifecycleAdmission` (`src/transport/rpc/operational-catalog.ts`), which reads `running-or-draining` off exactly those IPC route specs whose `requiresRunningLifecycle` is `false` — so `jobs.abort`, provider-proxy containment, and `provider_host.list`/`list.v2`/`inspect`/`evict` are issued to a draining incumbent, identity-checked over the authenticated `transport.health` route that is itself drain-admitted, while `sessions.create` still waits for socket release and replaces it. The provider-host routes are `report-refusal` rather than `spawn-successor`, because a successor has not captured the incumbent's owners: its `list` and `inspect` answer for its own inventory rather than the one the operator asked about, and `evict` on an exact reference it holds no row for answers `provider_host_not_found` while the host it was told to evict stays untouched — and `provider-host evict` is the operator exit of a hold that only a drain creates. A draining coordinator that does not admit the method answers the success-shaped `backend_shutting_down` body, which the unary IPC client decodes into a typed `IpcLifecycleRefusal`; the refused route's own `onRefusal` column then decides what follows — `spawn-successor` obtains a successor and re-issues the request once, `report-refusal` surfaces the refusal as it stands. A draining coordinator may also admit and dispatch `jobs.abort`, then refuse it before any effect when the job's stop can only be recorded by the successor; this follows the route's `spawn-successor` disposition, so the CLI has already re-issued the abort once when that refusal surfaces. Every current coordinator launch starts or contacts the namespace supervisor, which holds a kernel released lock at `namespace-supervisor.v1.lock`, admits a child through a private parent channel before startup effects, and then supervises that exact child through an IPC heartbeat. The supervisor challenges once per second, resets a late scheduling window after a five-second gap, and after ten minutes of unanswered challenges sends `SIGTERM` to that exact child, then `SIGKILL` after 30 seconds if it remains. An observed Linux uninterruptible `D` state resets the window because a queued signal cannot end it until the kernel resumes the thread. The coordinator stops admitting and enters bounded shutdown when its supervisor pipe closes. A waiting CLI observes recovery for at most 660 seconds when the holder advertises a sentinel, or 30 seconds for a legacy or unknown holder, then returns retryable `coordinator_recovering` (exit `75`) without signalling it. A terminal child that left no refusal does not by itself end the wait either — if a coordinator still answers the address and has not named its own shutdown, the wait becomes the bounded existing-starting wait rather than a failed startup, because an incumbent the child conceded to may still be in `starting`. `KERNEL_READY_DEADLINE_MS` (15s) bounds attachment to an already-starting incumbent, and also bounds a nested command waiting for its exact parent. `HANDOFF_DRAIN_TIMEOUT_MS` (30s) bounds the incumbent's drain on socket handoff, and bounds a request issued to a reached draining incumbent so an admitted route cannot inherit the whole tool budget; that bound expiring is neither a refusal nor a completion, and leaves as `coordinator_drain_unanswered` (exit `75`) saying whether the method ran is unknown. These values are constants in `src/transport/ipc/ensure.ts` and `src/coordinator/shutdown.ts`.

`bindWithHandoff` in `src/coordinator/handoff.ts` no longer signals a live incumbent. A replying incumbent stays at its address until it completes an owned succession; an administratively draining incumbent releases the socket through its own shutdown sequence. The successor's handle-transfer commit keeps the address claim set listening through the generation change. If an address remains bound by an unanswerable live process, startup reports a hold; it does not infer consent from a version comparison, a timeout, or a prior signal ledger. A shipped contender can still carry its own signal behavior, which this build cannot change.

When `coordinator.sock` exceeds the platform's `sun_path` limit, the canonical relocated address is under `/tmp/coral-<state-root-hash>/`; the state root, not the caller uid or `TMPDIR`, owns that namespace. The binder still requires the directory to be owned by the calling uid with mode `0700`, so a second user of this build over the same installation refuses instead of deriving a second lock. The v0.10.9 guard uses that tag's own 104-byte Darwin/108-byte non-Darwin rule. Its path owner accepts only non-empty absolute configured and system temp directories and deduplicates the resulting addresses. If v0.10.9 would have relocated but its configured selector is empty or relative, the shipped address depended on its working directory and cannot be enumerated; this build refuses startup instead of treating that third answer as no guards. [`socket-address-ownership.md`](./todo/socket-address-ownership.md) records the remaining cross-environment limit.

Bootstrap diagnostics remain schema V1 and atomically publish one `retryable` boolean derived from `DOCUMENTED_CORAL_SETUP_ERRORS`. Backend status accepts both values, carries the distinction in `recent_failure`, and renders it without forwarding structured error context. An older reader encountering `true` treats the diagnostic as inapplicable and falls back without crashing; the diagnostic artifact and coordinator log remain the rollback-era inspection path.

#### Child Lifecycle Confinement

Coordinator lifecycle authority belongs to top-level invocations only. `ensure()` probes the socket, then routes any child-shaped invocation — `CORAL_CHILD=1`, or any non-empty `CORAL_CHILD_CREDENTIAL_ID` / `CORAL_CHILD_CREDENTIAL_KEY` / `CORAL_CHILD_PRINCIPAL_HANDLE` / `CORAL_JOB_ID` / `CORAL_SESSION_ID`, so partial bindings fail closed — into an existing-only branch before it computes desired bundle identity. That branch may read discovery and poll health, and it may never request shutdown, wait for socket release, spawn `coral-backend`, clear a startup sentinel, or rotate coordinator logs. `shutdownBackend()` carries the same guard independently. A KB-disabled incumbent is never force-restarted to re-enable it: `cli/dispatch.ts`'s `reconcileKbBoot` skips its own probe entirely for a child-shaped invocation (`ipcAuth !== undefined`), and even a top-level one only warns and lets KB turn on at the next idle restart (`CORAL_BACKEND_IDLE_MS`) or an operator-run `coral-cli backend shutdown` — there is no restart call left on that path for a guard to apply to.

A child starts from the exact incumbent it first observed and never starts or replaces a coordinator. `waitForExistingIncumbentReady` in `src/transport/ipc/ensure.ts` pins that identity while it waits. It may follow an identity change only when a completed durable upgrade intent names that incumbent and the exact serving successor in its completion receipt; any other replacement, missing receipt, or discovery mismatch fails closed. Transferred child handles are checked against the parent job's accepted obligation and recorded launch namespace, rather than assuming the new coordinator minted them. The reused client carries no boot credential, so normal child-principal capability rules still govern the request (see [CLI Errors](./cli-errors.md#nested-coral-commands)).

#### Child Authentication

A launched child authenticates to whichever coordinator serves, including one that replaced its launcher. Before launch, `ChildPrincipalRegistry.register` (`src/coordinator/child-principal-registry.ts`) mints an Ed25519 key pair and writes the child's authorization and public key into the `store.db` holding its job, under the additive `child_principal_credential.v1:<credentialId>` meta prefix (`src/coordinator/child-principal-credentials.ts`). The child receives only the public credential id and its private key (`CORAL_CHILD_CREDENTIAL_ID`, `CORAL_CHILD_CREDENTIAL_KEY`) and never transmits the key. Each request opens a connection, asks `transport.challenge` for a fresh challenge bound to the coordinator's random per-process incarnation and namespace, and sends a `child-proof` signature over that challenge, the credential, job, session, method, request id, and params digest (`src/security/child-credential.ts`). The IPC server holds the challenge only in that connection's memory and takes it before dispatch, so a proof authenticates one request at one coordinator; a successor, a second connection, or a retry after a lost reply needs a new challenge, and nothing about past authentications has to survive a process. Succession transfers nothing: the successor opens the same epoch and verifies from the store. A record that cannot be decoded denies only its own credential, as `child_credential_unavailable` naming the id, and is never read at boot. The replayable bearer `child` protocol is refused by this build's coordinators; the CLI still sends it only when the environment carries nothing but a shipped coordinator's `CORAL_CHILD_PRINCIPAL_HANDLE`, which only that shipped coordinator can accept.


KB is not hosted as a coordinator component. The parent daemon registers only `createKbDaemonHealthComponent(kbDaemonSupervisor)`, which mirrors KB daemon health into `/health.components[]`; the KB daemon process owns KB runtime boot, Corpus replay, CorpusConsumer registration, Orama freshness, curate work, and expansion lifecycle. With `CORAL_KB_ENABLE=0`, the parent wires a disabled KB daemon supervisor so the health component reports terminal `offline` without spawning the KB daemon. `createKbDaemonSupervisor` in `coordinator/live/kb-daemon-supervisor/index.ts` assembles explicit state from `kb-daemon-supervisor/state.ts`; that directory owns health, request dispatch, probes, recovery, process start and stop, and the public port implementation.

#### KB Daemon Protocol

Parent and child speak a newline-framed JSON protocol over the child's stdio (vocabulary owned by `kb-daemon/protocol.ts`; non-control stdout lines are ignored, stderr is buffered for diagnostics):

- **Child → parent**: `coral.kb_daemon.ready` (one-time readiness with pid/readyAt), `coral.kb_daemon.response` (correlated reply to a parent request), and `coral.kb_daemon.event` (journal/corpus events the parent ingests into the ConsumerDriver and lifecycle reactor).
- **Parent → child**: `coral.kb_daemon.request` carries KB reads, mutations, expansion RPC, job abort/list, and `shutdown`. Request ids are generation-scoped (`${generation}:${seq}`) so a reply from a previous daemon generation can never settle a current request.
- **Reverse channel (child → parent → child)**: `coral.kb_daemon.parent_request` / `coral.kb_daemon.parent_response` let the daemon call back into the parent for `curate.assistant.complete` and `curate.assistant.cancel`, since the provider host that runs the curate assistant lives in the parent.
- **Liveness**: the child runs a parent-PID watchdog (`DEFAULT_PARENT_WATCHDOG_INTERVAL_MS`, 1s) and self-terminates if the parent exits; the parent escalates a stuck child SIGTERM→SIGKILL via `gracefulKill` on start-timeout and stop.

### Discuss and KB

- `coral-cli discuss ...` maps to resource routes under `/discuss/*`; the discuss domain exposes explicit coordinator-facing owner modules for commands, reads, and recovery rather than a compatibility `api.ts` facade
- `coral-cli kb ...` maps to resource routes under `/kb/*`
- Discuss follows the functional-core / imperative-shell pattern: the core is pure event-sourced state transitions; the shell carries persistence, loop control, and subflows
- KB markdown is the Corpus authority for notes, sources, principles, communities, and wiki entries. Memos are project-scoped scratch artifacts that can be promoted into Corpus notes or wiki entries. Source import and explicit reindex are job-owned by the coordinator because they can be long-running; lightweight KB reads, note mutations, wiki mutations, and memo operations stay direct commands.
- KB markdown syncs across machines through git. Custom merge drivers make derivative files converge where possible (`.entity-graph.json`, note/source/community frontmatter), while tracked provenance (`inputFingerprint` and `summaryInputFingerprint`) lets a peer skip LLM work already computed for the current content.
- Retrieval projections are CorpusConsumers. The `kb.fts`, `kb.vector`, and `kb.embedding` `RuntimeBinding<Backed<T>>` cells are constructed empty; bundled Orama binds `kb.fts` during expansion lifecycle startup, while installed Gemini and ONNX engines can bind `kb.embedding`. No current first-party package fills `kb.vector`; external engines may do so through the same capability contract. Commands that need retrieval readiness wait through `ConsumerDriver.waitFreshUntil('corpus', snapshot, consumerId)` instead of polling expansion status.

Live launch capacity is owned by exact `LaunchPermit` values rather than an ambient job-to-pool lookup. A
permit has one current holder; holder transitions preserve its reservation identity, and release succeeds
only for that exact reservation and holder. The maintenance sweep considers aged permits but reclaims one
only with evidence matched to its current holder. Local-execution and recovery holders require an absent or
terminal job. A proxy-operation holder additionally requires absence of that exact operation record; an
undecided-provider-operation holder requires absence of the exact held record-key set. Both provider-operation
proofs retain the underlying absent-or-terminal job evidence. System-task and queue-handoff holders are not
automatically reclaimed. Reclamation returns capacity to the permit's own pool and admits that pool's queue
head.

Backend health exposes actionable launch state rather than a bare active total. `backend status` renders
reportable permits with reservation, job, pool, provider, held age, holder, and execution owner; non-releasing
attempts with the attempted holder and either an already-released disposition or the transferred current
holder; automatic reclamations with age, evidence, and reclamation time—the provider-operation evidence
includes its operation ID or exact record-key set plus the job evidence; and provider-operation adoption
refusals with the trigger and refused record identities,
row disposition, released-permit count, reason, and observation time. Release, reclamation, and adoption-refusal
history is bounded in memory.

Daemon-owned state is account-neutral. The `store`, `coordinator`, `exports`, `engine`, `projects`, and KB runtime families use one canonical tree per flavor; `CODEX_HOME` and `CLAUDE_CONFIG_DIR` never participate in path composition. Account selection crosses the transport boundary as validated request context. A real `ProviderSession` stores the immutable binding for one provider conversation; workflow and discussion roots persist the complete provider scope used to create future children. Recovery rehydrates those durable values and never lets the daemon boot environment choose later requests. See design-rationale §5.4.

The core architectural boundary is simple: the CLI is the only local command surface, the backend is the only daemon surface, and all long-running or resumable work is tracked as backend jobs.

Store-reset operation and legacy reporting are deliberate local carveouts for times when the daemon is unavailable. `src/store/operator-store-reset.ts` owns guarded discard and release requests; the CLI validates flags, supplies runtime/build identity, and renders results. `backend store-reset list` shows canonical and protected epochs by full lineage key with closure disposition, and appends rows from the bounded legacy incident reader while the old quarantine root exists. `backend store-reset release <K>` takes the operator socket guard and generation-adoption lock, then retains a present epoch pending automatic exact-key closure and result certification. The adoption lock coordinates operators but is not correctness authority. `backend store-reset discard` takes the same guards, then publishes the next epoch regardless of classification. `report <epoch-key>` opens no database: it reports observable filesystem facts, allowlisted `epoch.json` provenance, a relative database address, and the `sqlite3` command an operator can run. Legacy `report <uuid>` remains available while quarantine rows exist and uses only the bounded legacy file reader. `backend recovery-quarantine list` is separate product behavior: it opens the current epoch under a shared lease and reads its quarantine rows. No operator path restores a legacy incident as active state.

Routing-status discard and quarantine clear use the same offline layering. `src/coordinator/handoff-routing/status-operator.ts` owns authorization and the socket → generation-maintenance → guarded re-read → mutation sequence; `src/store/handoff-routing-status-store/quarantine.ts` owns raw quarantine moves and removal. `src/cli/routing-status-discard.ts` only supplies the real socket guard, and command registration parses arguments and renders the typed result. No additional offline carve-out is required.

Ordinary builds generate one build-set UUID and one store-format fingerprint embedded across the backend, CLI, and Claude helper, then write the authoritative adjacent `clients/build/manifest.json` with hashes for all three artifacts. Releases copy every artifact byte-for-byte into `clients/bridge`; they do not regenerate identity. Hidden package probes and the build/release contract verifiers execute all three artifacts against that manifest, verify all three artifact hashes, require byte equality between build and release copies, and enforce the package file allowlist.

## Design Rationale

For the **why** behind these structures — the duality of authorities, causal-graph fault model, provider stream composition, the Zelda Expansion philosophy, naming/subdivision policy with rejected anti-patterns — see [`docs/design-rationale.md`](design-rationale.md).

## Rewrite Policy

The rewrite branch is clean-slate. Retired module paths, compatibility shims, and fallback aliases are not kept for convenience. If an old path no longer represents the owner, it is deleted and guarded by invariants. When implementation reveals a better owner than the document predicted, update the document and code together rather than preserving a transitional layer.

## Terminal Outcome Model

Terminal results carry a typed outcome (`TerminalOutcome`) — a discriminated union owned by the jobs domain:

- `completed` — provider turn finished successfully.
- `aborted { reason }` — closed-token reason: `signal_abort` | `user_abort` | `queue_shutdown`.
- `provider_exit { code, note? }` — provider process terminated with a numeric exit code.
- `failed { causeRef }` — upstream cause resolvable via the Journal (`CauseRef = { stream, seq }`).
- `job_fault { fault }` — typed job-lifecycle fault (ghost launch, wrapper loss, wrapper crash).

Journal reads use only the strict current domain codecs. Runtime job ingestion emits canonical domain events directly; incompatible persisted shapes change the application-wide store fingerprint and trigger destructive reset rather than translation.
Domain registries own event schemas, append validators, and reducers. `store/` runs composed validators transactionally before insert, but does not hardcode domain vocabulary.
`jobs/terminal/recording.ts:appendJobTerminalRecorded` owns raw `job.terminal.recorded` construction with `{ terminal, diagnostics? }`. Coordinator terminal materialization and workflow/session event builders stay in their existing services and call that recording owner. `diagnostics.usage` is the durable home for provider usage; renderers derive totals from its additive buckets. Active wait continuity is read from the current provider session by `jobs/shell/wait.ts:readQueryContinuity`; historical wait continuity is null. There is no immutable terminal-continuity snapshot.

CLI wait output surfaces the outcome through five exhaustive headers, followed by a usage segment when terminal diagnostics carry usage:

```
Job <id> completed
Job <id> aborted: <reason>
Job <id> provider exited <N>[: <note>]
Job <id> failed: <cause description>
Job <id> errored: <sentence> [<kind>]
```

The trailing `[<kind>]` tag on `errored` lines is the machine-readable classifier (regex `/\[(\w+)\]$/`).

## Storage retention

`jobs/location-index.ts:JobLocationIndex` caches read validation by stored stat identity in a bounded 128-record LRU. Unchanged retained copies reuse their validated view; changed identities and evicted records are decoded and checked again. Publication and repair keep full terminal checks. Active terminals follow the same rule: `jobs/shell/wait.ts:WaitCoordinator` keeps up to 128 decoded terminal projections for the coordinator's lifetime, keyed by epoch identity and job, and decodes one again only after that job's own last seq moves, so a fresh snapshot or admission does work bounded by its output rather than by retained content size.

`jobs/location-index.ts:JobLocationIndex.compactTerminalRecords` owns automatic, bounded compaction of historical terminal copies. A terminal detail keeps its matching terminal event, status, exit and additive fields; nonterminal progress stays unresolved. `jobs/location-recovery.ts:recoverJobLocations` reads only terminal events for terminal jobs and durable writers skip identical records and certificates. Compaction cursors checkpoint independently of startup and resume after a crash.

`coordinator/services/recovery/custody-reconciliation.ts:reconcileFinishedCustody` owns bound-entry discharge. It requires retained exact terminal/result and matching controller-transfer evidence when carried, then observes the recorded incarnation and containment group and confirms absence through `reapRecordedContainment`. It never signals a live process to manufacture retention eligibility. A discharged receipt retains its exact binding additively; shipped readers stay conservative until whole retirement. `store/custody-ledger.ts:pruneCustodyLedger` owns retention after reconciliation, under entry locks and writer fencing. Validated absence becomes eligible after `CORAL_JOBS_RETENTION_DAYS` from proof. The whole entry is renamed into `.stage.retention.*`, fsynced, and cleaned in bounded turns. A durable receipt outside the stage binds cleanup authority to the ledger root and entry inode; interrupted stages resume automatically. Ledger root identity and epoch coverage metadata survive. Unknown owners, live containment, missing results and unreadable transfers hold for the next reconciliation.

`jobs/export-retention.ts` owns whole terminal exports, including provider artifacts. `JobLocationIndex.exportResultRetention` keeps a historical result while its superseded epoch exists or its address is unknown. A job with no location record has no epoch closure hold. Residue age is the newest mtime of the export directory and its top-level entries, including directories. Eligibility never walks descendants. One export directory's top-level eligibility scan is indivisible and is not split across slices: it finishes even when the cooperative budget expires during the scan, then the slice stops. Real exports have only a handful of top-level entries; a wide or slow top-level scan can exceed the slice budget. No eligibility checkpoint is reused.

Released location records can lack captured terminal-age evidence. While their source epoch remains readable, `JobLocationIndex.exportDeletionEligibility` keeps past-window legacy exports rather than deriving an expiry label from a timestamp alone. The export retention owner revisits them on its normal retention cycle after epoch retirement releases the source hold, using the existing filesystem age proof. This conservative residue is distinct from the unknown-age legacy retirement discharge, which still requires a successful source read and an absent export directory.

After proving age and releasing the epoch result hold, retention atomically renames an export to `.retiring-<encoded-job-id>-<uuid>` beside its original name. This quarantine redirects subsequent writes through the original pathname, but existing working directories and open directory handles can still write into the retired tree. Post-rename validation checks that the export directory's own mtime matches its value before rename and scans top-level mtimes against the admitted cutoff. The root's age check uses the rename time so that a terminal export can have a newer root mtime than its terminal cutoff. The validation records root and top-level directory mtimes; deeper directories record their own mtime when the recursive walk reaches them, without using descendant activity as an age proof.

Admission, retirement rename and initial evidence share a fenced SQLite transaction. After asynchronous discovery, small export trees preserve the first-leaf deletion and yield, then retire their remaining entries in one deletion transaction (at most eight entries). Larger trees batch at most eight leaf removals with their evidence writes. Completion clears admission and pending metadata in the final removal transaction; no transaction spans asynchronous discovery. Cursor hints checkpoint every 32 subjects and always at completion while authorized. After asynchronous enumeration yields and immediately before each unlink or directory removal, retention rechecks that directory and its ancestors against the recorded mtimes. Each successful removal updates only its direct parent's expected mtime, so retention's own deletions do not look like external activity. An external directory refresh stops the walk and reports a kept outcome for what remains. Retention restores the original name when it is free; if a writer has recreated it, the remainder becomes the visible `kept-retiring-<encoded-job-id>-<uuid>` directory. Keeping a retirement clears its admission, retry evidence and pending failure entry. Kept retirements remain scan candidates: a later scan checks the original job’s eligible state and released epoch/result hold, gathers fresh age evidence without reusing the cleared proof, and retires the remainder again through the same no-follow identity checks. Recent content stays protected until that fresh age proof expires.

Interrupted deletion leaves the quarantine for retry. Additive meta state saves the admitted cutoff and exact root and top-level directory mtimes witnessed after retention's own deletions. A retry accepts those saved mtimes as deletion evidence while rejecting recent activity with a different mtime. On startup or a later scan, `.retiring-` directories are recovered even when they precede the normal scan cursor: retention rechecks the job state, result hold and top-level age evidence before resuming, or restores/keeps the remainder when proof is lost. A crash before evidence is saved leaves no exemption for deletion-induced freshness, so recovery conservatively keeps recent residue. Unknown protected epoch observations retain exports, and the original directory, deterministic protected directory and deletion tombstone must all be absent before their result proof is released. `jobs/progress-retention.ts` prunes expired progress while retaining terminal, lifecycle and session events, fault diagnostics and causal evidence for replay and shipped readers.

New stores and new epochs enable `auto_vacuum=INCREMENTAL` before schema creation. Existing NONE-mode stores remain in NONE mode: deleted rows create free pages that subsequent writes reuse, bounding growth without returning those pages to the filesystem. They shrink at the next epoch mint or store reset. No runtime full VACUUM, conversion helper or startup conversion runs. Additive maintenance indexes are installed independently during writable store opening; neither indexes nor persisted cursor keys change the store-format fingerprint. `store/retention-vacuum.ts` yields between 32-page incremental chunks on incremental stores.

Storage retention rechecks `causeRef` and `causation_seq` inside each progress deletion transaction. Its additive indexes cover shipped direct, reason and terminal cause paths; unknown causal shapes conservatively hold progress. A progress sweep captures a terminal-sequence ceiling and scans only `afterSeq < seq <= ceiling`, at most 1,000 terminals per run. The persisted ceiling and the position within a job resume after shutdown, park or crash; progress checkpoints commit with deletion. Finishing the captured range resets the cursor even while newer terminals arrive, so expired prefixes get another turn. Older cursor meta without a ceiling is accepted and starts a fresh capture; unknown additive keys are retained. Each batch deletes at most 64 rows, caps SQLite lock waits at 25 ms; the connection timeout is restored before yielding. Normal SQLite automatic checkpoints remain enabled to prevent retention from accumulating a large WAL. Retention does not run an unbounded passive checkpoint. Native commits and filesystem I/O remain synchronous and cannot be interrupted by a timer. Export and holder directory continuations are additive keys in `meta`. Export traversal sorts names and resumes strictly after the last processed name without charging the retained prefix against the operation budget. Scratch scanning and settlement check the budget and yield between subjects; their meta cursor preserves progress. Active hydration quarantines report pending holds on every cycle until cleared. Scratch and export deletion failures each persist in a pending set of at most 100 subjects in meta. A persisted rotation index gives each member a turn across cycles. Retries receive at most half of the owner's cooperative time and operation allowance; the main scan receives the remainder and skips pending members. Individual synchronous operations can overrun that allowance. Outstanding subjects report `partial` with `scratch-cleanup-pending` or `export-cleanup-pending`; overflow reports `scratch-pending-overflow` or `export-pending-overflow` and stops cursor advancement at the failed subject until capacity is available. Pending reasons remain visible even when failure details fill the bounded status list. Actual scratch removals publish counted deleted outcomes; already-absent artifacts publish nonpending kept outcomes. Unfinished scans report `partial` and `scan-pending`, and each owner receives an independent budget on startup and daily retry.

Retention compares each wall-clock observation with the last trusted one, whose baseline survives idle periods. A wall-clock change that departs from the monotonic time elapsed since that baseline by more than one minute plus 12% of the elapsed time, in either direction, or a backward monotonic step, makes the cutoff untrusted; it stays untrusted until five minutes of monotonic time pass without another departure. The cutoff includes a one-minute safety margin, so second-scale wall-clock steps do not decide day-granular expiry. A terminal timestamp earlier than any preceding timestamp in the same job is kept as `terminal-clock-regression`. The cutoff uses wall time without a per-boot age anchor, so idle restarts do not reset expiration. An unwitnessed clock error larger than the retention period can still expire results early; this residual loss of results is accepted. Gradual drift below the detector tolerance is also not distinguished from elapsed age. Age, regression and residue holds are visible kept outcomes and make the run `partial` while work remains. The scheduler classifies kept outcomes by their pending disposition, independently of reason text. Owners explicitly mark subjects with no eligible work as nonpending; omitted or unknown dispositions conservatively make the run `partial`, including selection, epoch and codec refusals. `completed` means no eligible work remains.

`coordinator/composition/storage-retention-scheduler.ts` starts after serving and runs every owner at startup, then tracks a separate 24-hour due time for each owner. An owner with unfinished work retries after five minutes only when its own preceding turn made deletion progress or stopped for budget; fast turns dispatch only eligible owners and owners whose daily due time has arrived. Other owners keep their daily due time, and their last outcomes remain visible in status without recounting prior deletions. The scheduler uses `CORAL_JOBS_RETENTION_DAYS` (default 14). Each owner receives its own 5-second cooperative budget. Mutation authority expires at that deadline, on shutdown, or on writer park, including when filesystem reads complete late. An unsettled owner is skipped on subsequent cycles with `previous-owner-still-running` status until its outstanding work finishes. The scheduler stops on shutdown or writer park, and publishes typed deleted/kept/failed outcomes through backend status. No hook performs retention. The five-minute delay leaves a long idle interval between bounded owner turns on WSL ext4; asynchronous discovery and yields between small synchronous transactions let the five-second provider heartbeat continue. `deletedByOwner` adds directory, progress-row, holder-marker, scratch-artifact and custody-entry and reclaimed-vacuum-page counts without changing the aggregate count.

Detailed health projects each list to its first 20 entries and exposes original totals in `listCounts`, keyed by field path. Health responses that are oversized or cannot be parsed remain unknown to supervisor readiness; they do not authorize startup termination while the child continues answering heartbeats. Detached provider lifecycle initialization remains visible until it succeeds, retries transient failures automatically, and marks initialization complete only after durable disposition reconciliation succeeds.

Malformed retention metadata is preserved under `storage-retention.quarantine.v1.<original-key>`, removed from the active key, and reported once per changed value. Bookkeeping restarts enumeration; deletion admission and retirement evidence resets keep their subject for fresh observation, so a reset does not grant deletion authority. `store/epoch/holder.ts` removes a marker only when its own process is proven absent; an epoch-wide lock held by a newer process cannot hide a dead marker.

Compaction persists identity-keyed refusals under `job-locations.v1/compaction-refusals.v1`, advances past damaged records, and retries them daily; readable evidence clears the refusal. Custody discharge uses `JobLocationIndex.resultDurable` independently for each job: validated retained terminal detail is required before either a regular nonempty durable file, known expired-age discharge, or validated unknown-age legacy terminal with an absent export directory and includes both the initial identity-bound child root and all transferred roots. Missing or unobservable evidence holds custody until daily reconciliation can prove those obligations. Recovered export retirements commit validated admission and initial evidence before their first deletion batch. Every deletion mutation, the first leaf and each later batch included, reads the job's terminal eligibility and result hold again; once either stops authorizing deletion, deletion stops and the retirement is kept as `terminal-eligibility-changed`. Repair failures and pending repair use the five-minute retry cadence. A run that cannot execute an owner preserves its due slot and schedules another attempt after five minutes. Other owners use fast backlog cadence only after their own progress or budget exhaustion; held owners without progress and failed owners keep their daily cadence even while another owner drains a backlog.

Historical source ownership is a projection of the store inventory. Store open and every five-second epoch sweep register each present non-active epoch once, including preserved epochs and epochs protected after startup. The maintenance owner probes certified sources too and settles after three failed attempts. It hydrates at most 16 subjects per synchronous slice, closes the source guard between slices, and yields between epochs. Reads observe protected paths without publishing addresses. Only protection owners (`protectMintPredecessors`, `retryPendingProtections`, and the post-ready `reconcileProtectedEpochs`) publish protected addresses. Unknown discovery preserves the last known cursor membership, progress position and acknowledgement flags.
