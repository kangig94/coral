# Architecture

Coral is a coding-assistant plugin for Claude Code, Codex, and GitHub Copilot CLI. Its purpose is to help LLM agents do software work better: plan/review workflows, side-effect and bug discovery, multi-perspective discussion, durable job observation, session continuity, and long-term project memory through KB.

Internally, Coral is a local coding-agent coordination layer. Claude Code reaches Coral through hooks, slash-command skills, and Bash calls to `coral-cli`. For local mutating and live-follow commands, `coral-cli` ensures the backend daemon is running and talks over the authenticated IPC socket. Read-only no-coordinator paths use the `read-model/CoralStore` facade directly. HTTP remains available as the remote gateway plus the operational carveouts (`/health`, `/admin/shutdown`, `/events/stream`). No bridge or stdio proxy remains in the runtime path.

Coral also has a build flavor axis. `prod` is the marketplace-installed runtime and `dev` is a local build meant to coexist with it on the same machine. Each bundle embeds `version`, `buildSetId`, `flavor`, and `storeFormatFingerprint`; the adjacent manifest in the active artifact directory repeats those fields and binds the backend, CLI, and Claude helper by content hash. Ordinary and dev builds use `clients/build/manifest.json`; published release bundles use `clients/bridge/manifest.json`. The embedded identity and adjacent manifest form one matched attestation set. `CORAL_FLAVOR` is only a session-level hook selector that decides which hook set should execute.

A build that cannot present that attestation set does not borrow an identity. `resolveStrictBundleIdentity` (`infra/bundle-manifest.ts`) answers `embedded_identity_unavailable` both when the four injected constants are absent — a source checkout, where nothing replaced them — and when they are present but hold values its schema refuses, so this is a bundled build's failure mode too and not a source-mode-only path. On that one reason startup continues (`coordinator/composition/world.ts`) and mints a fresh `buildSetId` for the boot, so no two boots ever claim the same build; every other reason concerns the adjacent manifest — missing, invalid, or disagreeing — and still aborts. Such a boot does not inherit an earlier run's proxy set: redemption compares the durable record's `buildSetId` against its own, answers not-bequeathed before reading a capsule, and leaves the abandoned set to its own orphan deadline. Store selection recovery has no staged-reset resume or parked-active-evidence protocol: it durably republishes the retained transition and selection, then settles the selected store epoch through the ordinary startup routing path.

## Design Frame

The product frame is coding assistance. The architecture frame is local coordination. "Control plane" in this document is internal vocabulary: the coordinator owns local decisions, live state, recovery sequencing, and capability activation so Claude/Codex do not have to manage those concerns inside prompts or shell glue.

| Product capability                  | Internal owner                              |
| ----------------------------------- | ------------------------------------------- |
| Plan/review workflow                | Workflow plan + jobs execution              |
| Side-effect and bug discovery       | Workflow slots, provider jobs, wait/follow  |
| Idea digging and multi-agent review | Discuss domain and shell                    |
| Long-term coding memory             | KB Corpus authority + retrieval projections |
| Provider conversation continuity    | `ProviderSession` aggregate                 |
| Executable work ownership           | `ExecutionOwner` on every job               |
| Long-running observable work        | Jobs authority                              |
| Optional sharper retrieval          | KB daemon expansion lifecycle               |

This frame constrains new code: first name the truth owner, then decide whether the work is direct, durable, or projection freshness, then compose cross-domain behavior only in the coordinator or CLI.

## Provider Usage Reporting

Usage is captured at each provider boundary before provider-specific stream shapes enter the jobs domain. Providers normalize their raw counters to the canonical additive `UsageSummary`: `{ inputTokens, cacheReadTokens, cacheWriteTokens, outputTokens, costUsd }`. Token totals are derived by renderers from the four token buckets and are never stored as `totalTokens`.

The canonical storage home is the job terminal record's `diagnostics.usage` field. In the read model, that lives in `projection_jobs.diagnostics`; live wait, replay wait, SSE reconnect, and job detail all read usage from the same terminal diagnostics instead of recomputing it from provider artifacts.

Provider transports are intentionally asymmetric because Coral records only what the provider reports:

- Claude print (`claude -p` stream-json) reports token usage and `total_cost_usd`, so Coral can render both tokens and `costUsd`.
- Claude TUI reports token usage from the transcript but no cost, so Coral renders tokens only.
- Codex reports tokens only, captured from the native `thread/tokenUsage/updated` notification (`tokenUsage.total`, a cumulative `TokenUsageBreakdown`). Its `cachedInputTokens` are a subset of `inputTokens`, so Coral subtracts cached input before storing fresh `inputTokens` and records cached input as `cacheReadTokens`; Codex has no `costUsd`.

Workflow usage is not written onto `workflow.completed`. It is aggregated at read time by summing child job `diagnostics.usage` rows where `projection_jobs.parent_workflow_job_id` is the workflow job id. Token fields are summed across children, including children that failed after spending tokens. Cost is summed only where present; mixed-provider workflows render partial cost as `$X+` with `(+N jobs without cost data)`.

User-facing usage surfaces are deliberately narrow. `coral-cli wait` appends usage only to terminal completion lines, with `--verbose` expanding the four token buckets. `coral-cli jobs detail <jobId>` renders the terminal diagnostics usage, and workflow detail uses the same read-time aggregate as wait. When cache-read tokens dominate the total, renderers add the honesty annotation `(NN% cached)`; detail uses the fuller cache-read annotation with `billed ~0.1×`.

`GET /jobs` accepts optional `projectRoot`, `phase`, `provider`, and `all=1` query filters. Without `all=1`, the list stays live-only (`queued`, `launching`, `running`) and remains sorted by `updatedAt` descending.

Error responses use real HTTP status codes: 400 (validation), 403 (scope mismatch), 404 (not found), 409 (conflict / non-resumable or provider-mismatched session), 503 (recovering / busy).

Accepted launches use explicit, discriminated identifiers. Provider launches return `{ kind: 'provider-session', jobId, sessionId, launchState }`; workflow launches return `{ kind: 'workflow', jobId, workflowId, launchState }`. Owner, binding, and workflow-lifecycle conflicts are typed 409 responses rather than opaque internal errors.

The provider-session branch of `LaunchDecision` has three answers: accepted (`running` or `queued`), `refused`, and `undetermined`; its workflow branch has no `undetermined` answer because workflow submission performs no provider preflight. The launch wire seam is the only place a status is assigned, and for provider preflight that status preserves the answer boundary: 503 means the answer was not established and the request may be repeated; 400 means it was refused. A preflight that returns no valid answer at all escapes instead as the internal fault `provider_preflight_faulted`, with HTTP 500 and CLI exit 70 — it is not a third undetermined cause. Who classifies what, and what counts as no valid answer, is in `docs/core-modules.md`; the operator-facing mappings are in `docs/cli-errors.md`.

`POST /kb/sources` accepts `{ filePath, slug?, readiness?, async? }`. It does not accept pre-staged markdown paths from clients. Source conversion, staging, persistence, progress, terminal outcome, and failure causes are coordinator-owned as an internal `kb.source_import` job. `readiness` defaults to `base-search` and may be `commit`, `base-search`, `active-vector`, or `all-equipped`; `async: true` returns 202 with the job id immediately, while the default waits for the requested readiness and returns 201 after the completed import.

`POST /kb/index` rebuilds KB text artifacts through an internal coordinator-owned `kb.reindex` job and waits for base-search readiness before returning. The job is recorded for recovery and observability, but it is not a provider/session job.

Raw work-directory spellings stop at transport ingress. Capability authorization happens before filesystem access; then Coral resolves the directory with `realpath`, rejects missing or non-directory targets explicitly, and authorizes resource binding against the canonical project root. Internal launch, workflow, recovery, provider-host identity, and displayed cwd values carry that same canonical value. A symlink and its target therefore identify one provider-server specification rather than silently creating separate hosts.

## Work Classification

Not every command becomes a job. Jobs are for work that is long-running, observable, resumable, or recovery-relevant. Immediate reads and small mutations remain direct commands.

| Class                     | Examples                                                               | Surface                                                             | Rule                                                                                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Direct read               | `kb read`, `kb principles`, KB metadata lists, `jobs`, `discuss watch` | Return result immediately                                           | No job id; uses `read-model/CoralStore` direct library reads. KB list/read paths do not persist derived rebuild artifacts.                                                             |
| Served read               | `kb search`                                                            | Return result immediately                                           | No job id; routes through IPC to the KB daemon's hot search runtime and never builds a library-direct lexical index.                                                                   |
| Direct mutation           | KB note write/delete; memo write/delete                                | Return result after the small write                                 | Corpus writes use the KB mutation lock. Memos are project-scoped scratch artifacts (under `runtime.paths.projectData(projectRoot)` — see design-rationale §5.3), not Corpus authority. |
| Provider job              | `codex`, `claude`, workflow/discussion children                        | Return job and provider-session ids; `wait` observes terminal state | User-facing provider work is Journal-observable and recoverable.                                                                                                                       |
| Internal coordinator job  | `kb source import`, `kb reindex`                                       | Default may wait; `async` returns job id                            | Used when source conversion, indexing, or readiness can take time.                                                                                                                     |
| Projection freshness wait | Active retrieval-consumer catch-up after Corpus commit                 | `ConsumerDriver.waitFreshUntil(...)`                                | Freshness wait is not itself truth; failure reports against the hosting command/job.                                                                                                   |

Every job has an `ExecutionOwner` independent of provider continuity. A direct provider job is owned by its `ProviderSession`; a workflow root owns itself; workflow children are owned by the workflow; discussion children are owned by the discussion; KB work is owned by a system task. Only provider jobs have a non-null provider-session id. Workflow queued wait events carry `workflowId`, and KB queued events carry `systemTaskId`, instead of fabricating `sessionId: ''`.

`kb source import` is job-backed because it can spend time reading and converting large documents before committing Corpus markdown. With retrieval readiness, it also waits for the applicable active retrieval consumers. By contrast, KB read/list commands, note write, memo operations, and principle reads are direct unless a future implementation gives them durable work to recover. `kb search` is a served read owned by the KB daemon, but it is still not a job. Direct list/read commands may build transient in-memory views, but explicit `kb reindex` owns durable text-artifact repair.

Direct does not mean ambient. CLI/bootstrap adapters choose the active plugin root, build flavor, project root, Corpus markdown root, and KB runtime root before calling KB/read-model code. KB path helpers and `read-model/CoralStore` do not silently fall back to the current working directory or the user's home KB.

## Primary Execution Flows

### Session lifecycle

1. `coral-cli codex -i ...` or `coral-cli codex <agent> -i ...`
2. The CLI client calls `POST /sessions`
3. The transport layer validates the direct body, builds `CallerContext`, and forwards a domain-shaped request into the coordinator
4. The coordinator API resolves agent intent, persists session continuity, and launches or resumes work through jobs-owned launch/admission contracts plus sessions-owned continuity storage
5. Provider adapters spawn the real CLI/runtime and emit progress
6. Journal appends publish projection freshness through the live `ConsumerDriver`; session continuity remains authoritative in the sessions shell

### Proxied provider execution

An app-server operation does not have to run inside the coordinator. When a live guardian/reaper/proxy set exists for the job's executable identity, the coordinator sends a strictly-validated, data-only prepared envelope and the **proxy runs the kernel in its own process** — which is the point: the carrier outlives a coordinator restart.

Publication is a durable saga rather than a returned transport result. Before each prepare send, the coordinator commits a `prepare-pending` record containing the exact attempt fingerprint. Proxy preparation and guardian authorization advance that record through explicit phases; only `operation.activate.v1` can start the kernel. A complete activation ACK then commits the `executing` phase and `job.runtime.started` in one SQLite transaction. Lost replies leave a named phase for `inspect.v2` and the reconciler to resolve, while `cancel.v2` can prove an attempt never started without reconstructing a reservation. **No operation is reported executing without both a real activation ACK and committed saga evidence.**

Events may be buffered after the kernel starts, but they cannot leave the proxy until the coordinator commits `executing + job.runtime.started` and attaches the operation to the current control epoch with `operation.attach.v1`. They then travel back over that connection as `provider.event.v1` — the one method in the protocol that runs proxy-to-coordinator. Each is applied durably by `applyProviderEventAtSeq` and acknowledged only after its transaction commits.

That makes durable-effect authority exclusive, and the two paths are kept apart structurally rather than by discipline: a proxied job returns from `executeJob` before the local consume/finalize path is ever entered, so the applier is the only writer. Running both would record every terminal twice.

The coordinator still owns what it is responsible for. `LocalOperationRegistry` holds each executing saga record, its stop capability, and exact proxy-binding cleanup identity. Admission itself issues one generation-bound `LaunchPermit` carrying reservation, job, pool, provider, holder, and acquisition time. Release accepts that permit rather than reconstructing authority from job and pool: a stale reservation reports `already-released`, a holder change reports `transferred`, and only the matching current permit returns capacity and admits the next queued launch. When a terminal or suspension commits, the registry routes binding settlement and process-local cleanup; the binding owner releases the exact permit. Without that path the durable state would be correct while finished work continued to hold launch capacity.

With no live set, the route returns explicit local authorization. Acquisition is deliberately fire-and-forget, so a cold start never waits on a proxy handshake.

### Provider-host serviceability and recovery

A provider host has three independent states. They answer different questions and must not be collapsed:

| State          | Vocabulary                                | Question answered                                      |
| -------------- | ----------------------------------------- | ------------------------------------------------------ |
| Process        | `open \| closed`                          | Is this concrete provider process present?             |
| Serviceability | `unknown \| serviceable \| unserviceable` | Has it produced typed evidence that it can serve work? |
| Admission      | `candidate \| blocked`                    | May fresh work be placed on this host slot?            |

This is intentionally not carrier-liveness vocabulary. Carrier observation asks whether work is still there; the incidents handled here involve a provider process that is present but cannot serve. Each new host instance starts at `unknown`, and `unserviceable` is terminal for that instance. Serviceability is derived only from a completed provider response. For Codex, a successful required `config/read` prerequisite is `serviceable` and its typed failure is `unserviceable`; unrelated responses remain `unknown`. A silent request and a host/process fault publish no response fact at all. There is no clock, elapsed-time comparison, retry count, or transport timeout that turns silence into a finding, so a mute host may remain `unknown` indefinitely.

A negative finding changes fresh-placement admission only. It does not close the process and does not gate exact attachment, because an already-running job still needs that attachment for provider interrupt and probe. If a blocked process exits naturally, its owner retains a `retired-blocked` tombstone with canonical non-secret metadata and bounded diagnostic evidence; the slot remains blocked. The only path that clears either blocked form is an operator eviction of the exact `HostRef`, after the owning process has closed that live host or confirmed the retained tombstone's process is absent.

Host ownership is process-local in two places. `DefaultProviderHostManager` owns coordinator-local hosts, while each provider-proxy process owns the hosts used by operations routed through that proxy. Both run the same admission model, but each performs its own placement and physical eviction. The RPC boundary performs capability and resource authorization before calling `ProviderHostAdministrationService`; the service itself receives no principal. It captures the current owner set and, for exact-reference eviction, first asks every owner whether it retains a terminal disposition for that reference. One match reconstructs the route and replays the eviction through that owner; no match falls through to complete-inventory selection; multiple matches are identity corruption. An unavailable owner fails the whole request, so neither discovery nor inventory selection can silently omit part of the federation. `--work-dir` is only a convenience resolver over complete inventory: it is canonicalized relative to the CLI invocation root and refuses zero or multiple matches rather than guessing. See [Configuration](./configuration.md#provider-host-recovery) for the operator commands.

Containment follows those two ownership boundaries but shares one low-level primitive. It exists because a provider can leak its own children: a codex app-server spawns MCP servers per thread and does not reap them when those threads end ([openai/codex#30408](https://github.com/openai/codex/issues/30408), open). Coral cannot repair lifecycle ownership inside codex, and it never attributes a descendant to a session — codex itself does not track which MCP belongs to which thread, so any such attribution would be resemblance rather than identity. Containment instead reclaims by group at host teardown, which needs no descendant enumeration. Provider-host admission requires Linux; any other platform is refused before spawn and directs the operator to run Coral on Linux. The provider server is spawned `detached`; before the entry becomes live, the coordinator reads the child's process incarnation, proves `kill(-pid, 0)` can address the new group, and records `{ pid, incarnation, processGroupId: pid }` on the entry. Either identity check failing kills the child and refuses admission. Teardown uses `reapRecordedContainment`, which revalidates identity before SIGTERM→SIGKILL escalation and stable absence observation. That check is fail-closed rather than exhaustive: if the leader PID has been recycled, Coral still probes the numeric group to distinguish absence from a surviving or unobservable group, but it never signals that group because ownership can no longer be proven. Surviving members of the original group may therefore remain. The guarantee is never to signal the wrong group, not always to reap ours. The provider proxy uses the same primitive at proxy-set teardown. Its app-server is deliberately not detached again; per-host close signals only that child, so leaked descendants can remain inside the guardian-established set until set teardown.

Pins, not job counts, authorize idle retirement. Each `ProviderHostEntry` keeps a `Map<PinToken, ProviderHostPin>` whose acquisition and attached-session pins carry origin metadata and are released by idempotent closures; `activePinCount` is the map size. For shared hosts, `idleRetirement` names the condition: `'unleased'` permits retirement after the last pin releases, `'unleased-and-host-idle'` additionally requires an idle `host/stats` report, and `'never'` retains the host until explicit shutdown. Codex uses `'unleased'` because Coral's pin ledger sees its work. Claude uses `'unleased-and-host-idle'` because its broker multiplexes sessions that the pin ledger cannot see; `host/stats` is emitted by that Coral-owned broker, not by the external codex app-server. A diagnostic names every outstanding pin when no live Codex job owns the host, but never closes on that observation: an attached-session pin has no job id, so zero jobs does not prove zero attachments.

Completed-response diagnostics retain the typed RPC result and the sequenced host-log interval occupied by that request, with explicit truncation markers. This separates a call's cause from accumulated process stderr and keeps the same evidence available after a blocked host retires. It does not repair either upstream root cause: provider-side resource exhaustion can still make a host mute, and provider per-cwd state can still reject `config/read`. Coral now makes both incidents scoped, diagnosable, and recoverable without restarting the daemon or disturbing unrelated hosts.

### What a coordinator restart does to a running job

This is the question proxied execution exists to answer. Clean shutdown only relinquishes control sooner; it does not create recoverability.

A fresh set receives one exact-set recovery credential before it becomes visible to routing. Guardian, reaper, and proxy retain the credential digest; the protected mode-0600 capsule retains its secret. Every operation is registered into the set's succession membership before prepare, so the durable journal always names work a successor can recover.

After either graceful control release or an abrupt transport loss, the successor computes the capsule address from the operation identity and set locator in the saga journal, redeems the set in guardian → reaper → proxy order, and registers the recovered set before resolving any individual operation. Each `executing` row is independently attached at its durable watermark; the other phases resume their phase-specific reconciler work. An indeterminate `operation.attach.v1` outcome is retry-safe and cannot authorize set reaping; `control_client_closed` and malformed unattributable frames are narrower channel incidents and cannot enter the terminal-fault union. Heartbeats use the transport's closed `ControlExchange` directly. `provider-proxy/heartbeat-observation.ts` alone decodes that exchange into a branded reply, no-response, locally-unsent, delivery-unconfirmed, or channel-fault observation. A timeout or close after write is retryable no-response evidence; a socket error after write is delivery-unconfirmed, a local-failure outcome that cannot advance a peer-silence window. Request encoding and synchronous write failures are locally unsent and likewise cannot enter that window. A well-formed but unusable reply remains answered evidence and can only reach the coordinator's separately bounded independent-absence containment wait. That wait does not send the destructive control RPC; once both enforcers are proven absent, the read-only containment prover returns the recorded targets and the provider-proxy-set lifecycle reaps the orphaned proxy group through `reapRecordedContainment`. Only the endpoint's complete JSON-RPC `invalid_request` refusal shape can name `teardown-latched` as terminal. If an accepted echo's response was lost, the endpoint returns `heartbeatRefusal: challenge-mismatch` plus a fresh `nextHeartbeatChallenge` on the tenancy's own socket, allowing the establish retry or next periodic tick to resynchronize without treating the mismatch as displacement.

Ambiguous redemption failures and retry-safe attachment failures remain retryable; a transport error is never translated into operation absence. Only a typed `operation-absent` proof resolves that exact `executing` row as provider-lost. If exact containment disappearance is proven instead, each saga phase follows its own durable outcome: prestart phases complete local placement or their terminal directive, ambiguous activation terminalizes without fallback, executing terminalizes without re-execution, and settlement deletes its already-terminal tombstone.

Every mutation control policy declares how an indeterminate outcome affects supervision. `operation.attach.v1`, `operation.settle.v1`, and `operation.stop.v1` are retry-safe and stay on the non-consuming incident channel. `operation.prepare.v1`, `guardian.operation-activate.v1`, `operation.activate.v1`, and `operation.cancel.v1` require containment and may consume the terminal authority-fault latch. Heartbeat silence stays on that same incident channel; an accepted echo revives the lease even after its clock window. The enforcer's own tick classifies the admitted control holder `alive | absent | unobservable` from a recorded-process observation and mints a demolition capability only on proven `absent`, never from elapsed time alone; the coordinator's bounded silence hold joins its two siblings on the non-destructive `await-containment-absence` action instead of starting a destructive attempt by itself. Control-channel close and invalid-unattributable-frame observations stay on the incident channel regardless of the interrupted method.

A channel incident moves the established slot to `reattaching`, removes its route immediately, stops the displaced generation's heartbeats, and leaves durable claims attached. This is not heartbeat silence: it has its own first monotonic observation and one absolute adoption-window deadline. Each attempt runs authenticated three-role redemption beside independent containment proof. A branded success rebuilds the complete operation authority before it is promoted, restores the prior `available` or `draining` state, restores routing only for `available`, invalidates old callbacks by attempt token, and notifies establishment so live operations reattach to newly built controls. Refusal stops redemption immediately; unavailability may retry only inside the original bound. Refusal and expiry both enter `await-containment-absence` without calling `stopAndReap`; after guardian and reaper are both proven absent, the read-only prover supplies the exact recorded targets and the lifecycle reaps the orphaned proxy group before entering the existing disappearance-delivery path.

The channel hold also has an exact-set operator exit after its recorded monotonic adoption-window deadline:
`coral-cli backend provider-proxy-set contain <pps1-token>`, where `backend status` supplies the canonical token
and live-claim count. Its opaque capability can be minted only for a held set after that deadline. Confirmed
absence enters the ordinary disappearance path; observed-live and unobservable enforcers remain refusals unless
the operator explicitly runs `coral-cli backend provider-proxy-set abandon <pps1-token>`, which releases representation through a separate
faultless action and claim-acceptance path without minting absence. A local unreadable-row fence cannot be
overridden. Ordinary shutdown remains handoff and reports every decoded set token plus whether its best-effort
inventory was complete. A fault-driven `containing` or `containment-wait` hold uses a fixed 30-second
containment-attempt observation gate instead of the configured adoption window. The forced route signals the
recorded proxy process group and every recorded provider root for the set that is observed present through
`reapRecordedContainment`. Guardian and reaper are never signalled; successful containment requires both to
have been observed absent, while explicit abandonment may leave either live because it sends no signal.

Each role and method has one exclusive heartbeat evidence window: `clear | silence | answered-unusable`. An unusable answer replaces silence with a fresh answered-unusable window; a later no-response replaces answered-unusable with a fresh silence window. Accepted echoes and current-tenancy resynchronization clear either prior state. The shape therefore cannot retain a stale silence timestamp beside answered evidence. The guardian and reaper each hold an armed enforcer. Before publication, no operation authority has been returned and no claim can exist, so the tick lets the pure clock bound decide even when an installed provisional holder is unobservable — the one place elapsed time alone still authorizes teardown, and nothing is at risk when it does. Once a holder is published, that adoption deadline no longer latches teardown on elapsed time: `createArmedEnforcer`'s tick (`src/provider-proxy/enforcement.ts`) instead classifies the admitted control holder `alive | absent | unobservable` from a recorded-process observation, renews the check on `alive`, holds on `unobservable`, and mints a demolition capability only on proven `absent` — `buildDeadlines` (`src/provider-proxy/role-main.ts`) is constructed only inside `startProviderGuardianRole` and `startProviderReaperRole`, never `startProviderProxyRole`, so no enforcer exists to observe holder absence for the proxy's own `control.heartbeat.v1` hold at all. Where an enforcer does exist, it is anchored on its own role's round-trip evidence: the guardian's `adoptionDeadline()` advances on the coordinator's heartbeat *to the guardian*, a channel independent of the coordinator's heartbeat *to the proxy*, so a coordinator starved specifically toward the proxy — while the guardian and reaper keep answering normally — never reaches that deadline either. A containment-required control call against the wedged role reaches `faultAuthority` through `routeControlCallFailure`'s `requires-containment` policy independently of any of the above, but only if some operation attempts one; a job already `executing` and merely waiting attempts none. `containment-proof` is not itself a trigger: it is the absence half of a containment attempt already started. Silence containment runs it beside `role-control`'s `stop-and-reap`; answered-unusable exhaustion and `method_not_found` run the independent proof without treating the answering roles as custody of the set. `coral-cli backend shutdown` reaps a live set only in `shutdownModeFromReason`'s hard mode, and this command never reaches it: both its IPC dispatch (`transport/ipc/server.ts`) and its HTTP handler (`transport/http/handler.ts`'s `/admin/shutdown`) hard-code `reason = 'replaced'`, which maps to handoff. Handoff calls `releaseHandoffAuthority` instead, preserving the set for a successor to redeem rather than ending the hold — so running this command against a live, wedged set hands the same wedge to the next coordinator rather than closing it. Ending one exact held set is `coral-cli backend provider-proxy-set contain <pps1-token>`, which is deliberately a separate operation: a routine restart must not reap live provider work. Hard mode is real and does reap every live set, but it is reached only by a `sigint` shutdown or an internal provider-proxy lifecycle fatal, never by an operator's own shutdown request.

The provider-proxy reducer separates silence from an answer this build cannot use before coordinator policy sees either. After `heartbeatHoldBound.spanMs` of continuous silence without material scheduler starvation, `heartbeat_hold_exhausted` joins its two siblings on the non-destructive `await-containment-absence` action rather than `stop-and-reap`: with zero live claims the coordinator stops heartbeating, closes control, and waits for independent containment absence, exactly as `heartbeat_answer_unusable_hold_exhausted` already does. With live claims present none of the three heartbeat sources may authorize destruction on their own; the coordinator instead records a held, non-authorizing disposition and keeps the route and heartbeat loop running. After both enforcers are proven absent, the read-only prover supplies the exact targets and the lifecycle reaps the orphaned proxy group. A decoded `method_not_found` clears the prior window, skips timing, and takes the same `heartbeat_protocol_incompatible` containment path. Neither path treats a role ACK or owner label as discharge. The heartbeat loop records `observedWake − requestedWake` on the monotonic clock and carries that delay beside the branded observation for its exact role and method. The observation that opens a window contributes no accumulated lateness because the window begins at that observation; only later observations add `schedulerLatenessAfterFirstObservationMs`. `providerProxyHeartbeatHoldBound` derives the span and material-lateness threshold from per-set timing — resolved configuration for fresh acquisition or the redeemed capsule for an inherited set. The threshold is one quarter of the span, requiring at least three quarters of a candidate window to remain attributable to heartbeat work. Reaching it resets that evidence window. At the default timeout the span is 23 seconds and material lateness is 5.75 seconds. The enforcer and coordinator window share a formula and monotonic instrument, but not an anchor or an ordering; an endpoint may accept an echo whose reply the coordinator never receives. Human-readable `unanswered`, `unclassified`, and `method-not-found` labels are derived only after the reducer transition and never feed policy.

One recovery consumer seam is a deliberate exception to that separation. Capsule discovery at boot can meet a handoff capsule this build may not dial — an earlier bundled build's, left by a rollback, an upgrade, or a reinstall — and retiring one is a boot's housekeeping rather than a claim on any authority, so on the `foreign-capsule-retirement` seam every producer disappointment reaches the incident channel and none reaches the global fatal sink. Three things can end an attempt short of retirement: the producer reporting the capsule directory not durable, a rejection carrying a filesystem error code, and a fulfillment the producer's own outcome schema refuses. All three are owner-local and retryable, the reported incident kind distinguishes them, and it carries an operating-system code wherever one could be read. The retry is bounded at five attempts and the last failure reaches a named terminal rather than another wait: the retirement owner is dropped, the capsule keeps the conservative representation installed for it for the rest of the boot, and a later boot retries it from discovery while it stays readable. Abandoning that hold on a count is only sound because the owner holds a path and nothing else — no acquisition capacity, no claim, and no absence slot — so dropping it strands nothing.

The lifecycle emits one pinned log record before route removal, heartbeat shutdown, containment, or reaping. Its base message body and field order are exactly `Provider proxy set action=<action> reason=<reason> fault=<kind|none> subject=<role|method|retirement> liveClaims=<n> set=<key> error=<formatted|none>`. After the evidence-window transition, heartbeat records derive `incidentReason=<unanswered|unclassified|method-not-found>` for preserved or protocol-incompatible decisions, `terminalReason=<teardown-latched|local-failure>` for the endpoint's own decisive refusal or this process's locally unsent call, or window evidence as `attempts=<n> elapsedMs=<n> schedulerLatenessMs=<n> lastIncidentReason=<x>`. A channel-reattachment record instead appends its exact `cause=<closed|invalid-unattributable-frame>` and `attempts=<n> elapsedMs=<n> boundMs=<n>`. Coalesced preservation records may then append ` summary=<kind> suppressed=<n>` after that base. `/health` and `backend status` use the existing per-set disposition for active heartbeat holds, channel-reattachment holds, and containment waits. While reattaching, that disposition carries the exact set, triggering role and cause, attempts, elapsed time, absolute-window bound, and live claim count; refusal or expiry replaces it with an awaiting-absence disposition naming which outcome ended reattachment. The entry is removed when the slot is discharged, so completed sets do not accumulate in coordinator-lifetime history. The logging intent is INFO for expected preservation and retirement decisions and WARN for authority loss, hold exhaustion, and protocol-incompatible containment; an authority-loss message's own `set=` reference is shared with the corresponding job terminal message for correlation. Slot removal accepts only the lifecycle's opaque combined discharge: branded process-containment absence plus branded durable-claim discharge. A zero-claim set mints the claim half only after rechecking the claim mirror, and a claim-bearing set mints it only after every disappearance delivery is accepted. A claim-bearing retirement records `drain` first and, only after the claim count reaches zero, records a distinct zero-claim `stop-and-reap` transition.

Every saga row, including `executing`, is excluded from generic carrier recovery. Startup and control-established workers select the reconciler phases, active proxy deadlines drive remote release, and exact disappearance provides the phase-specific final exit.

### Wait / follow

1. Detached provider launches print `Provider job <jobId> <launchState> (provider session <sessionId>)`; detached workflows print their `workflowId` and `jobId`
2. `coral-cli wait jobs <id...> [--embed]` opens the `jobs.wait` IPC subscription
3. The local IPC stream and the remote `POST /jobs/wait` HTTP gateway both read the same coordinator-owned wait surface, which uses the same job truth as startup recovery and steady-state launch orchestration
4. Terminal text always includes `Result path: <path>`; `--embed` may add preview text, but the durable artifact is always at the printed path
5. Terminal completion lines append usage when available, for example `Job <id> completed · $4.18 · 18.6M tokens (90% cached)`; `--verbose` expands the input/cache-read/cache-write/output breakdown

Each projected job retains two coordinates. `projection_jobs.project_root` is the launcher's project identity and continues to drive project grouping. `projection_jobs.work_dir` is the canonical directory where provider or workflow work ran; KB jobs alone store it as `NULL`. Ambient selectors such as `abort --all|--phase|--provider` and unfiltered event streams require exact work-directory equality, while explicit wait, abort, and detail requests accept a job only when the caller's directory contains its `work_dir`. Both relations apply to non-KB jobs; a KB job belongs to no single work directory and matches from every caller directory. `coral-cli jobs` requests all projects and therefore bypasses the ambient selector, then groups results by `project_root`. Neither relation treats a descendant caller as authority over an ancestor job.

### Carrier observation

Observable liveness is derived; stored lifecycle and mutation authority are not. A read never rewrites stored phase, and **only the journal ends a job**.

The coordinator classifies a job's carrier — the thing actually running the work — from its in-memory admission state, operation registry, the OS process table, and the durable-CLI identity row. The verdict is deliberately tri-state:

| Verdict   | Meaning                                  | Wait effect                            |
| --------- | ---------------------------------------- | -------------------------------------- |
| `live`    | positive evidence the carrier is running | none; the wait continues               |
| `absent`  | positive evidence it is gone             | emits a nonterminal `interrupted` line |
| `unknown` | no evidence either way                   | treated as conservatively active       |

Only `absent` is a positive finding. `unknown` means the question was not answered; it is not a weaker `absent`. A transport error, timeout, unsupported endpoint, malformed or relationally mismatched reply, exhausted observation budget, predecessor build, or unreadable process incarnation remains compatible with the work still running, so every consumer treats `unknown` as active. A transport error never becomes `absent`.

Absence is established, never inferred from a pid. The kernel reuses pids, so a durable CLI is judged on the recorded pid's liveness and on its **process incarnation** matching the token captured at launch. A failing fact does not become `absent`; it becomes `unknown` wherever the failure is itself unobserved. Missing runtime metadata, metadata naming a different pid, and a live pid whose incarnation cannot be read are all `uncaptured` — the last deliberately, because an unreadable identity cannot distinguish a recycled pid from the same process (`composition/carrier-observation.ts`). Only a pid observed dead, or a successfully probed incarnation that differs from the recorded one, can establish `absent`. An app-server operation with no live entry in this coordinator generation's operation registry — not yet attached, inherited from a predecessor, or already settled and evicted (`LocalOperationRegistry.settled` deletes rather than marking it ended) — has no decisive local evidence. Health and idle leave it `unknown`; only an open wait subscription may ask the recorded proxy through `operation.status.v1`. The proxy returns ledger liveness only, with the nonce, exact proxy instance, build set, and complete requested operation relation echoed so the coordinator can reject a stale or mispartitioned answer. `held` becomes `live`; `absent` is the only answer that becomes `absent`; every failure to obtain that exact answer remains `unknown`.

The boundary this buys is enforced, not conventional: `tests/invariants/no-carrier-observation-in-action-paths.test.ts` proves no recovery, cleanup, reconciliation, terminal-materialization, or other action path can obtain a carrier verdict **at any import depth**, over runtime edges only. A recovery walk that filtered candidates by observation would skip exactly the stored-nonterminal work it exists to settle; a cleanup pass that deleted on it would delete artifacts belonging to a running job. Derived absence therefore authorizes nothing: wait may render one nonterminal `interrupted` event, but it does not remove the job from the pending set, end the stream, or enter a recovery/action path. `coordinator/composition/` is the only runtime root allowed to import the classifier. It uses synchronous local classification for health and idle and injects the asynchronous external observer only into wait (`composition/execution-services.ts` to `jobs/shell/wait.ts`). Health and idle perform no network probe. The idle-retirement guard fails closed on missing services, read or mapping errors, unexpected stored phases, and either `live` or `unknown`; it does not ask a foreign process whether hard retirement is safe.

Recovery completeness is also a per-job classification, not a single global post-recovery assertion. Each coordinator owns a startup-recovery barrier; until its provider reconciliation and applicable generic recovery walk return, every job's coverage is `in-progress`. After the barrier passes, a job with a durable provider-operation record is `accounted-for`; one without such a record is `unaccounted`, and only that last state can add `local-unknown-after-recovery-decision`. This distinction is necessary because provider reconciliation may return with retries still scheduled while the generic walk deliberately excludes saga-owned jobs: crossing the barrier cannot truthfully say that every job was handled.

The operational health snapshot uses the same conservative but network-free local policy. `activeJobs` is `live + unknown`; `diagnostics.carriers` reports exact fields `{ coverage, liveJobs, unknownJobs, recoveryDefectJobs }`, where normal local classification yields `coverage: 'complete'`. If the store or classification cannot provide a complete mapping, the fallback is `coverage: 'unknown'`, `liveJobs: 0`, `unknownJobs: activeJobs`, and `recoveryDefectJobs: 0`: every job still counted active by the fallback is explicitly counted unknown rather than silently presented as live. Reading `/health` never invokes `operation.status.v1`.

### Generation boundary and operator recovery

1. Pre-boundary state remains under `data[-dev]` and `run[-dev]`; generated state lives under `gen2/data[-dev]` and `gen2/run[-dev]`. Current code never mutates or binds the legacy generation during ordinary startup.
2. Before generated initialization, readiness is one of three states: `generated-ready` proceeds; `no-legacy` initializes; `legacy-ignored` leaves legacy bytes untouched, reports the stored version or `unknown`, and initializes this generation's own state. A previous generation is never a precondition for startup and is never imported: the boundary exists to end that coupling, so whether this build could read the legacy store makes no difference to whether it boots.
3. Cold start consults `active-store-selection.v1.json` before store settlement. A selection naming a valid newer local build hands off to that build. Otherwise `store/epoch.ts` discovers the highest `epoch-<N>` directory, with the shipped flat `store.db` treated as epoch zero, and opens it writable. A compatible or `legacy-adoptable` store opens in place; an incompatible decision or thrown open publishes a fresh current-format successor. A transition from another build is retained beneath the coordination root before selection continues. Unsafe coordination paths still refuse as `active_store_coordination_invalid`, and an unresolvable running bundle refuses as `startup_bundle_unresolvable` before selection.
4. Publication constructs the database, WAL/SHM state, format sidecar, and additive `epoch.json` beneath `.mint-<uuid>`, then renames that directory to `epoch-<N+1>`. Only a mint can be renamed to an epoch destination. The superseded store is never moved or copied. `ENOTEMPTY`/`EEXIST` means another publisher won and is adopted on the next loop; `ENOENT` means the mint was swept and is rebuilt. Sweep deletes only old positive epochs outside the current/predecessor retention pair, abandoned mints, and the legacy quarantine once epoch one exists. Epoch zero remains until an explicit `release 0 --allow-unproven-legacy-reader`. Sweep failures are audited and never block boot.
5. `backend store-reset list --target <legacy|current>` classifies visible epochs read-only and appends bounded legacy quarantine rows while that root exists. `backend store-reset report --target current <epoch>` runs the bounded read-only SQLite diagnostic for an epoch; a legacy incident UUID still routes through the legacy reader. `backend store-reset release <epoch> --target <current|gen2> --flavor <prod|dev>` removes a numeric non-current epoch through the sweep owner. Its result is one of `released`, `current`, `absent`, `release-legacy-reader-unproven`, `release-metadata-unobservable`, `release-holder-live`, `release-holder-unobservable`, `release-holder-cleanup-failed`, `release-deletion-failed`, `release-lock-cleanup-failed`, `release-pre-deletion-durability-sync-failed`, `release-absent-durability-sync-failed`, or `release-durability-sync-failed`. Release and discard both take the operator socket guard and refuse a live incumbent with `coordinator_socket_in_use`; the adoption lock they also take is a performance mechanism, not publication authority.
6. `backend kb-commit quarantine --flavor <prod|dev> --commit <id>` is the explicit recovery for a `kb_commit_corrupt_or_unsupported` refusal. After `backend shutdown`, it holds the same socket → adoption → maintenance boundary, validates the single-segment commit ID before acquisition, and durably moves only that commit and matching index evidence to retained quarantine.

`backend recovery-quarantine discard-provider-operation` is the coordinator-owned destructive exit for one
exact quarantined provider-operation coordinate. Its strict CLI and RPC ingress reject a key carrying the
retired NUL-delimited subject tag. The CLI adds `allowReadable: true` only for an explicit `--allow-readable`;
without that consent a row this build can decode is refused. With consent, readable deletion still requires
the encoded record to match the requested SHA-256 fingerprint.

Composition checks the coordinator launch fence before constructing the discard service or reading the recovery
database. While startup recovery owns that fence, it returns `recovery-in-progress` with code
`backend_recovering`, message `Provider-operation discard is unavailable while startup recovery owns the launch
fence.`, and a structured discard remedy carrying the exact key, revision, and consent flag. The CLI renders
the complete retry invocation from that structure. Run it as printed once startup recovery finishes. This exit-`75`
refusal inspects and claims no raw row and performs no mutation: the raw row, due pointers, quarantine evidence,
startup permit, and launch capacity remain unchanged. It is therefore distinct from both a completed destructive
result and a no-verdict response that may follow a completed deletion.

Once the launch fence is inactive, the service claims the exact unowned quarantine subject before deletion and
never signals a process or settles the operation.

After the row is removed or observed absent, recovery releases startup permits no remaining record needs and
offers a sole surviving readable record to the reconciler. A refused adoption returns `adoption-refused` with
exit `75`, the row disposition, released-permit count, and each refused record's key, job, operation, proxy,
build set, and reason. Reconciliation and settlement have not been observed for those records; they remain
unowned and their launch capacity remains held. Composition retains the same facts with observation time in a
bounded backend-health diagnostic. Multiple readable records for one job remain an
`undecided-provider-operation` hold: neither recovery nor automatic reclamation can choose an authoritative
record without risking capacity assigned to live work, so that ambiguity requires operator repair.

Routing history has separate resolution, discard, and retained-quarantine commands. Every registered `backend routing-status` leaf passes through one exhaustive operator classification and is excluded from routing lifecycle recording; unclassified future leaves fail the CLI coverage invariant, while an unrecognized routing-status invocation remains excluded by default. `backend routing-status resolve --invocation <id>` resolves a retained opening or acknowledges a retained capacity eviction. For an opening, a decisively live owner is refused, a decisively absent owner may be resolved, and an unobservable owner requires `--force-unobservable` after external verification. The override is false by default and cannot override `deadline-expired`, because an expired sweep established nothing about the owner. A capacity acknowledgement atomically folds the exact tombstone into aggregate history; exact `operator-resolved` tombstones are already terminal information and require no acknowledgement. The resolve boundary preserves commit truth as distinct success, `artifact-refused`, `not-published`, and `commit-outcome-unknown` result arms, with the requested invocation ID intersected directly into each publication outcome instead of duplicating its discriminator; every non-validation failure contributes exit `75`. Every committed terminal remains rendered history with its policy severity but contributes `0`, while the next live invocation re-derives any recurring routing problem and its actionable exit. The journal body is also the only persisted retention authority: completed-pair stability is derived from its validated JSON during the bounded retention scan, not stored as a parallel bit. Production publication retries generation admission and SQLite contention against one monotonic deadline. It performs filesystem and WAL preflight before opening, classifies after opening but before configuration, and repeats the full classification under `BEGIN IMMEDIATE` before initialization or mutation. Maintenance winning an admission retry is reported distinctly. `backend routing-status discard` is allowed only for `detached-wal`, `generation-missing`, `foreign-generation`, `format-mismatch`, `schema-divergent`, and `unreadable`; under the coordinator-socket and generation-maintenance guards it revalidates ownership after the guarded read and quarantine scan, preserves the WAL before removing the observation-rewritten source SHM, and then preserves the main database when one was observed. A wal-only incomplete UUID-addressed set is a successful discard only when both observations found the main absent; otherwise an incomplete set refuses the next discard with its exact ID until `backend routing-status quarantine clear --id <id>` removes it. A retained WAL cannot establish the identity of a database currently at the source path. Expected pre-effect refusals and post-attempt failures are public result arms rather than throws: coordinate observation, root creation, artifact preservation, directory sync, and ownership loss all exit `75` with the exact quarantine ID and applicable repair/retry command. Moved and removed arrays contain only effects made durable by their directory barriers; successful namespace changes whose barriers fail are reported separately as observed effects. Known-empty retention names storage repair and a discard retry; known retained evidence additionally names quarantine list and exact clear. Unknown retention is a separate result arm that never reports absence and requires `backend routing-status quarantine list` to resolve the hold. Clear likewise returns typed `quarantine-clear-undeterminable` before removal and `quarantine-clear-storage-failed` for any failed removal or sync; both exit `75`, retain the exact ID, and name the exact clear retry, with storage failure also naming quarantine list. `current` and `undeterminable` refuse discard with a nonzero exit; `absent`, `vacant`, and `uninitialized` report that no discard action is needed and exit successfully. Expected socket and generation-maintenance guard failures are typed refusals: a live owner names `backend shutdown`, an unobservable socket remains a distinct no-verdict answer, maintenance contention names a later retry, an unobservable writer identity names process-observation repair or the heartbeat stale bound, and lease loss names repair of the generation coordination root followed by a fresh status read and discard retry. At most 16 complete or incomplete sets are retained; the next discard refuses until `backend routing-status quarantine list` exposes exact evidence and `backend routing-status quarantine clear --id <id>` removes an operator-selected set under the same guards. No evidence is pruned automatically. Journal and Corpus authority are unchanged by these commands.

`HandoffRoutingStoreClassification` and `readHandoffRoutingStoreSnapshotWithObservation`
(`src/store/handoff-routing-status-store.ts`) define a closed eleven-arm observational vocabulary: `absent`,
`vacant`, `uninitialized`, `detached-wal`, `generation-missing`, `foreign-generation`, `format-mismatch`,
`schema-divergent`, `current`, `unreadable`, and `undeterminable`. `readHandoffRoutingStatus`
(`src/coordinator/handoff-routing/status.ts`) projects that observation and may add owner observations, but read
authority grants neither initialization nor publication authority. Publication applies the separate total policy
and may enter SQLite mutation only through
`publishGenerationCoordinatedHandoffRoutingTransitions` (`src/coordinator/handoff-routing/status.ts`), after
generation-writer admission. Artifact classifications such as `unreadable` and `foreign-generation` are
`artifact-refused` results, not `not-published` causes, and the retired uncoordinated publication surface has no
supported import or export.

An ordinary routing writer probes the maintenance lease through heartbeat-aware lock acquisition while it holds
generation admission. A live holder still produces `generation-maintenance`; an abandoned holder becomes
reclaimable after ten minutes without a heartbeat. Publication and maintenance-refusal successors name that
retry path and forbid deleting the lease by hand.

The sixteen-set routing-status quarantine ceiling is a count bound, not a byte bound. A complete set contains the database and an optional WAL; an incomplete set contains a WAL without a database. The main database is hard-capped at 1 MiB; the WAL returns to its 1-MiB `journal_size_limit` when a checkpoint can reset it, but may exceed that limit while an open reader prevents reset, with growth limited by the writes accumulated during that reader's lifetime. Before upgrading a dev or CI checkout that used the pre-two-file implementation, list and clear every routing-status quarantine with the pre-change build. Uncleared three-file database/WAL/SHM residue is unsupported and is not swept during upgrade.

The routing-status store's schema renderer, `handoffRoutingStatusFingerprint(schema)`, and
`handoffRoutingStatusGeneration(schema)` are the canonical identity home. The fingerprint is the full 32-byte
SHA-256 identity of the canonical durable format, rendered SQL, and completed-pair stability contract. The metadata
row persists that fingerprint beside its ten-digit generation projection; the projection supplies SQLite
`user_version`, event envelopes, and the `handoff-routing.<generation>.db` address, but never replaces the full
identity check. Operational capacity remains outside the durable identity because it changes allocation rather
than decodability. Publication compares generation, the complete non-internal schema, and the persisted fingerprint
before initialization or mutation, then repeats admission inside `BEGIN IMMEDIATE`. A mismatched canonical schema
is `schema-divergent`; a matching address and schema with another full identity is `format-mismatch`.

Persisted body grammar participates in that identity by extraction from the hand-written Zod schemas through
`zodPersistedContract` (`src/infra/persisted-contract.ts`). A descriptor-first language is therefore not required,
and the claim that complete identity must cost the readability of hand-written Zod is false. The same extraction
direction already supplies production persisted contracts in `src/store/current-format.ts` and
`src/providers/registry.ts`. Callers derive the generation before passing it to the path authority; the coordinator
does not re-export it. Superseded-address artifacts remain isolated and outside the current address's quarantine
listing.

### Workflow

1. `coral-cli workflow ...` posts to `POST /workflow`
2. The workflow domain compiles the DSL into a semantic plan (slot id, dependencies, provider, instruction, optional agent)
3. The executor launches provider or `coral:` atoms through the coordinator API; launch and retry stay intertwined per architecture §10.1a
4. Workflow state is persisted as Journal events with a projection row per workflow. `workflowSlotId` identifies a semantic slot and is carried and surfaced separately from child job identity. Each child receives a separately minted canonical UUID job id from the runtime `ids` port. Recovery reconstructs the current slot-to-job mapping from durable child rows, reuses the durable job id for a slot with a current row, mints an id for a plan slot without a row, and mints a new id for the next replacement generation when a pending continuation lease requires one; job ids are never stored in the semantic plan. `coral-cli wait` reads the same job store
5. Workflow usage is resolved from child job terminal diagnostics at read time, not stored on the workflow terminal event

### Boot Eras

Backend boot is split into three sequential eras so the CLI gets a usable socket as quickly as possible and individual component failures stay isolated.

| Era                             | Owner                                        | What runs                                                                                                            | Lifecycle phase on completion                 |
| ------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| I — Kernel                      | `coordinator/lifecycle.ts`                   | Bind IPC socket, open Journal, install transport listeners                                                           | `kernel-ready`                                |
| II — Recovery                   | jobs / discuss / workflow shells             | One-shot startup reconciliation for in-flight work                                                                   | `running`                                     |
| III — Runtime Health Components | `coordinator/runtime-components/registry.ts` | Fire-and-forget `initAll()`; each `RuntimeComponent` projects daemon-visible health without blocking the kernel path | per-component `online \| degraded \| offline` |

The CLI waits for a usable coordinator (`ok`, `kernel-ready`, or `running`); Era III takes whatever time it needs without holding the CLI. A coordinator spawned by the current invocation is not cut off by any elapsed-time budget: the wait continues until that attempt reaches usable readiness or its child process reaches a terminal outcome, including across a delegated startup. A terminal child that left no refusal does not by itself end the wait either — if a coordinator still answers the address and has not named its own shutdown, the wait becomes the bounded existing-starting wait rather than a failed startup, because an incumbent the child conceded to may still be in `starting`. `KERNEL_READY_DEADLINE_MS` (15s) bounds attachment to an already-starting incumbent, and also bounds a nested command waiting for its exact parent. `HANDOFF_DRAIN_TIMEOUT_MS` (30s) bounds the incumbent's drain on socket handoff. These values are constants in `src/transport/ipc/ensure.ts` and `src/coordinator/shutdown.ts`.

Daemon-side bind handoff observes process identity, then takes a distinct liveness verdict, and observes kernel acceptance of a signal request through the selected Runtime process port. A `true` result from `ProcessPort.kill` establishes only that acceptance, never that the target dequeued the signal, ran a handler, or exited; only an accepted request starts a pending settlement and attempts ledger publication. Publication first writes an atomic V1-shaped cooldown shadow at the shipped `handoff-signal.json` address, marked with the extra `accepted: true` field that the shipped validator ignores and this build recognises. Only after that shadow succeeds may the V2 detail be written. The shipped validator can therefore enforce its cooldown without opening V2 detail, while rejected attempts produce neither record. The reader retains every matching candidate with its source-address provenance. A shared publication id only correlates this build's detail and paired shadow; independent publications are ordered by recency, a tie keeps the conservative record, and every still-active independent candidate bears on the cooldown disposition. An accepted shadow remains accepted-signal evidence when V2 is absent, while a genuine V1 entry written by the shipped build remains an indeterminate foreign attempt. A shadow failure suppresses V2 publication, and a later V2 failure leaves the accepted shadow as the fence. Ledger persistence remains best-effort, so total write failure may cost cooldown evidence but never makes a verified incumbent permanently unreplaceable. A rejected request is followed by a fresh target observation: absence returns to binding without recording a signal, observed life refuses and names stopping the target through its owning service or account, and an unverified target refuses immediately and names the observation that must recover. A bound socket completes only after the anchored target is observed absent. Any unchosen exception while handling a pending signal — including bind, poll, and post-grace discovery failures — re-observes that target: absence propagates the original error, while observed life or an unverifiable target becomes a handoff refusal that retains the error as its cause. An abort instead logs the accepted signal, target pid, and observed status before propagating unchanged; it returns no coordinator and makes no claim about the incumbent, and the next startup re-derives the target's state from its own discovery and observation. Grace expiry observes the target before any policy gate or next-signal revalidation. After the kernel accepted `SIGKILL` and its grace elapsed, a verified live target names the uninterruptible-I/O wait, an absent target names retrying the original mutating command so Coral re-observes socket ownership and removes the socket only if it proves stale, and an unverified target names the observation that must recover.

When `coordinator.sock` exceeds the platform's `sun_path` limit, the canonical relocated address is under `/tmp/coral-<state-root-hash>/`; the state root, not the caller uid or `TMPDIR`, owns that namespace. The binder still requires the directory to be owned by the calling uid with mode `0700`, so a second user of this build over the same installation refuses instead of deriving a second lock. The v0.10.9 guard uses that tag's own 104-byte Darwin/108-byte non-Darwin rule. Its path owner accepts only non-empty absolute configured and system temp directories and deduplicates the resulting addresses. If v0.10.9 would have relocated but its configured selector is empty or relative, the shipped address depended on its working directory and cannot be enumerated; this build refuses startup instead of treating that third answer as no guards. [`socket-address-ownership.md`](./todo/socket-address-ownership.md) records the remaining cross-environment limit.

Bootstrap diagnostics remain schema V1 and atomically publish one `retryable` boolean derived from `DOCUMENTED_CORAL_SETUP_ERRORS`. Backend status accepts both values, carries the distinction in `recent_failure`, and renders it without forwarding structured error context. An older reader encountering `true` treats the diagnostic as inapplicable and falls back without crashing; the diagnostic artifact and coordinator log remain the rollback-era inspection path.

#### Child Lifecycle Confinement

Coordinator lifecycle authority belongs to top-level invocations only. `ensure()` probes the socket, then routes any child-shaped invocation — `CORAL_CHILD=1`, or any non-empty `CORAL_CHILD_PRINCIPAL_HANDLE` / `CORAL_JOB_ID` / `CORAL_SESSION_ID`, so partial bindings fail closed — into an existing-only branch before it computes desired bundle identity. That branch may read discovery and poll health, and it may never request shutdown, wait for socket release, spawn `coral-backend`, clear a startup sentinel, or rotate coordinator logs. `shutdownBackend()` carries the same guard independently. A KB-disabled incumbent is never force-restarted to re-enable it: `cli/dispatch.ts`'s `reconcileKbBoot` skips its own probe entirely for a child-shaped invocation (`ipcAuth !== undefined`), and even a top-level one only warns and lets KB turn on at the next idle restart (`CORAL_BACKEND_IDLE_MS`) or an operator-run `coral-cli backend shutdown` — there is no restart call left on that path for a guard to apply to.

A child reuses only the exact incumbent it first observed. Bundle compatibility is deliberately ignored, because the child's credential lives solely in that parent's in-memory registry, so a bundle mismatch must reconnect rather than hand off. The read-only readiness loop pins socket path, instance ID, version, bundle hash, flavor, namespace, and — when both observations report them — PID and process incarnation. A draining or unreachable parent, an identity replacement, discovery that does not match the observed parent, or a timeout fails closed with top-level recovery guidance; the child never follows a replacement. The reused client carries no boot credential, so the nested command is still authorized by normal child-principal capability rules (see [CLI Errors](./cli-errors.md#nested-coral-commands)).

KB is not hosted as a coordinator component. The parent daemon registers only `createKbDaemonHealthComponent(kbDaemonSupervisor)`, which mirrors KB daemon health into `/health.components[]`; the KB daemon process owns KB runtime boot, Corpus replay, CorpusConsumer registration, Orama freshness, curate work, and expansion lifecycle. With `CORAL_KB_ENABLE=0`, the parent wires a disabled KB daemon supervisor so the health component reports terminal `offline` without spawning the KB daemon.

#### KB Daemon Protocol

Parent and child speak a newline-framed JSON protocol over the child's stdio (vocabulary owned by `kb-daemon/protocol.ts`; non-control stdout lines are ignored, stderr is buffered for diagnostics):

- **Child → parent**: `coral.kb_daemon.ready` (one-time readiness with pid/readyAt), `coral.kb_daemon.response` (correlated reply to a parent request), and `coral.kb_daemon.event` (journal/corpus events the parent ingests into the ConsumerDriver and lifecycle reactor).
- **Parent → child**: `coral.kb_daemon.request` carries KB reads, mutations, expansion RPC, job abort/list, and `shutdown`. Request ids are generation-scoped (`${generation}:${seq}`) so a reply from a previous daemon generation can never settle a current request.
- **Reverse channel (child → parent → child)**: `coral.kb_daemon.parent_request` / `coral.kb_daemon.parent_response` let the daemon call back into the parent for `curate.assistant.complete` and `curate.assistant.cancel`, since the provider host that runs the curate assistant lives in the parent.
- **Liveness**: the child runs a parent-PID watchdog (`DEFAULT_PARENT_WATCHDOG_INTERVAL_MS`, 1s) and self-terminates if the parent exits; the parent escalates a stuck child SIGTERM→SIGKILL via `gracefulKill` on start-timeout and stop.

### Discuss and KB

- `coral-cli discuss ...` maps to resource routes under `/discuss/*`; the discuss domain exposes explicit coordinator-facing owner modules for commands, reads, and recovery rather than a compatibility `api.ts` facade
- `coral-cli kb ...` maps to resource routes under `/kb/*`
- Discuss follows the functional-core / imperative-shell pattern: the core is pure event-sourced state transitions; the shell carries persistence, loop control, and subflows
- KB markdown is the Corpus authority for notes, sources, principles, communities, and wiki entries. Memos are project-scoped scratch artifacts that can be promoted into Corpus notes or wiki entries. Source import and explicit reindex are job-owned by the coordinator because they can be long-running; lightweight KB reads, note mutations, wiki mutations, and memo operations stay direct commands.
- KB markdown syncs across machines through git. Custom merge drivers make derivative files converge where possible (`.entity-graph.json`, note/source/community frontmatter), while tracked provenance (`inputFingerprint` and `summaryInputFingerprint`) lets a peer skip LLM work already computed for the current content.
- Retrieval projections are CorpusConsumers. The `kb.fts`, `kb.vector`, and `kb.embedding` `RuntimeBinding<Backed<T>>` cells are constructed empty; bundled Orama binds `kb.fts` during expansion lifecycle startup, while installed Gemini and ONNX engines can bind `kb.embedding`. No current first-party package fills `kb.vector`; external engines may do so through the same capability contract. Commands that need retrieval readiness wait through `ConsumerDriver.waitFreshUntil('corpus', snapshot, consumerId)` instead of polling expansion status.

Live launch capacity is owned by exact `LaunchPermit` values rather than an ambient job-to-pool lookup. A
permit has one current holder; holder transitions preserve its reservation identity, and release succeeds
only for that exact reservation and holder. The maintenance sweep considers aged permits but reclaims one
only with evidence matched to its current holder. Local-execution and recovery holders require an absent or
terminal job. A proxy-operation holder additionally requires absence of that exact operation record; an
undecided-provider-operation holder requires absence of the exact held record-key set. Both provider-operation
proofs retain the underlying absent-or-terminal job evidence. System-task and queue-handoff holders are not
automatically reclaimed. Reclamation returns capacity to the permit's own pool and admits that pool's queue
head.

Backend health exposes actionable launch state rather than a bare active total. `backend status` renders
reportable permits with reservation, job, pool, provider, held age, holder, and execution owner; non-releasing
attempts with the attempted holder and either an already-released disposition or the transferred current
holder; automatic reclamations with age, evidence, and reclamation time—the provider-operation evidence
includes its operation ID or exact record-key set plus the job evidence; and provider-operation adoption
refusals with the trigger and refused record identities,
row disposition, released-permit count, reason, and observation time. Release, reclamation, and adoption-refusal
history is bounded in memory.

Daemon-owned state is account-neutral. The `store`, `coordinator`, `exports`, `engine`, `projects`, and KB runtime families use one canonical tree per flavor; `CODEX_HOME` and `CLAUDE_CONFIG_DIR` never participate in path composition. Account selection crosses the transport boundary as validated request context. A real `ProviderSession` stores the immutable binding for one provider conversation; workflow and discussion roots persist the complete provider scope used to create future children. Recovery rehydrates those durable values and never lets the daemon boot environment choose later requests. See design-rationale §5.4.

The core architectural boundary is simple: the CLI is the only local command surface, the backend is the only daemon surface, and all long-running or resumable work is tracked as backend jobs.

Store-reset operation and legacy reporting are deliberate local carveouts for times when the daemon is unavailable. The destructive service lives in `src/store/operator-store-reset.ts`; the CLI validates flags, supplies runtime/build identity, and renders results. `backend store-reset list` classifies each epoch read-only and appends rows from the bounded legacy incident reader while the old quarantine root exists. `backend store-reset release <K>` always takes the operator socket guard and generation-adoption lock before routing epoch removal through `sweepStoreEpochs`; it returns the complete typed success, semantic-refusal, deletion, lock, and durability failure union. The adoption lock coordinates operators but is not correctness authority. `backend store-reset discard` takes the same guards, then publishes the next epoch regardless of classification. `report <K>` runs the unchanged read-only SQLite child against the selected epoch when its store file set fits `MAX_SQLITE_DIAGNOSTIC_BYTES`; legacy `report <uuid>` remains available while quarantine rows exist. No operator path restores a legacy incident as active state.

Routing-status discard and quarantine clear use the same offline layering. `src/coordinator/handoff-routing/status-operator.ts` owns authorization and the socket → generation-maintenance → guarded re-read → mutation sequence; `src/store/handoff-routing-status-store.ts` owns raw quarantine moves and removal. `src/cli/routing-status-discard.ts` only supplies the real socket guard, and command registration parses arguments and renders the typed result. No additional offline carve-out is required.

Ordinary builds generate one build-set UUID and one store-format fingerprint embedded across the backend, CLI, and Claude helper, then write the authoritative adjacent `clients/build/manifest.json` with hashes for all three artifacts. Releases copy every artifact byte-for-byte into `clients/bridge`; they do not regenerate identity. Hidden package probes and the build/release contract verifiers execute all three artifacts against that manifest, verify all three artifact hashes, require byte equality between build and release copies, and enforce the package file allowlist.

## Design Rationale

For the **why** behind these structures — the duality of authorities, causal-graph fault model, provider stream composition, the Zelda Expansion philosophy, naming/subdivision policy with rejected anti-patterns — see [`docs/design-rationale.md`](design-rationale.md).

## Rewrite Policy

The rewrite branch is clean-slate. Retired module paths, compatibility shims, and fallback aliases are not kept for convenience. If an old path no longer represents the owner, it is deleted and guarded by invariants. When implementation reveals a better owner than the document predicted, update the document and code together rather than preserving a transitional layer.

## Terminal Outcome Model

Terminal results carry a typed outcome (`TerminalOutcome`) — a discriminated union owned by the jobs domain:

- `completed` — provider turn finished successfully.
- `aborted { reason }` — closed-token reason: `signal_abort` | `user_abort` | `queue_shutdown`.
- `provider_exit { code, note? }` — provider process terminated with a numeric exit code.
- `failed { causeRef }` — upstream cause resolvable via the Journal (`CauseRef = { stream, seq }`).
- `job_fault { fault }` — typed job-lifecycle fault (ghost launch, wrapper loss, wrapper crash).

Journal reads use only the strict current domain codecs. Runtime job ingestion emits canonical domain events directly; incompatible persisted shapes change the application-wide store fingerprint and trigger destructive reset rather than translation.
Domain registries own event schemas, append validators, and reducers. `store/` runs composed validators transactionally before insert, but does not hardcode domain vocabulary.
`job.terminal.recorded` stores `{ terminal, diagnostics?, continuity? }`: output and outcome stay under `terminal`, provider warnings and canonical `diagnostics.usage` stay under `diagnostics`, and session continuity stays in the explicit continuity snapshot. `diagnostics.usage` is the durable home for provider usage; renderers derive total token counts from its additive buckets instead of storing a separate total.
Raw `job.terminal.recorded` object construction is owned by `jobs/store.ts`; providers, workflows, KB internal jobs, and recovery code finalize through jobs-owned append/materialization APIs.

CLI wait output surfaces the outcome through five exhaustive headers, followed by a usage segment when terminal diagnostics carry usage:

```
Job <id> completed
Job <id> aborted: <reason>
Job <id> provider exited <N>[: <note>]
Job <id> failed: <cause description>
Job <id> errored: <sentence> [<kind>]
```

The trailing `[<kind>]` tag on `errored` lines is the machine-readable classifier (regex `/\[(\w+)\]$/`).
