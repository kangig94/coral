# CLI Errors

`coral-cli` writes a text error envelope to `stderr` for all commands. The envelope is human/LLM-facing and contains only the public message, stable tags, and optional authored remediation. Backend diagnostic context stays out of this default text surface. Parsers should not assume the message/head portion is single-line because Commander-surfaced errors may contain newlines.

`wait` and follow-mode commands keep successful human-readable text on `stdout`. Only failures move to `stderr`.

## Envelope

CLI errors use this shape:

```text
timeoutSeconds: Number must be less than or equal to 1200 [code=invalid_request, http=400]
```

Fields:

| Field         | Type             | Meaning                                                                                                                                                                  |
| ------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `message`     | string           | Human-readable summary. It is not guaranteed to stay on one line                                                                                                         |
| `code`        | string           | Stable programmatic error code, emitted inside the trailing tag block                                                                                                    |
| `http`        | number, optional | HTTP status when the error came from a backend HTTP response                                                                                                             |
| `remediation` | string, optional | Operator-actionable hint included by backend error paths (e.g. `kb_initializing`, `kb_offline`). Surfaced after the message so wrappers can present a concrete next step |

Backend HTTP errors are lifted into the same envelope. Transport-only diagnostic fields are not rendered.

Backend IPC errors are lifted the same way. Mutating and live commands reach the coordinator over IPC, and a JSON-RPC rejection carries its public `{code, message, remediation?}` in the error data. The CLI reads that payload, so an IPC rejection surfaces its own code and exit code rather than a generic internal failure. When an IPC rejection carries no recognized `code`, the CLI falls back to `ipc_rpc_error`.

When a backend HTTP response body is missing, non-JSON, or does not carry a `code`/`message` field, the CLI falls back to:

- `code`: `backend_error`
- `message`: the client-side HTTP status description (e.g. `HTTP 503 Service Unavailable`)

This only affects malformed or truncated backend responses. In normal operation every backend error path emits `{code, message}` and is surfaced unchanged.

Provider endpoint construction reports a settled ownership, entry-type, or parent-permission refusal as `proxy_endpoint_insecure`, with `refusal` set to `foreign`, `unusable`, or `unsecurable`. It reports no settled verdict as `proxy_endpoint_unverified`, with `refusal` set to `unverified`: an operation may have failed, a successful observation may have reported no owner, or the fallback address may have named an unusable uid. Consumers must not interpret that code as an insecure-directory verdict.

The coordinator's schema-V1 `startup-diagnostic.json` carries a boolean `retryable` derived from the documented setup-error registry. `store_open_contended` writes `true`; undocumented failures and documented codes without an authored retry policy write `false`. `backend status` accepts both values, preserves the boolean in `recent_failure`, and renders it. This is intentionally a tolerant same-address extension: an older build already rejects `retryable: true` as an inapplicable diagnostic and falls back to its ordinary no-daemon status instead of failing startup. That rollback loses the recent-failure rendering, but the diagnostic file and coordinator log remain available; moving the same payload to another address would make it equally invisible to that shipped reader without improving safety.

Provider-host `list` and `inspect` can report `reclamation-failed`. This status means the coordinator did not complete a provider-host close or recorded-containment reclamation, not that the host was classified broken. Its host metadata always names `reclamationAttempts`, `reclamationFailure`, and `reclamationRetryable`. Before a process handle exists, `pid` and `processGroupId` are absent; after a process is observed but before group authority is recorded, only `pid` is present; recorded containment carries both values. Use `reclamationRetryable`, not field presence, to choose the response. For a retryable reap failure, `provider-host evict <ref>` joins an in-flight attempt or starts another and clears the row only after absence is confirmed. Identity-verification and pre-containment failures are not retryable, and eviction cannot recreate missing process authority; preserve the inspect output and escalate rather than discarding that evidence by restarting.

## Exit Codes

| Exit | When used                                                                                                                                                                                                                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `2`  | `invalid_usage`, `invalid_store_reset_incident_id`                                                                                                                                                                                                                                                                                           |
| `1`  | User-correctable backend/domain errors such as `invalid_request`, `not_found`, `session_not_found`, `audit_requires_ended_session`, `scope_mismatch`, `unauthorized`, `kb_unavailable`, provider-host errors other than `provider_host_inventory_unavailable`, the generation-boundary/operator codes whose rows below say `1`, `store_reset_incident_not_found`, `store_reset_incident_limit_exceeded`, and default `backend_error` cases |
| `75` | Temporary holds and no-verdict refusals: `transient`, `backend_shutting_down`, `kb_disabled`, `kb_initializing`, `kb_offline`, `store_open_contended`, `provider_host_inventory_unavailable` (matched by code name because the IPC path carries no HTTP status), and `coordinator_unreachable`/`coordinator_record_unreadable`/`coordinator_socket_dir_unverified`, plus `legacy_source_writer_observation_unknown` when a generation's writer lease could not be observed at all, plus generic HTTP `503` fallback. Documented-code exits come from `DOCUMENTED_CORAL_SETUP_ERRORS` through `errorCodeToExit`; `coral-cli expansion` delegates error results to that same mapper. `store_open_contended` is positive evidence of contention and is deliberately not a member of `NOT_OBSERVED_CORAL_SETUP_ERROR_CODES`. Retry only when that code's remediation says the condition can clear without intervention |
| `69` | `backend_unreachable`                                                                                                                                                                                                                                                                                                                        |
| `77` | Authorization failures that no retry fixes: `missing_capability` and `child_credentials_incomplete`. The same code is used by `coral-cli expansion …`, whose single-JSON-line output carries these two codes as an `InstallError`                                                                                                            |
| `70` | `internal`, `internal_error`, `store_open_unclassified`, `store_reset_build_mismatch`, `store_reset_incident_build_mismatch`, `store_reset_reporting_failed`, and generic HTTP `500` fallback                                                                                                                                                |

`kb_unavailable` deliberately remains exit `1` when mapped by code alone. Its remediation requires equipping the
missing engine rather than waiting for an observed temporary hold, and this preserves the code-only mapping from
before documented exits moved into the registry. A transported HTTP `503` still contributes the generic exit
`75`, as it did before centralization; documented codes with an explicit non-default exit keep that authored
exit. The registry sweep found no other existing code whose code-only exit changed: `startup_not_ready`, `kb_initializing`, `kb_offline`,
`coordinator_unreachable`, `coordinator_record_unreadable`, and `coordinator_socket_dir_unverified` remain `75`;
all other pre-existing documented codes remain `1`. The new `store_open_contended` and
`store_open_unclassified` codes deliberately add exits `75` and `70` respectively.

`coral-cli backend shutdown` also exits `75` when the command has no verdict about whether a coordinator stopped. That group includes an unreadable discovery record (`unreadable_record`); a missing record while the current socket is present (`no_record_socket_present`); a refused connection (`socket_refused`); a response that did not resolve the shutdown request (`refused_by_response`); a request that never completed (`no_response`); and both absence-evidence outcomes. `no_record` found neither a discovery record nor this build's current socket, but that file evidence can miss a live v0.10.9 coordinator at an unenumerated custom fallback before it publishes. `recorded_process_absent` directly confirms that the process named by the record is gone, but the record may be stale while a different coordinator has bound its socket and not yet published its own record; the v0.10.9 custom-fallback window is one way this happens, not the only one. The formatter therefore states the evidence for each outcome and explicitly declines to report that the backend stopped. `socket_refused` belongs to the same group because an absent recorded pid short-circuits before any request is sent, so the refusal proves only that nothing answered at that exact socket at that moment; a coordinator's HTTP listener can also close at the top of its drain while its confirmed-live process continues through IPC close and store finalizers. The remaining refusals exit `1`: `capability_rejected` is a coordinator that answered and declined, while `nested_child` is a stable local prohibition that refuses before observing the coordinator because a nested Coral child must never drain the coordinator its parent job runs on (see [Nested Coral Commands](#nested-coral-commands)). The distinction is load-bearing because [Configuration](./configuration.md) requires a successful shutdown before `store-reset discard` or `kb-commit quarantine`: only exit `0` authorizes the destructive follow-up. Exit `75` means "do not proceed without a verdict," not necessarily "retry until success." For example, `unreadable_record` remains `75` until a person repairs or removes the discovery record. Retry only where the specific remediation says the evidence can change without intervention. A caller running under `set -e` stops on every refusal, as it should; it must not reinterpret either absence-evidence row as permission to continue. The full mapping is `SHUTDOWN_REFUSAL_EXIT_CODES` (`src/cli/commands/backend.ts`), which is exhaustive over `ShutdownReason` so a new refusal cannot inherit either answer by default.

shutdown reason, mode, or exit code. `backend status` supplies the token and live-claim count. Its result and
claim-discharge result are separate discriminators, with this exhaustive treatment:

An older coordinator's JSON-RPC method-not-found or a structurally identified result whose newer shape this CLI
cannot decode becomes a named `75` no-verdict telling the operator to upgrade or restart, rerun status, and
retry. A coordinator that starts draining before the request also becomes a named `75` no-verdict, but tells the
operator to wait for the successor before rerunning status. None is rendered as an internal parse error. Forced
containment may signal the recorded proxy process group plus every recorded provider root for the set that is
observed present. Guardian and reaper are never signalled; the contained outcome was authorized only after both
were observed absent. An `--abandon-without-absence` outcome may leave either enforcer live because that mode
releases representation without signalling or asserting process absence.

`coral-cli backend status` sets an exit code too, for the same reason `backend shutdown` does: `backend status && <destructive op>` used to read every outcome, including "state is unknown," as permission to proceed. Its daemon-status contribution is `0` for `ok`, `not_running`, `shutting_down`, `unauthorized`, and `recent_failure`, and `75` for `undecodable_record`, `unreachable`, and `no_record_socket_present` (the coordinator's own IPC socket exists with no record written yet — the same boot-race/stale-socket evidence `backend shutdown` reports as `no_record_socket_present`). `not_running` covers both no record/current socket and an observed-absent recorded pid. The residual unpublished window can reach the first path directly and the second through a stale record, so its `0` reports a completed read and does not override the configuration rule that only a successful `backend shutdown` authorizes a destructive follow-up. The command also composes its process-local handoff preflight: of the eight production-reachable routing bases, `same-build-set` and `incumbent-absent` contribute `0`, while the other six contribute `75`; an abandoned handoff whose stdout did not drain also contributes `75`. The composition helper additionally maps no live result and a display-only continuation to `0`, but those are isolated/default test-seam states, not states that reach the production `backend status` action. Only `incumbent-unresolved` is not-observed evidence; the other five nonzero routing-basis contributions mark decisive conditions requiring operator attention, including the ordinary same-version/different-build-set case. For `incumbent-unresolved{cause:'health-shape-rejected'}`, daemon status may still render the peer as healthy, so the successor does not delegate to daemon remediation: run `coral-cli backend shutdown`, then run any `coral-cli` mutating command (or start a Claude Code session) to relaunch the backend from the current installation. A structurally valid provider-proxy-set row whose `disposition`, `cause`, or `waitingFor` value this build does not recognize no longer produces that cause: the health reader skips the row, and `backend status` contributes `75`, prints every retained set token, and names the exact `backend provider-proxy-set contain <token>` command while stating that it cannot show those rows' dispositions, causes, or waiting conditions. A malformed row or non-array `providerProxySets` value still rejects the health shape. Known provider-proxy-set rows render the guardian and reaper observations separately whenever a status disposition carries them. The other two unresolved causes continue to use the daemon-status remediation.

The same local composition includes the routing journal and this process's publication incidents. An absent journal contributes `0`; an unreadable, unsupported-generation, or undeterminable read contributes `75`. A current journal contributes `75` for an absent unresolved owner, an unobservable unresolved owner except `probe-not-available`, or an exact `selection-evicted-at-capacity` retirement; otherwise it contributes `0`. On platforms without incarnation inspection, a positive PID-liveness result maps to `probe-not-available`, while an unexpected PID-probe error maps to `probe-failed` and therefore contributes `75`; unknown liveness never inherits the unsupported-platform `0`. Every committed terminal is history and contributes `0`, while its info or warning severity remains visible in the rendering. The exit-code distinction is hold versus history, not severity. A `continued-current{reason:routing}` terminal therefore remains rendered with its basis's info/warning severity but contributes `0`, because the routing lifecycle is complete and `resolve` can only answer `already-terminal`; its publication successor says that routing finished and the local operation continues, not that the operation finished. The six warning routing bases still contribute `75` when re-derived as the current process's live routing result, so a recurring peer defect remains actionable. Delegated exit/signal, execution failure, recording gaps, and terminal-after-resolution disagreement remain warning-severity history and contribute `0`; the child exit or live routing result already carries the actionable signal. Exact `operator-resolved` and completed-pair-compaction tombstones are also history and contribute `0`. A publication refusal or `undeterminable` incident contributes `75`. A `not-published{invalid-record}` incident contributes `70`, while every other `not-published` cause — `contended`, `generation-maintenance`, `capacity-exhausted`, `io-failed`, `unreadable`, `unsupported-generation`, `rejected-transition`, and `coordination-unavailable` — contributes `75`. Local contributions use explicit precedence `70` over `75` over `0`, so an internal invalid-record defect is not hidden by a simultaneous temporary hold. A delegated `backend status` whose child succeeds applies that same incident arbitration; any nonzero child exit passes through unchanged. The daemon mapping and composition live in `BACKEND_STATUS_EXIT_CODES` and `src/cli/commands/backend.ts`; the one total not-published mapping is `HANDOFF_ROUTING_NOT_PUBLISHED_EXIT_CODES` in that CLI module. The basis mapping remains `HANDOFF_ROUTING_BASIS_OBLIGATIONS` (`src/coordinator/handoff-routing.ts`), and the continuation mapping remains `HANDOFF_CONTINUATION_REASON_OBLIGATIONS` (`src/coordinator/handoff-runner.ts`). Every publication incident carries its exact invocation ID, and terminal incidents also carry the terminal disposition being recorded. Cause-specific repair comes first. An `execution-failed` terminal retains the original error's remediation without adding a journal-status exit contribution. A delegated success says the child operation succeeded and should not be rerun. A delegated nonzero exit or signal defers to the child's own diagnosis instead of replacing it with a generic success. The formatter always prints the concrete `--invocation` value. Recording-refusal `reason` and `remediation` enum tokens remain internal; the CLI renders human diagnostics and successors instead.

An unreadable or unsupported routing journal is a durable `75`, so `backend status` names `backend routing-status discard` as its successor. That operator-only command accepts only those two decisive read states, holds the coordinator socket and generation-maintenance lease while it re-reads the artifact, revalidates lease ownership after the read and the bounded quarantine scan, and lets the next publication initialize a clean journal. SQLite sidecars move before the main database; the main move completes the set. A failed sidecar move therefore leaves the source database in place and any already-moved sidecar visible as an incomplete quarantine. The next discard refuses with that exact set ID because the retained sidecars do not prove ownership of the database currently at the source path; the operator exit is `coral-cli backend routing-status quarantine clear --id <id>`, followed by a fresh discard. A completed discard exits `0`. A current or undeterminable journal is a refusal and exits `75`; an ambiguous I/O observation never authorizes quarantine. An absent journal still renders that there is nothing to discard, but exits `0` because the requested artifact already does not exist. Socket ownership, socket unobservability, an insecure socket directory, generation-maintenance contention or ownership loss, an incomplete quarantine, and quarantine capacity are typed discard refusals, and each exits `75`. A live coordinator names `coral-cli backend shutdown`; socket unobservability is rendered as no verdict rather than as either ownership answer. Maintenance contention says to wait and retry discard, while ownership loss says to repair the generation coordination root, rerun status, and then retry discard. A storage failure before the first artifact is moved still throws because there is no durable effect to reconcile. After the first move, storage failure returns a typed `75` outcome carrying the exact quarantine ID and moved artifact set; the CLI names `routing-status quarantine list`, the exact clear command, and a fresh discard. Unexpected implementation failures still throw. Routing history is derived operational evidence, so this operation does not alter Journal or Corpus authority.

Routing-status quarantine retains at most 16 complete or incomplete database sets and never silently prunes them. `coral-cli backend routing-status quarantine list` shows each visible exact ID, path, artifact set, and completeness; a bounded-list overflow exits `75` and tells the operator to clear visible entries and list again. At the ceiling, discard refuses until the operator uses `coral-cli backend routing-status quarantine clear --id <id>` for evidence that is no longer needed. Clear permanently removes one exact set under the same socket and generation-maintenance guards; it removes sidecars before the main retained database so a failed attempt remains listable and retryable. A clear storage failure before the first removal still throws. After the first removal, it returns a typed `75` outcome with the exact ID and removed artifact set, then names quarantine list and the same exact clear command as its successor. A missing exact ID is idempotent success. An exact retained `selection-evicted-at-capacity` tombstone contributes `75` because its invocation identity remains actionable through `backend routing-status resolve --invocation <id>`; its rendered line also says whether a terminal was recorded before acknowledgement. A successful acknowledgement folds the exact tombstone into aggregate history and exits `0`. Exact `operator-resolved` tombstones render `owner-absent` for a decisive absence or `operator-abandoned-unobservable` for a forced abandonment, so the latter's weaker owner evidence remains visible even though both are terminal information with exit contribution `0`. Once exact identity expires by acknowledgement or retention pressure, the `retirement-history-truncated` aggregate remains rendered but contributes `0`: the aggregate deliberately retains no identity an operator could act on.

`coral-cli backend routing-status resolve --invocation <id>` has its own command-level exit contract. Its return type preserves publication truth at the outer boundary with distinct successful, `not-published`, and `undeterminable` arms; an undeterminable commit is never represented or rendered as not published. The failure arms are `Readonly<{invocationId: string}> & Exclude<PublicationOutcome, {kind: 'committed'}>`, so the publication outcome's discriminator is also the result discriminator and cannot disagree with a nested copy. `HANDOFF_ROUTING_RESOLVE_EXIT_CODES` (`src/cli/commands/backend.ts`) is exhaustive over the non-publication-failure result kinds: `resolved`, `acknowledged-capacity-eviction`, and `already-terminal` exit `0`; `stale` and `live-owner` exit `1`; `unauthorized-unobservable` and `status-unavailable` exit `75`. The separate canonical `HANDOFF_ROUTING_NOT_PUBLISHED_EXIT_CODES` maps `not-published{invalid-record}` to `70` and every other `not-published` cause to `75`; the distinct outer `undeterminable` arm always exits `75`. Unsupported generation is decisively `not-published` because validation precedes the commit attempt. A failed resolve result retains the requested invocation ID, so its successor prints a directly reusable command rather than an `<id>` placeholder. A decisively absent owner may be resolved; a live owner must finish first. An unobservable owner requires `--force-unobservable` only after external verification, and `deadline-expired` cannot be overridden because it describes the observation budget rather than the owner. For an exact capacity-eviction tombstone, the same command acknowledges the named loss and atomically folds its identity into the informational aggregate.

`coral-cli wait jobs` reuses exit `75` for a second, unrelated meaning that is not one of the failures above: `src/cli/follow.ts` calls `errorCodeToExit('transient')` when the bounded wait's timeout elapses, or a `waiting` event names still-running jobs, while jobs remain outstanding. That is an expected, benign pause — the jobs are still running, not failing — and the fix is to resume, not retry: rerun with the printed `--cursor` value. See [Skills](./skills.md) and the provider skill files (`clients/skills/*/SKILL.md`), which document this same code as part of the `wait jobs` monitoring contract.

An interrupted live wait also exits `75` with code `transient` when its delegated child ends from a signal, its subscription exhausts transient retries, or its initial subscription attempts exhaust while the backend is recovering or draining. The error keeps the signal or subscription diagnostic as its message and adds an exact remediation command: `coral-cli wait jobs <remaining-job-ids>` before any subscription opens, or `coral-cli wait jobs <remaining-job-ids> --cursor <current-cursor>` after the CLI has observed a wait position. Exhausted `backend_unreachable` attempts remain code `backend_unreachable` with exit `69`; the backend must be made reachable before the wait can resume. A second locally received Ctrl+C remains different: it aborts the jobs and exits `1`; when the first local Ctrl+C is reflected back as delegated `SIGINT`, the CLI reconnects instead of emitting an error.

### Provider-proxy role process exit codes

These are process exit codes for the backend artifact (`coral-backend.cjs`) itself when dispatched into a
guardian, reaper, or proxy role via `--provider-guardian` / `--provider-reaper` / `--provider-proxy
<capsule-path>` (`src/coordinator/bootstrap.ts`) — not `coral-cli` exit codes, and not part of the stderr
error envelope above. They let an operator reading a role process's own exit code tell which role failed to
start without correlating it against a log line, and are distinct per role and from `0` (success), `1` (a
coordinator's own generic startup failure), and `70` (`--print-store-reset-build-identity`'s own strict
identity failure):

| Exit | Role       |
| ---- | ---------- |
| `71` | `guardian` |
| `72` | `reaper`   |
| `73` | `proxy`    |

These three codes cover only a failure inside `runProviderRoleMain` after role dispatch succeeded. Parsing
the role invocation itself (`parseProviderRoleArgv`) happens earlier and is not wrapped in that same
try/catch: a malformed invocation — an unparseable or non-canonical capsule path, two role flags, or two
occurrences of the same flag — throws synchronously out of `main()` and is caught only by the top-level
`.catch()`, which exits `1`. A malformed provider-role argv therefore exits `1`, the same generic code as an
ordinary coordinator startup failure, not a distinct code.

## Validation Timing Matters

Two failures can both mean "bad input" and still produce different exit codes because they were caught at different stages.

Client-caught example: local CLI validation (e.g. `parseIntegerFlag`) fails before any backend request, producing `invalid_usage` and exit code `2`.

```text
--<flag> must be an integer [code=invalid_usage]
```

Server-caught example: the CLI accepts the flag shape, but backend Zod schema validation rejects the value. The call reaches the backend, which returns an authored `invalid_request` message and exit code `1`; the raw issue list is not printed by the default CLI formatter.

```text
<field>: <constraint> [code=invalid_request, http=400]
```

The input is wrong in both cases. The exit code differs because `invalid_usage` is rejected locally, while `invalid_request` is rejected by backend schema validation.

## `503` vs Unreachable

Two "service unavailable" cases also differ on purpose:

- `backend_shutting_down` means the backend answered and said it is draining. Its exit code is `75`, and this specific condition can clear when the drain finishes.
- `backend_unreachable` means the CLI could not talk to the backend at all. Exit code is `69`, which usually means the daemon needs to be started or restarted first.
- `kb_initializing` and `kb_offline` mean the daemon answered, but the KB daemon runtime specifically is not ready. The daemon itself is healthy — only KB-touching commands surface these. Both map to exit `75`.

Drain-in-progress example:

```text
Backend shutting down [code=backend_shutting_down, http=503]
```

Backend-not-running example:

```text
fetch failed [code=backend_unreachable]
```

## Nested Coral Commands

A `coral-cli` invoked from inside a provider job (a Coral child) reconnects to its parent coordinator and never starts or replaces one. Three failures are specific to that boundary, and all three tell the operator to go back to the top-level Coral session:

- `child_credentials_incomplete` (exit `77`) — the child binding was partial, so the command was rejected locally and no request was sent.
- `missing_capability` (exit `77`) — the child principal is valid but its capability set does not cover the command. The denial is authoritative; the parent's capability set is not negotiable from the child.
- `backend_unreachable` (exit `69`) — the parent coordinator was unreachable, draining, replaced, or too slow. The message states that no coordinator was started or replaced and points at `coral-cli backend status` from the top-level session.

`coral-cli backend shutdown` from a child is refused for the same reason and exits `1`, because a child must not drain the coordinator its parent job is running on.

## Consumer Examples

Retry only on retry-later failures:

```bash
#!/usr/bin/env bash
set -o pipefail

stderr_file="$(mktemp)"
trap 'rm -f "$stderr_file"' EXIT

while true; do
  if coral-cli wait jobs "$JOB_ID" 2>"$stderr_file"; then
    exit 0
  else
    wait_status=$?
  fi

  stderr_text="$(cat "$stderr_file")"
  case "$stderr_text" in
    *"[code=transient"*|*"[code=backend_shutting_down"*)
      sleep 2
      ;;
    *"[code=backend_unreachable"*)
      echo "Coral backend is not reachable; restart it first." >&2
      exit "$wait_status"
      ;;
    *)
      printf '%s\n' "$stderr_text" >&2
      exit "$wait_status"
      ;;
  esac
done
```

Branch in an LLM/tool wrapper by the trailing `code` tag:

```ts
type CliError = { message: string; code: string };

function parseCliError(stderr: string): CliError {
  const match = stderr.match(/\[code=([^,\]]+)/);
  return {
    message: stderr,
    code: match?.[1] ?? 'unknown',
  };
}

function classify(error: CliError): 'fix-input' | 'retry' | 'restart-backend' | 'run-at-top-level' | 'escalate' {
  switch (error.code) {
    case 'invalid_usage':
    case 'invalid_request':
    case 'not_found':
    case 'session_not_found':
    case 'scope_mismatch':
      return 'fix-input';
    case 'transient':
    case 'backend_shutting_down':
      return 'retry';
    case 'backend_unreachable':
      return 'restart-backend';
    case 'missing_capability':
    case 'child_credentials_incomplete':
      return 'run-at-top-level';
    default:
      return 'escalate';
  }
}
```
